# Проектные решения (ADR-лог)

Формат: решение · причина · статус. Изменения утверждённых пунктов ТЗ фиксируются здесь и в `CHANGELOG.md`.
«Допущение» = технический выбор из §9 ТЗ, который можно пересмотреть.

## D-001. Godot 4.7.2 stable .NET + C# (net8.0)
Рекомендовано ТЗ. Установленная версия: `4.7.2.stable.mono.official.ed1daf0bf`, .NET SDK 8.0.133.
`GodotSharp` 4.7.2 собран под .NET 8, поэтому все проекты — `net8.0` (переход на `net10.0` возможен позже
без изменения кода). Beta/dev-версии движка не используются. **Статус:** принято.

## D-002. Рендерер Compatibility (OpenGL 3.3)
Минималистичная графика прототипа не требует Forward+; Compatibility запускается на любой Windows-машине
(включая встроенную графику и удалённые рабочие столы) и даёт одинаковую картинку при проверке.
Особенность: рендерер затеняет в sRGB-пространстве, поэтому цвета вершин/инстансов передаются без
линеаризации (`VisualConfig.ToRenderColor`). **Статус:** принято (допущение).

## D-003. Pointy-top, odd-r offset для хранения, axial/cube для правил
Как в ТЗ §3.1. Порядок направлений `E, NE, NW, W, SW, SE` фиксирован и задаёт порядок обхода соседей.
`HexDirection` используется и как направление взгляда (тип `FacingDirection` из ТЗ). **Статус:** принято.

## D-004. Структура решения
Godot-проект лежит в `src/GodotClient` и ссылается на чистые сборки через `ProjectReference`; чистые
сборки и тесты не попадают в папку Godot-проекта (не импортируются движком). Решение `HexTactics.sln` в корне,
`dotnet/project/solution_directory="../.."`. Конфигурации решения: `Debug`, `ExportDebug`, `ExportRelease`
(как ожидает Godot). **Статус:** принято.

## D-005. Данные карты — текстовый файл `.hexmap`
Простая читаемая сетка токенов (см. ARCHITECTURE §5), разбирается в Core и тестируется без движка.
Клетки зон появления обязаны лежать на краю карты. Редактор карт — вне этапа 1. **Статус:** принято.

## D-006. Визуальный стиль прототипа
По запросу пользователя — «базовые геометрические примитивы 3D-редактора»: светло-серые матовые
гексагональные призмы, препятствия — поднятые тёмно-серые колонны, база — голубоватый тон, зоны появления —
песочный тон, мягкая направленная тень, тёмный нейтральный фон. Границы клеток — тонкие бледные линии
шейдером в мировых единицах. **Статус:** принято (допущение, уточняется визуальными тестами).

## D-007. Камера и область UI
Ортографическая камера, возвышение 60° (ТЗ §3.2). Панель HUD слева шириной 272 px (× масштаб UI);
камера вписывает поле в оставшуюся область, поэтому UI не перекрывает поле на 1920×1080, 1600×900, 1366×768.
Масштаб UI = высота окна / 1080, округление 0.25, в пределах 1..2. **Статус:** принято.

## D-008. Единый источник версии
`Directory.Build.props` (`HexTacticsVersion`) для .NET и `project.godot` (`config/version`) для движка;
`tools/build_release.ps1` отказывается собирать при расхождении или при отсутствии тега на HEAD.
**Статус:** принято.

## D-009. Хранение релизных архивов
ZIP Windows-сборок (~70 МБ) хранятся в `release_archives/vX.Y.Z/` в корне репозитория — вне папки игры
(`src/GodotClient`), рядом SHA-256 и `BUILD_INFO.txt` (дата, коммит, версии). Архивы добавляются
отдельным коммитом после тега, потому что архив ссылается на коммит тега. Скрипты никогда не
перезаписывают существующий архив. Способ хранения бинарных файлов в Git — см. D-010. **Статус:** принято.

## D-010. Бинарные архивы — обычные файлы Git, без LFS
Проверено при выпуске v0.1.0: загрузка в Git LFS из среды сборки запрещена сетевой политикой
(`lfs.github.com` → 403). Поэтому ZIP хранится как обычный blob (≈ 75 МБ, лимит GitHub — 100 МБ на файл).
Цена — рост размера репозитория на ~75 МБ за версию; для работы только с исходниками рекомендуется
частичный клон `--filter=blob:limit=1m`. Если архив когда-либо превысит 100 МБ, нужно будет перейти на
GitHub Releases или LFS (зафиксировать как миграцию). **Статус:** принято.

## D-012. Восстановление тегов из BUILD_INFO
Облачная среда может пушить только рабочую ветку (push тегов → HTTP 403). Теги создаются локально при релизе,
а их точные коммиты записываются в `BUILD_INFO.txt` архива. `tools/create_release_tags.ps1` воссоздаёт
аннотированные теги на этих коммитах и никогда не перемещает существующие; `verify_release.ps1`
при отсутствии тега проверяет наличие коммита и выдаёт предупреждение. **Статус:** принято.

## D-011. Автоматизация через аргументы командной строки
`AutomationRunner` (аргументы `--hx-*` после `--`) позволяет делать скриншоты и смоук-тесты как из
исходников, так и из экспортированной сборки, вводя события мыши через `Input.ParseInputEvent` — то есть
проверяется настоящий путь ввода. Без аргументов узел неактивен. **Статус:** принято.

## D-013. Порядок выбора клетки при появлении в зоне/на базе
Запрос «на базу» или «в зону» адресует зону целиком: используется первая свободная проходимая клетка зоны в
построчном порядке карты. Это не «перенос» юнита — запрошенная зона соблюдена. Если все клетки заняты —
отказ (`BaseFull`/`ZoneFull`), ничего не меняется. Точную клетку зоны можно указать явно (тогда она проверяется
строго). **Статус:** принято (допущение).

## D-014. Направление взгляда при появлении
По умолчанию — к центру карты (квантуется до одного из 6 направлений); запрос может задать направление явно.
**Статус:** принято (допущение).

## D-015. Отдельная сборка `HexTactics.Interaction`
Конечный автомат ввода (ТЗ §5.3) реализован в чистом C#, а связка с Godot — тонкий слой `PointerInput`.
Причина: сценарии мыши (щелчок/порог/режимы, позже — протягивание стрелок) покрываются автотестами без движка.
**Статус:** принято.

## D-016. Режим прямого выставления — состояние автомата
`Placement` — отдельное отладочное состояние: щелчок по клетке выставляет юнита; при успехе юнит выбирается и
режим закрывается, при отказе режим остаётся открытым. В режиме все клетки подсвечены зелёным/красным по тем же
правилам, что использует симуляция. Будущая стоимость выставления не реализуется (вне этапа). **Статус:** принято.

## D-017. Визуал юнита и отладочный поворот
Юнит — цилиндр (r 0,32, h 0,5) цвета стороны; направление взгляда показывают «дротик» на крышке и стрелка на земле
к соседнему гексу; выделение — тонкое светло-жёлтое кольцо. Клавиши Q/E поворачивают выбранного юнита на 60° —
это отладочное средство v0.2.0; штатный поворот жестом мыши появится в v0.3.0. **Статус:** принято (допущение).

## D-018. Поворот без движения (ТЗ §5.2)
Доступен только при протягивании **из юнита**, у которого **нет ТД** («если ТД ещё нет»), и только если отпускание
произошло в исходной клетке на расстоянии ≥ 0,25 размера гекса от её центра (направленный жест). Направление —
ближайшее из 6 к вектору «центр → точка отпускания» в плоскости карты. Если у юнита уже есть ТД или отпускание в
мёртвой зоне — ничего не меняется (исключает случайный поворот). **Статус:** принято (допущение).

## D-019. Продолжение цепочки только из последней ТД
Протягивание из промежуточной ТД (не последней) не начинает стрелку: выводится подсказка. Вставка/перестроение
середины очереди и удаление ТД — отдельный этап (ТЗ §5.3). Щелчок по любой ТД выделяет её. **Статус:** принято.

## D-020. Нумерация ТД стабильна внутри цепочки
`Waypoint.Sequence` присваивается при создании (последний + 1) и не меняется, пока точки выполняются; новая цепочка
из юнита (Replace) начинается с 1. Так «ТД2» остаётся «ТД2», пока юнит идёт к ней. **Статус:** принято.

## D-021. Предпросмотр направления в v0.3.0 (закрыто в v0.4.0)
До появления поиска пути (v0.4.0) предварительное направление взгляда берётся по первому шагу прямой гекс-линии
к курсорному гексу (`HexLine`). В v0.4.0 заменено первым шагом кратчайшего пути (ТЗ §5.2). **Статус:** закрыто.

## D-022. Валидация ТД в v0.3.0
ТД нельзя поставить вне поля, на препятствии, на клетке другого юнита и на исходной клетке сегмента. Проверка
наличия пути добавляется в v0.4.0 (тем же `WaypointRules`, чтобы подсветка и команда симуляции совпадали). Цепочка
может вернуться на собственную клетку юнита. **Статус:** принято.

## D-023. Отрисовка стрелок
Стрелки — плоские полупрозрачные полигоны чуть выше поверхности поля, с тестом глубины: проходя под поднятыми
препятствиями, прямая стрелка частично скрывается ими (она показывает намерение, а не путь). Юниты рисуются поверх
стрелок, номера ТД — всегда поверх (без теста глубины). **Статус:** принято (допущение).

## D-024. A* и детерминизм
A* с эвристикой cube distance (допустима: стоимость шага ≥ 1), веса клеток `MoveCost` (сейчас все 1). Соседи — в
фиксированном порядке `E, NE, NW, W, SW, SE`; равенства в открытом списке разрешаются по (f, h, отклонение от прямой
старт→цель, порядок вставки); предшественник заменяется только строго лучшим. Итог: путь кратчайший, повторяемый и
среди равных — ближайший к прямой (без визуальных «скачков»). Корректность длины проверяется сверкой с независимым BFS.
**Статус:** принято.

## D-025. Логическая занятость и резервирование
Шаг A→B начинается, только если B свободна и не зарезервирована другим юнитом; B резервируется. При прогрессе 0,5
логическая клетка юнита атомарно меняется с A на B (единственный момент перехода), A остаётся зарезервированной до
конца шага. Поэтому юнит всегда в одной логической клетке, а два корпуса не делят клетку. Шаг, однажды начатый,
всегда завершается (нет взаимных блокировок резервами). Появление на зарезервированной клетке запрещено.
Препятствиями для поиска пути служат логические клетки других юнитов, резервы — нет (их ждут). **Статус:** принято.

## D-026. Перестроение маршрута и остановка
Путь до текущей ТД пересчитывается в центре гекса, если изменились рельеф/занятость (`TopologyVersion`), сменилась ТД
или следующая клетка занята. Нет пути → юнит стоит в центре гекса, статус `Blocked` с причиной (`NoPath` /
`TargetOccupied`), приказы сохраняются; новая попытка — при следующем изменении топологии. Юнит не телепортируется и
не пропускает ТД. Если следующая клетка лишь зарезервирована — статус `Waiting`. **Статус:** принято.

## D-027. Команды во время движения
`CommandAnchor` = клетка, в которую идёт текущий шаг (или текущая клетка, если юнит стоит). Протягивание из юнита
заменяет очередь, но текущий шаг доводится до конца; новый путь строится из этого центра гекса. Протягивание из
последней ТД дополняет очередь. Поворот без движения у идущего юнита не применяется. **Статус:** принято.

## D-028. Фиксированный шаг симуляции
30 тиков/с (`SimulationClock`); не более 8 тиков за кадр — после длительной заминки отставание сбрасывается, а не
«догоняется» ускорением. Отрисовка интерполирует позицию внутри тика (только визуально). Независимость от FPS
проверяется тестом (30/60/144 кадров/с дают одинаковое состояние). **Статус:** принято.

## D-029. Отладочное редактирование препятствий
Режим «Препятствие (O)» в автомате ввода и команда `GameSimulation.SetObstacle` нужны для проверки перестроения
маршрутов (ТЗ §6.1). Нельзя менять базу, зоны появления и клетки с юнитами/резервами. Не является редактором карт
(вне этапа 1). **Статус:** принято (отладка).

## D-030. Семантика тактической паузы
Пауза — состояние симуляции (`GameSimulation.IsPaused`), а не ввода: `Advance` при паузе не накапливает время,
поэтому после снятия нет «догоняющих» тиков и скачков позиций. Команды (появление, приказы, поворот) на паузе
принимаются: они меняют только очередь/состояние, исполнение начинается после снятия; текущий шаг движения доводится
до конца (D-027). Визуальные анимации интерфейса (плавный поворот предпросмотра, подсветка) не зависят от паузы.
Низкоуровневый `Step()` паузу игнорирует (для тестов/отладки). **Статус:** принято.

## D-031. Системы симуляции как точка расширения
Правила, выполняемые каждый тик, реализуют `ISimulationSystem` и регистрируются в `GameSimulation.AddSystem`;
порядок выполнения = порядок регистрации; общение — через события `SimulationEvent`. Движение — первая система.
Будущие способности/атаки/волны добавляются отдельными системами (ТЗ §7). **Статус:** принято.

## D-032. Регрессионная проверка сборки
Помимо юнит-тестов, каждый релиз начиная с v0.5.0 проверяется сквозным сценарием в самой экспортированной
Windows-сборке (`verify_release.ps1 -Run`): шаги мыши идут через входной конвейер Godot, проверки `expect:`
завершают процесс с кодом 1 при ошибке. Для более старых архивов выполняется смоук-запуск. **Статус:** принято.

ТЗ ч.2 §13 предлагает раскладку v0.1.0–v0.7.0, но v0.1.0–v0.5.0 уже выпущены и неизменяемы (ТЗ ч.1 §1, ч.2 §13).
Поэтому требования ч.2 реализуются новыми версиями поверх v0.5.0:

| Версия | Содержание (строки таблицы ТЗ ч.2 §13) |

| v0.7.0 | непрерывные цепочки ТД, обязательный финальный взгляд, отмена, замена приказов движущегося юнита на паузе (v0.3, v0.5) |

**Статус:** принято.

## D-034. Геометрия flat-top / odd-q (ТЗ ч.2 §2)
Гексы — плоской стороной вверх, хранение odd-q (нечётные колонки ниже на ½ высоты), правила — axial/cube.
`HexDirection` переопределён: `North, NorthEast, SouthEast, South, SouthWest, NorthWest` — направления на середины рёбер,
верхнее ребро = North. Вся логика (соседи, расстояние, A*, попадание мышью, сектора взгляда) зависит только от
`HexLayout`/`HexDirection`, поэтому старой ориентации в коде нет; карта обязана объявлять `@layout flat-top odd-q`.
Ширина поля 18,5, высота ≈ 18,2 единиц (почти квадратное, «компактное прямоугольное»). **Статус:** принято.

## D-035. Верхний слой стрелок (ТЗ ч.2 §3.1)
Стрелки, линии маршрутов, маркеры ТД и номера рисуются материалами `NoDepthTest` в прозрачном проходе с
`render_priority` 20…28 — после всех непрозрачных объектов, поэтому их не перекрывают ни юниты, ни препятствия, ни
будущие здания, при любом наклоне/зуме. Это не небольшой Z-сдвиг, а отключённый тест глубины. HUD (CanvasLayer)
остаётся над ними. Стрелки не участвуют в выборе мышью (выбор считается по модели), кликабельны только маркеры ТД.
**Статус:** принято.

## D-036. Указатель взгляда у ребра (ТЗ ч.2 §3.2)
Вместо «дротика» на крышке — маленькая белая стрелка с тёмной обводкой на земле у середины ребра в направлении взгляда,
видна всегда. Рисуется с тестом глубины (это часть юнита, а не стрелка приказа); корпус юнита уменьшен до r 0,28, чтобы не
закрывать указатель северного ребра при наклоне 60°. **Статус:** принято (допущение).

## D-037. Цвета и зона выставления
Личные стрелки и маркеры ТД — белые (маркер с тёмной каймой для читаемости на светлом поле), линия рассчитанного
маршрута — тёмная тонкая, предпросмотр пути — зелёный. База — зелёная, новый тип клетки `DeployZone` (`D` в карте) —
светло-зелёный: дополнительные клетки выставления из ростера (ТЗ ч.2 §5.6, используется с v0.8.0). **Статус:** принято.

## D-038. Транзакционный черновик приказа (ТЗ ч.2 §4.3, §14.3)
Пока игрок ставит ТД и выбирает взгляд, всё — предпросмотр (`OrderDraft` в ядре); при подтверждении финального
взгляда `GameSimulation.ApplyOrder(IndividualOrder)` проверяет всю цепочку (каждый сегмент — достижимая свободная клетка)
и заменяет очередь целиком. Если цепочка стала невозможной — приказ отклоняется полностью, прежний маршрут сохраняется,
черновик остаётся открытым (§9.5). На паузе принятый приказ ждёт снятия паузы. **Статус:** принято (допущение ТЗ).

## D-039. Непрерывная прокладка (§4.1, §14.1)
ТД1 — отпусканием первого протягивания из юнита; дальше режим не заканчивается: живая стрелка идёт от последней ТД к
курсору без нажатой кнопки, каждая следующая ТД — коротким кликом ЛКМ. Отпускание первого протягивания трактуется как
клик в точке отпускания (в т. ч. в секторе своей клетки = поворот на месте). **Статус:** принято.

## D-040. Сектора взгляда (§4.2, §14.2)
Исходная клетка (юнит или последняя ТД) делится на 6 секторов по рёбрам; сектор — ближайшее из 6 направлений к вектору
«центр → курсор» в плоскости карты. Нейтральная зона — круг радиусом 0,3 размера гекса: клик там ничего не подтверждает.
Клик в секторе = обязательный финальный взгляд и применение приказа; без ТД — поворот на месте. У выбранного юнита (без
черновика) те же сектора его текущей клетки поворачивают его на месте. **Статус:** принято.

## D-041. Отмена (§8, §14.4, §14.6)
ПКМ и Esc отменяют весь черновик (стрелки, ТД, подсветка), не трогая подтверждённые приказы. Попытка поставить ТД на
красную клетку (клик или отпускание первого протягивания) — та же отмена; простое наведение на красную клетку — нет.
ПКМ по ТД черновика удаляет её и все следующие (черновик продолжается). ПКМ по подтверждённой ТД выбранного юнита (без
черновика) удаляет её и следующие из очереди; финальный взгляд сохраняется и применяется в новом конце. Чужие цепочки не
затрагиваются. **Статус:** принято.

## D-042. Редактирование подтверждённого маршрута
Протягивание из **последней** подтверждённой ТД открывает черновик, заполненный оставшимися ТД юнита (продолжение
маршрута); подтверждение взгляда заменяет очередь целиком (нумерация с 1). Протягивание из промежуточной ТД отклоняется
(подсказка). Пока черновик открыт, старый маршрут показывается бледным. **Статус:** принято.

## D-043. Финальный взгляд
Хранится в `OrderQueue.FinalFacing` и применяется, когда очередь выполнена (на последней ТД, независимо от направления
последнего шага; для поворота на месте — как только юнит стоит в центре гекса, т. е. у идущего юнита — после текущего
шага). Во время движения указатель показывает направление шага. Сохранённый финальный взгляд рисуется белой стрелкой у
ребра последней ТД. **Статус:** принято.

## D-044. Зарезервированный приказ атаки (§7)
`OrderKind { MoveToTile, AttackTarget }`; в черновике клетка с вражеским юнитом получает статус `AttackTarget`
(оранжевая стрелка), клик даёт обратную связь `AttackTargetReserved(unit, targetId)` — ссылка на ID врага, а не на
клетку. В этой версии ничего не исполняется: ТД не создаётся, юнит не идёт в клетку врага, урона нет; черновик не
отменяется. Порядок обработки клика: враг → (будущая атака); свободная допустимая клетка → ТД; иное → отмена.
**Статус:** принято (резерв архитектуры).

## D-045. Движущийся юнит (§9)
Выбирается кликом по корпусу или по своей логической клетке; новая цепочка строится от `CommandAnchor` (клетка, в
которую идёт шаг — ближайший безопасный центр); текущий шаг всегда доводится до конца, поэтому нет рывка/телепорта и
логическая занятость не нарушается (единый момент смены клетки — середина шага, D-025). **Статус:** принято.

## D-046. Ростер и разрешённые клетки (ТЗ ч.2 §5)
Ростер прототипа — пять оперативников с фиксированными именами (`RosterState.Prototype()`); ресурсы и ограничения
количества — будущий этап (§5.7). Разрешённые для выставления клетки берутся **только из данных карты**: база игрока
(`B`) и клетки зоны выставления (`D`). Краевые зоны появления (`1`, `2`…) игроку для ростера не разрешены (§5.6);
отладочное появление на базе/краях/клетке из ч.1 сохранено и создаёт активных юнитов. **Статус:** принято.

## D-047. Жизненный цикл выставленного юнита (§5.4, §5.7, §12.7)
`PlaceFromRoster` создаёт юнита со статусом `PlacedPendingFacing` и `Facing = null`: он занимает клетку (её нельзя занять
другому), но не двигается и не действует. Активным (`Active`, карточка тоже `Active`) он становится, когда принят первый
приказ (`ApplyOrder`) — начальный взгляд = направление первого шага, финальный — выбранный сектор, — или поворот на месте
(`SetFacing`). Отклонённый приказ оставляет его в ожидании. Отменённый черновик — тоже; выбор такого юнита (клик по нему
или по его карточке) снова открывает черновик. **Статус:** принято (допущение ТЗ).

## D-048. Перетаскивание карточки (§5.2–5.5)
Нажатие ЛКМ на карточке (UI) вызывает `InputStateMachine.BeginRosterDrag`; движения и отпускание мыши передаются автомату,
даже если нажатие было над панелью. Под курсором — полупрозрачный «призрак» (зелёный/красный), разрешённые клетки зелёные,
остальные мягко-красные. Отпускание на разрешённой свободной клетке → юнит и сразу черновик (стрелка от него без нажатой
кнопки). Отпускание на запрещённой клетке, вне поля или над панелью, ПКМ, Esc → карточка возвращается (`RosterCardReturned`),
модель не меняется. Клик по карточке уже выставленного оперативника выбирает его. **Статус:** принято.

## D-049. Нижняя панель и камера
Панель ростера — отдельный `CanvasLayer` по центру свободной области справа от HUD, высота 96 px × масштаб UI; камера
вписывает поле над ней (`FitCamera`). Над панелями указатель не попадает на карту (в режиме перетаскивания карточки
выборка «над UI» не содержит клетки). **Статус:** принято.

## D-050. Режим «Команда» — явный инструмент (ТЗ ч.2 §6.1, §11)
Карточка «Команда» в нижней панели справа от ростера включает режим сбора (`GroupCollect`); повторное нажатие, ПКМ или Esc
выключают его без применения. Первый клик по своему юниту — капитан (`Members[0]`), следующие — участники; клик по уже
выбранному не меняет состав и капитана; не больше 7 участников (капитан + 6 мест первого кольца; крупнее — §14.8, не
нормировано). Клик по земле без капитана — подсказка (режим не закрывается); по врагу — зарезервированная атака. После КТД1
состав фиксирован: свой юнит не из команды на клетке — занятая клетка (клик — отмена), участник — без действия.
**Статус:** принято.

## D-051. Построение вокруг КТД (§6.2, §10)
`GroupStageEvaluator` — одно правило и для подсветки, и для применения: капитан должен дойти до КТД (клетку КТД может
занимать только он); каждому спутнику — своя свободная проходимая достижимая клетка первого кольца вокруг КТД. Юниты вне
команды — препятствия, участники друг другу — нет (они уходят вместе). Назначение — полный перебор (≤ 6! = 720 вариантов)
с минимумом суммарной длины путей; при равенстве выигрывает первый вариант в порядке сторон N, NE, SE, S, SW, NW по порядку
участников — результат зависит только от состояния и входа (стабилен при движении курсора). Этап k начинается с мест
этапа k−1. Клетка зелёная, только если помещается вся команда. Распределение мест (в D-033 — v0.10.0) сделано в v0.9.0,
потому что от него зависит допустимость КТД; v0.10.0 добавляет синхронность этапов, взгляды спутников и уступание прохода.
**Статус:** принято.

## D-052. Применение и жизнь командного приказа (§6.4)
`GameSimulation.ApplyGroupOrder(GroupOrder)` — транзакция: вся цепочка планируется от `CommandAnchor` участников; при любой
невозможной КТД ничего не меняется (`GroupOrderRejected`, черновик остаётся открытым). Иначе регистрируется
`GroupOrderState` (участники, капитан, КТД, места по этапам, финальные взгляды), очередь каждого участника заменяется его
местами, `OrderQueue.GroupId` указывает на приказ, ожидающие (из ростера) участники активируются. Личный приказ участнику
выводит его из командного; приказ удаляется, когда его не выполняет ни один участник (`GroupOrderFinished`). Постоянных
отрядов, смены капитана и меню строя нет. **Статус:** принято.

## D-053. Взгляд спутников в v0.9.0 (§6.3, §14.5)
Капитан — выбранный игроком сектор последней КТД; спутники в v0.9.0 смотрят так же (ТЗ §14.5 допускает «ровно
FacingCaptain»). Случайный выбор из {капитан, ±60°} один раз при подтверждении с фиксируемым seed — v0.10.0.
**Статус:** принято (временно).

## D-054. Участник ждёт участника
Если место участника занято другим участником того же командного приказа (например, капитан проходит через него), юнит
получает статус `Waiting` без события `UnitBlocked` и без красного «!»; путь пересчитывается при изменении занятости
(`TopologyVersion`). Для чужих юнитов поведение прежнее (`Blocked` с причиной). **Статус:** принято.

## D-055. Голубая графика команды (§3.1, §6)
Всё командное — голубое, в верхнем слое без теста глубины: при сборе — стрелка от корпуса каждого участника к курсору; над
допустимой клеткой — стрелки к местам (у капитана шире); подтверждённые этапы — стрелки участник → место; КТД — номерные
маркеры (в черновике с янтарной каймой), места спутников — маленькие голубые шестиугольники; взгляд капитана — белая
мини-стрелка у ребра последней КТД (у спутников — меньшие). Участники при сборе — голубые кольца, капитан — голубой ромб
над юнитом, рисуется поверх стрелок. Подтверждённые командные цепочки остаются голубыми. **Статус:** принято.

## D-056. Синхронные этапы КТД (§6.2)
Прогресс участника — число пройденных этапов (`число КТД − оставшиеся ТД приказа`, обходные шаги не считаются). Участник,
у которого прогресс больше минимального по команде, не начинает шаг к следующему месту (`Waiting`, `WaitReason.TeamStage`).
Так никто не идёт к КТД k+1, пока все не встали на места у КТД k; внутри этапа участники идут независимо. Командный приказ
завершается для всех сразу, когда закончили все (до этого закончившие остаются «своими» — их можно попросить отойти).
Участник, получивший личный приказ или обрезавший цепочку ПКМ, выходит из командного приказа и команду не задерживает.
**Статус:** принято.

## D-057. Взгляды спутников с seed (§6.3, §10, §14.5; заменяет D-053)
Смещение спутника относительно взгляда капитана ∈ {−60°, 0, +60°} = SplitMix64(seed, номер приказа, id юнита) mod 3.
`SimulationSettings.Seed` (по умолчанию 20261106). Вычисляется при подтверждении и хранится в `GroupOrderState.FinalFacings`;
`GameSimulation.PreviewCompanionFacings` даёт те же значения для предпросмотра (используется следующий номер приказа),
поэтому наведение не «перебрасывает» взгляды. Одинаковое состояние + команды + seed → одинаковые взгляды. **Статус:** принято.

## D-058. Построение без взаимной блокировки (§6.2)
Порядок прихода внутри этапа не управляется, поэтому место, на котором ждёт пришедший, не должно стоять на чужом пути.
Конфликт: место спутника на кратчайшем пути капитана; путь спутника через КТД; путь спутника через место другого спутника
(пути — по дереву кратчайших путей, участники не препятствия). Цель поиска — минимум (конфликты, суммарная длина), ничьи —
порядок сторон. Циклы «каждый ждёт клетку соседа» между спутниками невозможны (стоять на месте всегда дешевле обхода цикла);
обмен «капитан ↔ спутник на следующей КТД» исключён запретом клетки капитана для такого спутника. В узком коридоре конфликт
бывает неизбежен — тогда работает уступание прохода (D-059). **Статус:** принято.

## D-059. Ожидание и уступание прохода внутри команды (§6.2; расширяет D-054)
Если пути нет только из-за участников той же команды (путь без них есть), юнит ждёт (`WaitReason.Teammate`) без
`UnitBlocked`; путь пересчитывается при изменении занятости. Через 0,8 с ожидания первый стоящий участник на этом пути
получает обходной шаг (`Waypoint.IsDetour`) на свободную соседнюю клетку вне пути (ближе к своей цели), ждёт там, пока
попросивший не пройдёт освобождённую клетку (`WaitReason.Yielding`), и продолжает свой маршрут; закончивший участник
возвращается на своё место, и его финальный взгляд применяется снова. Обходные шаги не рисуются, не нумеруются и не
задерживаются синхронизацией. Если отойти некому/некуда 6 с — `UnitBlocked(BlockedByTeammates)`, без вечного ожидания и
без входа в занятую клетку. **Статус:** принято.

## D-060. Выбор сектора у поднятого препятствия
`PointerSample.Ground` — точка земли без учёта поднятых клеток. Если она лежит в исходной клетке черновика (юнит/последняя
ТД/КТД, клетка выбранного юнита для поворота), сектор берётся по ней, даже когда луч сначала попал в верх соседнего
препятствия, закрывающего край клетки на экране. Иначе действует прежнее правило (препятствия загораживают то, что за ними).
**Статус:** принято.

## D-061. Ромб капитана
Белый (освещённый) ромб над капитаном, рисуется без теста глубины поверх стрелок: голубой терялся на собственной голубой
стрелке капитана (уточнение D-055). **Статус:** принято.

## D-062. Версии для ТЗ части 3
ТЗ ч.3 §10 предлагает номера v0.8.0–v0.11.0, но они уже выпущены (ч.2) и неизменяемы. Строки плана ч.3 реализуются
следующими версиями: v0.11.0 — 1 гекс/с, непрерывная позиция, безопасное сглаживание; v0.12.0 — HP 100, смерть, обычная
атака 3/с, мишени, `AttackTargetOrder`; v0.13.0 — «Линейный удар»; v0.14.0 — навык в ТД (клик по ТД, иконка, красная
стрелка, шестиугольник «1»). **Статус:** принято.

## D-063. Файл актуального ТЗ
ТЗ ч.3 просит обновлять «актуальное, а не историческое ТЗ» и не трогать файлы редакций 0.1–0.2. Поэтому редакция 0.3
хранится в `docs/GAME_SPEC_PART3.md` (дословно), `GAME_SPEC.md` и `GAME_SPEC_PART2.md` не меняются; пункт §10 «обновление
`docs/GAME_SPEC.md`» трактуется как ведение актуального файла ТЗ. **Статус:** принято.

## D-064. Модель движения: шаги + кривые (§2.1–2.3)
Авторитетная модель — прежние шаги по `GraphPath`: резерв следующего гекса при начале шага, хвостовой резерв до конца
шага, одна клетка на юнита. Для каждого шага строится кривая (`StepGeometry`): первая часть внутри покидаемого гекса,
вторая — внутри входного, стык — середина общего ребра. Поворот скругляется квадратичной кривой «середина входного ребра
→ центр → середина выходного ребра» (лежит в одном гексе, касательная непрерывна); поэтому тело проходит ровно гексы пути
и в их порядке, а у заблокированного внутреннего угла остаётся ≥ 0,54 от его границы. Логический гекс переключается,
когда положение тела оказывается в следующем гексе (одно правило, нарисованное = логическое). ТД и конец маршрута —
якоря (кривая приходит в центр). Новый приказ во время шага: остаток шага перестраивается от текущей точки и касательной
(`Retarget`); шаг всегда доигрывается, `CommandAnchor` прежний (D-045). **Статус:** принято (проектное решение §2.2).

## D-065. Проверка коридора и откат (§2.2 п.4–5)
Каждая кривая проверяется выборкой через 0,03 по длине: круг тела (r 0,28) не должен задевать гекс вне {покидаемый,
входной, следующий по пути}. Не прошла — шаг идёт по прямым через центры. Для стандартных поворотов (0°, ±60°, ±120°)
проверка доказуемо проходит (тест на все 30 сочетаний); откат нужен для перестроек из нестандартного положения.
**Статус:** принято.

## D-066. Скорость и время (§2.4)
`SimulationSettings.DefaultUnitSpeed = 1,0` гекс/с. Шаг длится `1 / скорость` игрового времени независимо от длины
кривой (тело внутри шага движется равномерно по длине кривой), поэтому сглаживание не ускоряет и не замедляет маршрут:
три перехода — 3 игровые секунды при любой частоте кадров. **Статус:** принято.

## D-067. Диагностика движения (§8)
F3 (и шаг автоматизации `debug:on|off`) показывает поверх сцены: гексы `GraphPath` (жёлтые), логический гекс (белый),
кривую текущего шага (розовая) и след последних позиций (оранжевый). Только отображение; правила не меняются.
**Статус:** принято.

## D-068. Характеристики и данные баланса (§3, §8)
`UnitStats` (MaxHealth 100, MoveSpeedHexPerSecond 1,0, AttackRatePerSecond 3,0, NormalAttackDamage 10,
NormalAttackRangeHex 1) задаются в `SimulationSettings.DefaultStats`; клиент читает их из `res://data/balance.json`
(экспортируется вместе с картой). Урон 10 и дальность 1 — `PROTOTYPE_DEFAULT`, не канон (§11). **Статус:** принято.

## D-069. Смерть (§3, §7 п.5)
`GameState.ApplyDamage` уменьшает здоровье не ниже 0; при 0 юнит сразу `Dead` (не бьёт, не ходит, не получает приказов).
После всех систем тика `RemoveDead` по порядку id снимает погибших: клетка и все резервы освобождаются, очередь
сбрасывается, юнит переносится в `Fallen`, карточка ростера → `Unavailable`, событие `UnitDied`. Тело не остаётся
препятствием (допущение §3). Судьба команды при гибели капитана — открытый вопрос §11: участники просто продолжают свои
маршруты. **Статус:** принято.

## D-070. Приказ атаки (§4.1, §4.3)
`IndividualOrder.AttackTarget` — конечная стадия цепочки после ТД; `OrderQueue.AttackTarget`, `FinalFacing = null`.
Ввод: живой враг под концом стрелки (тело или его клетка) проверяется до правила «красная клетка = отмена»; клик/отпускание
→ `ApplyOrder` сразу, без выбора взгляда. Взгляд — `HexDirections.Toward(клетка юнита, клетка цели)`: ближайшее из шести
по скалярному произведению, равенство — первое в порядке N, NE, SE, S, SW, NW; ставится при подтверждении (и на паузе).
Цель — только живой юнит другой стороны (`WaypointError.InvalidTarget`). Групповая атака не вводится (§4.1 п.5).
**Статус:** принято.

## D-071. Исполнение атаки (§4.2, §7 п.4)
`AttackSystem` после `MovementSystem`, юниты по id. Пока есть ТД — идёт по ним. Цель вне радиуса — обходной шаг к
ближайшей свободной достижимой клетке в радиусе (длина пути, равенство — порядок клеток), не чаще раза в 0,5 с; клетку
цели не занимает; нет такой клетки — `TargetUnreachable` + событие, ожидание на месте. В радиусе и стоя — поворот к цели
и удар каждые 1/AttackRate игрового времени, первый — через интервал (3 с → 9 ударов). Цель ушла из радиуса — снова
подход, таймер заново. Цель погибла/исчезла — `AttackTargetLost`, приказ снят. Новой цели сам не ищет (без ИИ/агро).
**Статус:** принято (проектные предложения §4.2).

## D-072. Мишени и стенд (§9)
Враги — юниты стороны `Enemy` без приказов и без ИИ: «Мишень врага (T)» (режим выставления со стороной Enemy) и кнопка
«Стенд» (четыре мишени у стены и на открытом месте). **Статус:** принято.

## D-073. Описание навыка и область (§5.1, §8)
`SkillDefinition`: `RelativeSteps` (пути по направлениям относительно выбранного; «Линейный удар» = [вперёд], [вперёд,
вперёд]), `Damage`, `FriendlyFire = false`, `BlockedByObstacles = false`, `Cost/CooldownSeconds/CastSeconds = null`
(временные правила §5.1, расширяются данными). `Area(origin, direction, grid)` — чистая гекс-арифметика; клетки вне
поля отбрасываются. Урон «Линейного удара» (20) — в `data/balance.json`. **Статус:** принято.

## D-074. Немедленное применение (§5.2 — проектное предложение)
Вызов — кнопка «✦ Линейный удар (R)» в блоке выбранного юнита или клавиша R. Направление — ближайшее из шести к вектору
«центр клетки юнита (якорь команд) → точка курсора на земле», нейтральный центр 0,3 гекса не выбирает. Подтверждение ЛКМ
создаёт `SkillAction` (`UseSkill`), ПКМ/Esc отменяют только прицеливание. Действие срабатывает в первом тике, когда юнит
стоит в центре клетки (текущий шаг доводится до конца), — от этой клетки; юнит поворачивается в направление удара и так
остаётся до следующего шага (§6.3). Повторное прицеливание заменяет несработавшее действие (старое — `Cancelled`).
Красная стрелка прицеливания используется и здесь — тот же визуальный язык, что для ТД в v0.14.0. **Статус:** принято.

## D-075. Порядок тика (§7)
`MovementSystem` → `SkillSystem` → `AttackSystem` → снятие погибших → завершение команд. На паузе нет тиков: ни
срабатываний, ни урона, ни таймеров. Все системы обходят юнитов по возрастанию id. **Статус:** принято.

## D-076. Навык в ТД: модель (§6.1, §6.5, §8)
Навык хранится на самой ТД: `Waypoint.Skill` — `SkillAction` с `OriginWaypointId`. Подтверждённый приказ несёт
`IndividualOrder.WaypointSkills` (индекс ТД → `WaypointSkillSpec(SkillId, Direction)`), `ApplyOrder` проверяет их
(`WaypointError.InvalidSkill`: навыка нет у юнита, индекс вне цепочки) и создаёт по `SkillAction` на ТД (`SkillPlanned` с
`WaypointId`). На ТД не больше одного навыка — повторное назначение заменяет прежнее (старое `Cancelled`). Удаление ТД
(усечение, очистка, новый приказ) отменяет только её навык. Обходные ТД (подход к цели, уступание) и КТД командного
приказа навыков не несут (ТЗ ч.3 §6 описывает только собственный маршрут юнита; удержание одного участника сбивало бы
синхронные этапы).
**Статус:** принято.

## D-077. Навык в ТД: исполнение (§6.1 п.6, §6.3, §6.5, §7)
ТД с запланированным навыком — якорь: кривая приходит в её центр. `MovementSystem`, дойдя до неё, не начинает следующий
шаг в том же тике (`Waiting`, `WaitReason.Skill`); `SkillSystem` в этом тике поворачивает юнита в направление навыка,
берёт снимок врагов в двух клетках от ТД, наносит урон (`SkillActivated`) и помечает действие `Executed`; со следующего
тика маршрут продолжается сам. Итого удержание — ровно один тик (время каста 0, §7 п.6). На последней ТД после удара
юнит возвращается к финальному взгляду приказа (проектное правило §6.3). Исполнение привязано к id действия и ТД, а не к
клетке: повторный вход в клетку, пауза, перестройка кривой, частота кадров его не повторяют. Погибший юнит и
недостижимая/удалённая ТД навык не исполняют (на чужом гексе — никогда). Приказ атаки — последняя стадия после ТД и навык
не трогает. **Статус:** принято.

## D-078. Меню ТД и прицеливание от ТД (§6.1–6.2, §6.4)
- Короткий клик ЛКМ (без выхода за порог drag 8 px, D-040) по центральному маркеру ТД — круг радиуса нейтральной зоны
  (0,3 гекса) вокруг центра ТД — открывает `WaypointMenuView`: у черновика — для любой ТД, у выбранного живого своего юнита —
  для подтверждённой не обходной ТД личного (не командного) приказа. Приоритет: меню/иконка > центр маркера > сектор взгляда > гекс; центр маркера и
  сектора у рёбер не пересекаются, поэтому финальный взгляд выбирается как в ч.2.
- Меню — `WaypointMenuPanel` (UI над стрелками): «✦ Линейный удар» и «✕» (если навык назначен). Нажатия по нему в автомат
  не попадают — ТД случайно не создаётся. Клик мимо меню, ПКМ и Esc закрывают только меню; новый черновик, выбор другого
  юнита, ростер, режим «Команда» и отладочные режимы — тоже.
- Иконка → `SkillAim` с началом в ТД (`SkillAimView.FromWaypoint`): направление — ближайшее из шести к вектору «центр ТД →
  курсор», нейтральный центр не выбирает. ЛКМ: в черновике — `OrderDraft.SetSkill` и возврат в черновик (ждёт следующей ТД
  или финального взгляда, красная стрелка взгляд не подменяет); на подтверждённом маршруте — `AssignWaypointSkill`
  (одной транзакцией; отмена прицеливания ничего не меняет). ПКМ/Esc в прицеливании отменяют только его.
- Отображение: красный шестиугольник «✦1» над правым верхним краем маркера ТД (поверх стрелок, не закрывает маркер);
  серые клетки — мягкая заливка; ярко — прицеливание и ТД под курсором/с открытым меню, приглушённо — остальные
  назначенные навыки выбранного юнита; в черновике — только по наведению на ТД, чтобы не смешиваться с подсветкой
  движения. После срабатывания значок и зона исчезают (остаётся короткая вспышка удара). **Статус:** принято.

## D-079. Подсветка движения при меню ТД и прицеливании (§6.4; уточняет D-078, v0.14.1)
Пока открыто меню ТД или идёт прицеливание навыка, зелёно-красная подсветка движения черновика скрыта: клик в этих
состояниях ТД не ставит, а серая область навыка не должна смешиваться с подсветкой движения. При наведении на ТД
черновика без меню подсветка движения остаётся (её режим — приоритет), серая область этой ТД показывается поверх.
В v0.14.0 подсветка не скрывалась (тег и архив неизменяемы — исправление выпущено как v0.14.1). **Статус:** принято.

## D-081. Файл ТЗ части 4
Редакция 0.4 хранится дословно в `docs/GAME_SPEC_PART4.md`; файлы 0.1–0.3 не меняются. Правила боя и движения — по 0.3,
всё о редакторах и способе задания характеристик — по 0.4. **Статус:** принято.

## D-082. Слои Content и Editor (§10)
`HexTactics.Content` (чистый C#, ссылается на Core): определения, реестры видов/полей/эффектов, валидация, хранилище,
`RuntimeFactory`. `HexTactics.Editor` (Core + Content): Undo/Redo и модели каталога/редакторов. Simulation о Content не знает:
фабрика выдаёт типы Core (`MapDefinition`, `UnitStats`, `SkillDefinition`), поэтому «Играть» и тест из редактора используют
одну симуляцию. Клиент Godot только показывает модели (папки `MainMenu`, `GameMode`, `DeveloperMode`). Тесты — новые
проекты `Content.Tests`, `Editor.Tests`. **Статус:** принято.

## D-083. Формат определений и ID (§8.1–8.2)
Оболочка `schemaVersion, id, kind, name, description, revision, modified, tags, references, data` (`docs/CONTENT_FORMAT.md`);
`references` вычисляются из `data` при записи. ID: `[a-z0-9]+([._-][a-z0-9]+)*`, 3–64 символа; имя файла = ID;
`core.` — только встроенный контент; новые — `<kind>_<8 hex>`. JSON UTF-8 с отступами, фиксированный порядок полей,
чтение с ограничением глубины и размера (2 МБ). Схема каждого вида — версия 1. **Статус:** принято (проектное предложение §13).

## D-084. Встроенный контент — данные, один источник правды (§1, §6.6, §9.1)
Игра поставляет определения в `res://data/content` (список — `index.json`): 7 типов гексов (обычный, высокий, препятствие,
база игрока, база врага, зона выставления, край/зона появления), юнит «Оперативник», навык «Линейный удар», карта
«Прототип 12×10». «Играть» строит матч только из библиотеки: `data/balance.json` удалён (значения — в юните и навыке),
`maps/prototype.hexmap` больше не загружается игрой (оставлен эталоном для тестов: тест сравнивает карту из JSON с ним
поклеточно). Цвета типов совпадают с прежними цветами ролей. **Статус:** принято.

## D-085. Пустые места, роли и уровни гексов (§4.1–4.2)
`TileType.Void` — места рабочей области без гекса: непроходимы, не край для себя, не цель ТД, не клетка навыка, не
рисуются; гекс рядом с пустотой считается краем (для зон появления). `TileType.EnemyBase` — метка «база врага»
(проходима, без ИИ). `TileState` получил `TileId` (тип из библиотеки) и `Level` (0…3, только вид: высоты 0/0,18/0,36/0,55;
на высоком гексе юнит рисуется на его верхней грани, подсветки поднимаются, луч выбора учитывает высоту). **Статус:** принято.

## D-086. Эффекты: одна трасса данных (§6.3, §9.1–9.2)
Core: `EffectSpec` (тип + параметры-данные) и `SkillCell(смещение, эффекты)`. Content: `EffectTypeRegistry` — поля,
диапазоны, значения по умолчанию, где разрешён эффект. Simulation: `EffectResolver` — единственный исполнитель (обработчик
на тип, проверка целей `enemies/allies/self/all`); неизвестный тип не исполняется. В v0.15.0 зарегистрирован только
`damage` с фиксированной величиной — «Линейный удар» исполняется им; формулы от Attack Power, удары с интервалами, лечение,
баффы и дебаффы — v0.18.0. Смещения клеток хранятся для взгляда на север и поворачиваются `HexCoord.RotateFor` (куб
(q,r,s) → (−r,−s,−q), тест на отсутствие отражения). Порядок применения: клетка (в порядке хранения) → эффект → цель.
**Статус:** принято.

## D-087. Хранилище пользователя (§8.1)
`ContentRepository` на `user://` (или `--hx-user-root`): `content/`, `drafts/`, `backups/`, `logs/`, `packs/`.
Запись атомарна: временный файл → чтение обратно и полная проверка → переименование поверх. Удаление переносит файл в
`backups/deleted` (Undo возвращает), копии перед заменой — `backups/<время>-<причина>`, журнал — `logs/content.log`.
Файлы, которые не удалось прочитать, не меняются и показываются в сообщениях. **Статус:** принято.

## D-088. Undo/Redo (§3.3)
`CommandHistory`: команды `Do/Undo`, транзакции (одна запись, откат всех частей при ошибке), отметка сохранённого
состояния (`IsDirty`), предел 500 шагов. Команда, которую нельзя выполнить/отменить (`EditorCommandException`), историю
не меняет. В каталоге v0.15.0 через неё идут дублирование, переименование и удаление (они сразу пишутся на диск, отмена
возвращает файлы). **Статус:** принято.

## D-089. Стартовое меню и режимы (§2.1)
Корень `AppRoot` (`scenes/App.tscn`): стартовый экран «Играть» / «Разработчик» / «Выход»; одновременно живёт один режим,
симуляция в редакторе не работает. «← Главное меню» из боя — с подтверждением (бой закрывается, данные библиотеки не
меняются). `ModalDialog` перехватывает мышь и клавиатуру (Esc = отмена); в бою ввод карты под ним выключен.
**Статус:** принято.

## D-090. Каталог разработчика (§2.2, §3.1)
Категории — из реестра (видимые `Available`). Список: название, тип/описание, ID, дата, ревизия/схема, проверка; поиск по
названию/ID/описанию, сортировка по названию/дате/ID. Действия: Создать, Открыть (по реестру редакторов клиента — в
v0.15.0 пуст), Дублировать (и встроенных), Переименовать, Удалить (с проверкой ссылок), Импорт/Экспорт (v0.20.0),
«Проверить всё». Справа — свойства, ссылки, «используется в», проверка; внизу — сообщения. **Статус:** принято.

## D-091. Автоматизация режимов
Шаги приложения: `ui:<id>` (клик по зарегистрированному элементу настоящими событиями мыши), `field:<id>=<значение>`,
`key:ctrl+z`, `row:<id>|name=<название>`; проверки `expect:screen|dialog|category|rows|selected|item|undo|message`.
Аргументы `--hx-start=play|dev`, `--hx-user-root=<папка>`. `verify_release.ps1` для v0.15.0+ запускает сборку дважды с одной
временной папкой пользователя: сценарий + проверка сохранения после перезапуска. **Статус:** принято.

## D-092. Модель редактора карт (§3.3, §4)
`MapEditorModel` (Editor) редактирует рабочую копию определения; каждая правка — команда-снимок «до/после» всей карты
(карты малы, ≤ 1024 гекса), пустые правки в историю не попадают. Выбор, режим удаления и «кисть» — состояние интерфейса,
не история. Клик: пустое место в области → один гекс типа «кисти» + выбор; гекс → выбор; в режиме удаления — отметка.
Гексы хранятся по координате, двух гексов на одном месте быть не может. **Статус:** принято.

## D-093. Красная кнопка удаления (§4.3)
`PressDeleteButton`: 1-е нажатие — режим выбора (ничего не удаляется); 2-е — удаление отмеченных одной командой (если
отмеченных нет — просто выход из режима); Esc/«Отмена» — выход без удаления. Связи гекса (сейчас — тестовые точки;
размещения и цели событий появятся с их механиками) перечисляются перед подтверждением и снимаются в той же команде,
Ctrl+Z возвращает всё. Тип гекса в библиотеке при этом не трогается. **Статус:** принято.

## D-094. Тестовые точки и проверка маршрута (§4.4)
Карта может иметь тестовые точки (поле `testPoints`, необязательное — схема 1 без миграции): метки A, B, C… на реальных
гексах. Проверка ищет проходимый путь (тот же `Pathfinder`) между соседними точками по порядку; нет пути — замечание.
Без точек маршрут не проверяется: разрозненные островки — не ошибка. **Статус:** принято.

## D-095. Сохранение, черновики, выход (§2.1, §8.1)
Сохранение — через библиотеку (проверка → атомарная запись); встроенная карта сохраняется копией с новым ID. Черновик
несохранённой работы пишется в `user://drafts/maps/<id>.json` каждые 2 с при изменениях, удаляется при сохранении или
«Не сохранять»; при входе в режим разработчика найденные черновики предлагаются к восстановлению (сохранённая версия
не меняется, пока черновик не сохранят). Выход из редактора с изменениями — «Сохранить / Не сохранять / Отмена».
**Статус:** принято.

## D-096. Тест карты (§4.4, §3.2)
«Тест карты» строит матч из временной копии (`RuntimeFactory.BuildGame(library, item)`) в обычном `GameMode`: те же
жесты, симуляция, пауза, коллизии. Режим разработчика на время теста вынимается из дерева узлов (не работает и не
рисуется, но сохраняет состояние — холст, выбор, историю); «← Вернуться в редактор» возвращает его. **Статус:** принято.

## D-097. Холст редактора и выбор карты для игры
Вид — как в игре (60°) с переключателем «строго сверху»; колесо — масштаб к точке под курсором, средняя кнопка или
пробел+ЛКМ — сдвиг (`CameraRig.Zoom/Pan`). Пустые места — бледные контуры с координатами `col,row`, реальные гексы — с
цветом и высотой своего типа (`TilePalette`). Стартовый экран получил список карт для «Играть» (встроенные и свои без
ошибок). **Статус:** принято.
