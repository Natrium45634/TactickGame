# Проектные решения (ADR-лог)

Формат: решение · причина · статус. Изменения утверждённых пунктов ТЗ фиксируются здесь и в `CHANGELOG.md`.
«Допущение» = технический выбор из §9 ТЗ, который можно пересмотреть.

## D-001. Godot 4.7.2 stable .NET + C# (net8.0)
Рекомендовано ТЗ. Установленная версия: `4.7.2.stable.mono.official.ed1daf0bf`, .NET SDK 8.0.133.
`GodotSharp` 4.7.2 собран под .NET 8, поэтому все проекты — `net8.0` (переход на `net10.0` возможен позже
без изменения кода). Beta/dev-версии движка не используются. **Статус:** принято.

## D-002. Рендерер Compatibility (OpenGL 3.3)
Минималистичная графика прототипа не требует Forward+; Compatibility запускается на любой Windows-машине
(включая встроенную графику и удалённые рабочие столы) и даёт одинаковую картинку при проверке.
Особенность: рендерер затеняет в sRGB-пространстве, поэтому цвета вершин/инстансов передаются без
линеаризации (`VisualConfig.ToRenderColor`). **Статус:** принято (допущение).

## D-003. Pointy-top, odd-r offset для хранения, axial/cube для правил
Как в ТЗ §3.1. Порядок направлений `E, NE, NW, W, SW, SE` фиксирован и задаёт порядок обхода соседей.
`HexDirection` используется и как направление взгляда (тип `FacingDirection` из ТЗ). **Статус:** принято.

## D-004. Структура решения
Godot-проект лежит в `src/GodotClient` и ссылается на чистые сборки через `ProjectReference`; чистые
сборки и тесты не попадают в папку Godot-проекта (не импортируются движком). Решение `HexTactics.sln` в корне,
`dotnet/project/solution_directory="../.."`. Конфигурации решения: `Debug`, `ExportDebug`, `ExportRelease`
(как ожидает Godot). **Статус:** принято.

## D-005. Данные карты — текстовый файл `.hexmap`
Простая читаемая сетка токенов (см. ARCHITECTURE §5), разбирается в Core и тестируется без движка.
Клетки зон появления обязаны лежать на краю карты. Редактор карт — вне этапа 1. **Статус:** принято.

## D-006. Визуальный стиль прототипа
По запросу пользователя — «базовые геометрические примитивы 3D-редактора»: светло-серые матовые
гексагональные призмы, препятствия — поднятые тёмно-серые колонны, база — голубоватый тон, зоны появления —
песочный тон, мягкая направленная тень, тёмный нейтральный фон. Границы клеток — тонкие бледные линии
шейдером в мировых единицах. **Статус:** принято (допущение, уточняется визуальными тестами).

## D-007. Камера и область UI
Ортографическая камера, возвышение 60° (ТЗ §3.2). Панель HUD слева шириной 272 px (× масштаб UI);
камера вписывает поле в оставшуюся область, поэтому UI не перекрывает поле на 1920×1080, 1600×900, 1366×768.
Масштаб UI = высота окна / 1080, округление 0.25, в пределах 1..2. **Статус:** принято.

## D-008. Единый источник версии
`Directory.Build.props` (`HexTacticsVersion`) для .NET и `project.godot` (`config/version`) для движка;
`tools/build_release.ps1` отказывается собирать при расхождении или при отсутствии тега на HEAD.
**Статус:** принято.

## D-009. Хранение релизных архивов
ZIP Windows-сборок (~70 МБ) хранятся в `release_archives/vX.Y.Z/` в корне репозитория — вне папки игры
(`src/GodotClient`), рядом SHA-256 и `BUILD_INFO.txt` (дата, коммит, версии). Архивы добавляются
отдельным коммитом после тега, потому что архив ссылается на коммит тега. Скрипты никогда не
перезаписывают существующий архив. Способ хранения бинарных файлов в Git — см. D-010. **Статус:** принято.

## D-010. Бинарные архивы — обычные файлы Git, без LFS
Проверено при выпуске v0.1.0: загрузка в Git LFS из среды сборки запрещена сетевой политикой
(`lfs.github.com` → 403). Поэтому ZIP хранится как обычный blob (≈ 75 МБ, лимит GitHub — 100 МБ на файл).
Цена — рост размера репозитория на ~75 МБ за версию; для работы только с исходниками рекомендуется
частичный клон `--filter=blob:limit=1m`. Если архив когда-либо превысит 100 МБ, нужно будет перейти на
GitHub Releases или LFS (зафиксировать как миграцию). **Статус:** принято.

## D-012. Восстановление тегов из BUILD_INFO
Облачная среда может пушить только рабочую ветку (push тегов → HTTP 403). Теги создаются локально при релизе,
а их точные коммиты записываются в `BUILD_INFO.txt` архива. `tools/create_release_tags.ps1` воссоздаёт
аннотированные теги на этих коммитах и никогда не перемещает существующие; `verify_release.ps1`
при отсутствии тега проверяет наличие коммита и выдаёт предупреждение. **Статус:** принято.

## D-011. Автоматизация через аргументы командной строки
`AutomationRunner` (аргументы `--hx-*` после `--`) позволяет делать скриншоты и смоук-тесты как из
исходников, так и из экспортированной сборки, вводя события мыши через `Input.ParseInputEvent` — то есть
проверяется настоящий путь ввода. Без аргументов узел неактивен. **Статус:** принято.

## D-013. Порядок выбора клетки при появлении в зоне/на базе
Запрос «на базу» или «в зону» адресует зону целиком: используется первая свободная проходимая клетка зоны в
построчном порядке карты. Это не «перенос» юнита — запрошенная зона соблюдена. Если все клетки заняты —
отказ (`BaseFull`/`ZoneFull`), ничего не меняется. Точную клетку зоны можно указать явно (тогда она проверяется
строго). **Статус:** принято (допущение).

## D-014. Направление взгляда при появлении
По умолчанию — к центру карты (квантуется до одного из 6 направлений); запрос может задать направление явно.
**Статус:** принято (допущение).

## D-015. Отдельная сборка `HexTactics.Interaction`
Конечный автомат ввода (ТЗ §5.3) реализован в чистом C#, а связка с Godot — тонкий слой `PointerInput`.
Причина: сценарии мыши (щелчок/порог/режимы, позже — протягивание стрелок) покрываются автотестами без движка.
**Статус:** принято.

## D-016. Режим прямого выставления — состояние автомата
`Placement` — отдельное отладочное состояние: щелчок по клетке выставляет юнита; при успехе юнит выбирается и
режим закрывается, при отказе режим остаётся открытым. В режиме все клетки подсвечены зелёным/красным по тем же
правилам, что использует симуляция. Будущая стоимость выставления не реализуется (вне этапа). **Статус:** принято.

## D-017. Визуал юнита и отладочный поворот
Юнит — цилиндр (r 0,32, h 0,5) цвета стороны; направление взгляда показывают «дротик» на крышке и стрелка на земле
к соседнему гексу; выделение — тонкое светло-жёлтое кольцо. Клавиши Q/E поворачивают выбранного юнита на 60° —
это отладочное средство v0.2.0; штатный поворот жестом мыши появится в v0.3.0. **Статус:** принято (допущение).

## D-018. Поворот без движения (ТЗ §5.2)
Доступен только при протягивании **из юнита**, у которого **нет ТД** («если ТД ещё нет»), и только если отпускание
произошло в исходной клетке на расстоянии ≥ 0,25 размера гекса от её центра (направленный жест). Направление —
ближайшее из 6 к вектору «центр → точка отпускания» в плоскости карты. Если у юнита уже есть ТД или отпускание в
мёртвой зоне — ничего не меняется (исключает случайный поворот). **Статус:** принято (допущение).

## D-019. Продолжение цепочки только из последней ТД
Протягивание из промежуточной ТД (не последней) не начинает стрелку: выводится подсказка. Вставка/перестроение
середины очереди и удаление ТД — отдельный этап (ТЗ §5.3). Щелчок по любой ТД выделяет её. **Статус:** принято.

## D-020. Нумерация ТД стабильна внутри цепочки
`Waypoint.Sequence` присваивается при создании (последний + 1) и не меняется, пока точки выполняются; новая цепочка
из юнита (Replace) начинается с 1. Так «ТД2» остаётся «ТД2», пока юнит идёт к ней. **Статус:** принято.

## D-021. Предпросмотр направления в v0.3.0 (закрыто в v0.4.0)
До появления поиска пути (v0.4.0) предварительное направление взгляда берётся по первому шагу прямой гекс-линии
к курсорному гексу (`HexLine`). В v0.4.0 заменено первым шагом кратчайшего пути (ТЗ §5.2). **Статус:** закрыто.

## D-022. Валидация ТД в v0.3.0
ТД нельзя поставить вне поля, на препятствии, на клетке другого юнита и на исходной клетке сегмента. Проверка
наличия пути добавляется в v0.4.0 (тем же `WaypointRules`, чтобы подсветка и команда симуляции совпадали). Цепочка
может вернуться на собственную клетку юнита. **Статус:** принято.

## D-023. Отрисовка стрелок
Стрелки — плоские полупрозрачные полигоны чуть выше поверхности поля, с тестом глубины: проходя под поднятыми
препятствиями, прямая стрелка частично скрывается ими (она показывает намерение, а не путь). Юниты рисуются поверх
стрелок, номера ТД — всегда поверх (без теста глубины). **Статус:** принято (допущение).

## D-024. A* и детерминизм
A* с эвристикой cube distance (допустима: стоимость шага ≥ 1), веса клеток `MoveCost` (сейчас все 1). Соседи — в
фиксированном порядке `E, NE, NW, W, SW, SE`; равенства в открытом списке разрешаются по (f, h, отклонение от прямой
старт→цель, порядок вставки); предшественник заменяется только строго лучшим. Итог: путь кратчайший, повторяемый и
среди равных — ближайший к прямой (без визуальных «скачков»). Корректность длины проверяется сверкой с независимым BFS.
**Статус:** принято.

## D-025. Логическая занятость и резервирование
Шаг A→B начинается, только если B свободна и не зарезервирована другим юнитом; B резервируется. При прогрессе 0,5
логическая клетка юнита атомарно меняется с A на B (единственный момент перехода), A остаётся зарезервированной до
конца шага. Поэтому юнит всегда в одной логической клетке, а два корпуса не делят клетку. Шаг, однажды начатый,
всегда завершается (нет взаимных блокировок резервами). Появление на зарезервированной клетке запрещено.
Препятствиями для поиска пути служат логические клетки других юнитов, резервы — нет (их ждут). **Статус:** принято.

## D-026. Перестроение маршрута и остановка
Путь до текущей ТД пересчитывается в центре гекса, если изменились рельеф/занятость (`TopologyVersion`), сменилась ТД
или следующая клетка занята. Нет пути → юнит стоит в центре гекса, статус `Blocked` с причиной (`NoPath` /
`TargetOccupied`), приказы сохраняются; новая попытка — при следующем изменении топологии. Юнит не телепортируется и
не пропускает ТД. Если следующая клетка лишь зарезервирована — статус `Waiting`. **Статус:** принято.

## D-027. Команды во время движения
`CommandAnchor` = клетка, в которую идёт текущий шаг (или текущая клетка, если юнит стоит). Протягивание из юнита
заменяет очередь, но текущий шаг доводится до конца; новый путь строится из этого центра гекса. Протягивание из
последней ТД дополняет очередь. Поворот без движения у идущего юнита не применяется. **Статус:** принято.

## D-028. Фиксированный шаг симуляции
30 тиков/с (`SimulationClock`); не более 8 тиков за кадр — после длительной заминки отставание сбрасывается, а не
«догоняется» ускорением. Отрисовка интерполирует позицию внутри тика (только визуально). Независимость от FPS
проверяется тестом (30/60/144 кадров/с дают одинаковое состояние). **Статус:** принято.

## D-029. Отладочное редактирование препятствий
Режим «Препятствие (O)» в автомате ввода и команда `GameSimulation.SetObstacle` нужны для проверки перестроения
маршрутов (ТЗ §6.1). Нельзя менять базу, зоны появления и клетки с юнитами/резервами. Не является редактором карт
(вне этапа 1). **Статус:** принято (отладка).

## D-030. Семантика тактической паузы
Пауза — состояние симуляции (`GameSimulation.IsPaused`), а не ввода: `Advance` при паузе не накапливает время,
поэтому после снятия нет «догоняющих» тиков и скачков позиций. Команды (появление, приказы, поворот) на паузе
принимаются: они меняют только очередь/состояние, исполнение начинается после снятия; текущий шаг движения доводится
до конца (D-027). Визуальные анимации интерфейса (плавный поворот предпросмотра, подсветка) не зависят от паузы.
Низкоуровневый `Step()` паузу игнорирует (для тестов/отладки). **Статус:** принято.

## D-031. Системы симуляции как точка расширения
Правила, выполняемые каждый тик, реализуют `ISimulationSystem` и регистрируются в `GameSimulation.AddSystem`;
порядок выполнения = порядок регистрации; общение — через события `SimulationEvent`. Движение — первая система.
Будущие способности/атаки/волны добавляются отдельными системами (ТЗ §7). **Статус:** принято.

## D-032. Регрессионная проверка сборки
Помимо юнит-тестов, каждый релиз начиная с v0.5.0 проверяется сквозным сценарием в самой экспортированной
Windows-сборке (`verify_release.ps1 -Run`): шаги мыши идут через входной конвейер Godot, проверки `expect:`
завершают процесс с кодом 1 при ошибке. Для более старых архивов выполняется смоук-запуск. **Статус:** принято.

ТЗ ч.2 §13 предлагает раскладку v0.1.0–v0.7.0, но v0.1.0–v0.5.0 уже выпущены и неизменяемы (ТЗ ч.1 §1, ч.2 §13).
Поэтому требования ч.2 реализуются новыми версиями поверх v0.5.0:

| Версия | Содержание (строки таблицы ТЗ ч.2 §13) |

| v0.7.0 | непрерывные цепочки ТД, обязательный финальный взгляд, отмена, замена приказов движущегося юнита на паузе (v0.3, v0.5) |

**Статус:** принято.

## D-034. Геометрия flat-top / odd-q (ТЗ ч.2 §2)
Гексы — плоской стороной вверх, хранение odd-q (нечётные колонки ниже на ½ высоты), правила — axial/cube.
`HexDirection` переопределён: `North, NorthEast, SouthEast, South, SouthWest, NorthWest` — направления на середины рёбер,
верхнее ребро = North. Вся логика (соседи, расстояние, A*, попадание мышью, сектора взгляда) зависит только от
`HexLayout`/`HexDirection`, поэтому старой ориентации в коде нет; карта обязана объявлять `@layout flat-top odd-q`.
Ширина поля 18,5, высота ≈ 18,2 единиц (почти квадратное, «компактное прямоугольное»). **Статус:** принято.

## D-035. Верхний слой стрелок (ТЗ ч.2 §3.1)
Стрелки, линии маршрутов, маркеры ТД и номера рисуются материалами `NoDepthTest` в прозрачном проходе с
`render_priority` 20…28 — после всех непрозрачных объектов, поэтому их не перекрывают ни юниты, ни препятствия, ни
будущие здания, при любом наклоне/зуме. Это не небольшой Z-сдвиг, а отключённый тест глубины. HUD (CanvasLayer)
остаётся над ними. Стрелки не участвуют в выборе мышью (выбор считается по модели), кликабельны только маркеры ТД.
**Статус:** принято.

## D-036. Указатель взгляда у ребра (ТЗ ч.2 §3.2)
Вместо «дротика» на крышке — маленькая белая стрелка с тёмной обводкой на земле у середины ребра в направлении взгляда,
видна всегда. Рисуется с тестом глубины (это часть юнита, а не стрелка приказа); корпус юнита уменьшен до r 0,28, чтобы не
закрывать указатель северного ребра при наклоне 60°. **Статус:** принято (допущение).

## D-037. Цвета и зона выставления
Личные стрелки и маркеры ТД — белые (маркер с тёмной каймой для читаемости на светлом поле), линия рассчитанного
маршрута — тёмная тонкая, предпросмотр пути — зелёный. База — зелёная, новый тип клетки `DeployZone` (`D` в карте) —
светло-зелёный: дополнительные клетки выставления из ростера (ТЗ ч.2 §5.6, используется с v0.8.0). **Статус:** принято.

## D-038. Транзакционный черновик приказа (ТЗ ч.2 §4.3, §14.3)
Пока игрок ставит ТД и выбирает взгляд, всё — предпросмотр (`OrderDraft` в ядре); при подтверждении финального
взгляда `GameSimulation.ApplyOrder(IndividualOrder)` проверяет всю цепочку (каждый сегмент — достижимая свободная клетка)
и заменяет очередь целиком. Если цепочка стала невозможной — приказ отклоняется полностью, прежний маршрут сохраняется,
черновик остаётся открытым (§9.5). На паузе принятый приказ ждёт снятия паузы. **Статус:** принято (допущение ТЗ).

## D-039. Непрерывная прокладка (§4.1, §14.1)
ТД1 — отпусканием первого протягивания из юнита; дальше режим не заканчивается: живая стрелка идёт от последней ТД к
курсору без нажатой кнопки, каждая следующая ТД — коротким кликом ЛКМ. Отпускание первого протягивания трактуется как
клик в точке отпускания (в т. ч. в секторе своей клетки = поворот на месте). **Статус:** принято.

## D-040. Сектора взгляда (§4.2, §14.2)
Исходная клетка (юнит или последняя ТД) делится на 6 секторов по рёбрам; сектор — ближайшее из 6 направлений к вектору
«центр → курсор» в плоскости карты. Нейтральная зона — круг радиусом 0,3 размера гекса: клик там ничего не подтверждает.
Клик в секторе = обязательный финальный взгляд и применение приказа; без ТД — поворот на месте. У выбранного юнита (без
черновика) те же сектора его текущей клетки поворачивают его на месте. **Статус:** принято.

## D-041. Отмена (§8, §14.4, §14.6)
ПКМ и Esc отменяют весь черновик (стрелки, ТД, подсветка), не трогая подтверждённые приказы. Попытка поставить ТД на
красную клетку (клик или отпускание первого протягивания) — та же отмена; простое наведение на красную клетку — нет.
ПКМ по ТД черновика удаляет её и все следующие (черновик продолжается). ПКМ по подтверждённой ТД выбранного юнита (без
черновика) удаляет её и следующие из очереди; финальный взгляд сохраняется и применяется в новом конце. Чужие цепочки не
затрагиваются. **Статус:** принято.

## D-042. Редактирование подтверждённого маршрута
Протягивание из **последней** подтверждённой ТД открывает черновик, заполненный оставшимися ТД юнита (продолжение
маршрута); подтверждение взгляда заменяет очередь целиком (нумерация с 1). Протягивание из промежуточной ТД отклоняется
(подсказка). Пока черновик открыт, старый маршрут показывается бледным. **Статус:** принято.

## D-043. Финальный взгляд
Хранится в `OrderQueue.FinalFacing` и применяется, когда очередь выполнена (на последней ТД, независимо от направления
последнего шага; для поворота на месте — как только юнит стоит в центре гекса, т. е. у идущего юнита — после текущего
шага). Во время движения указатель показывает направление шага. Сохранённый финальный взгляд рисуется белой стрелкой у
ребра последней ТД. **Статус:** принято.

## D-044. Зарезервированный приказ атаки (§7)
`OrderKind { MoveToTile, AttackTarget }`; в черновике клетка с вражеским юнитом получает статус `AttackTarget`
(оранжевая стрелка), клик даёт обратную связь `AttackTargetReserved(unit, targetId)` — ссылка на ID врага, а не на
клетку. В этой версии ничего не исполняется: ТД не создаётся, юнит не идёт в клетку врага, урона нет; черновик не
отменяется. Порядок обработки клика: враг → (будущая атака); свободная допустимая клетка → ТД; иное → отмена.
**Статус:** принято (резерв архитектуры).

## D-045. Движущийся юнит (§9)
Выбирается кликом по корпусу или по своей логической клетке; новая цепочка строится от `CommandAnchor` (клетка, в
которую идёт шаг — ближайший безопасный центр); текущий шаг всегда доводится до конца, поэтому нет рывка/телепорта и
логическая занятость не нарушается (единый момент смены клетки — середина шага, D-025). **Статус:** принято.

## D-046. Ростер и разрешённые клетки (ТЗ ч.2 §5)
Ростер прототипа — пять оперативников с фиксированными именами (`RosterState.Prototype()`); ресурсы и ограничения
количества — будущий этап (§5.7). Разрешённые для выставления клетки берутся **только из данных карты**: база игрока
(`B`) и клетки зоны выставления (`D`). Краевые зоны появления (`1`, `2`…) игроку для ростера не разрешены (§5.6);
отладочное появление на базе/краях/клетке из ч.1 сохранено и создаёт активных юнитов. **Статус:** принято.

## D-047. Жизненный цикл выставленного юнита (§5.4, §5.7, §12.7)
`PlaceFromRoster` создаёт юнита со статусом `PlacedPendingFacing` и `Facing = null`: он занимает клетку (её нельзя занять
другому), но не двигается и не действует. Активным (`Active`, карточка тоже `Active`) он становится, когда принят первый
приказ (`ApplyOrder`) — начальный взгляд = направление первого шага, финальный — выбранный сектор, — или поворот на месте
(`SetFacing`). Отклонённый приказ оставляет его в ожидании. Отменённый черновик — тоже; выбор такого юнита (клик по нему
или по его карточке) снова открывает черновик. **Статус:** принято (допущение ТЗ).

## D-048. Перетаскивание карточки (§5.2–5.5)
Нажатие ЛКМ на карточке (UI) вызывает `InputStateMachine.BeginRosterDrag`; движения и отпускание мыши передаются автомату,
даже если нажатие было над панелью. Под курсором — полупрозрачный «призрак» (зелёный/красный), разрешённые клетки зелёные,
остальные мягко-красные. Отпускание на разрешённой свободной клетке → юнит и сразу черновик (стрелка от него без нажатой
кнопки). Отпускание на запрещённой клетке, вне поля или над панелью, ПКМ, Esc → карточка возвращается (`RosterCardReturned`),
модель не меняется. Клик по карточке уже выставленного оперативника выбирает его. **Статус:** принято.

## D-049. Нижняя панель и камера
Панель ростера — отдельный `CanvasLayer` по центру свободной области справа от HUD, высота 96 px × масштаб UI; камера
вписывает поле над ней (`FitCamera`). Над панелями указатель не попадает на карту (в режиме перетаскивания карточки
выборка «над UI» не содержит клетки). **Статус:** принято.

## D-050. Режим «Команда» — явный инструмент (ТЗ ч.2 §6.1, §11)
Карточка «Команда» в нижней панели справа от ростера включает режим сбора (`GroupCollect`); повторное нажатие, ПКМ или Esc
выключают его без применения. Первый клик по своему юниту — капитан (`Members[0]`), следующие — участники; клик по уже
выбранному не меняет состав и капитана; не больше 7 участников (капитан + 6 мест первого кольца; крупнее — §14.8, не
нормировано). Клик по земле без капитана — подсказка (режим не закрывается); по врагу — зарезервированная атака. После КТД1
состав фиксирован: свой юнит не из команды на клетке — занятая клетка (клик — отмена), участник — без действия.
**Статус:** принято.

## D-051. Построение вокруг КТД (§6.2, §10)
`GroupStageEvaluator` — одно правило и для подсветки, и для применения: капитан должен дойти до КТД (клетку КТД может
занимать только он); каждому спутнику — своя свободная проходимая достижимая клетка первого кольца вокруг КТД. Юниты вне
команды — препятствия, участники друг другу — нет (они уходят вместе). Назначение — полный перебор (≤ 6! = 720 вариантов)
с минимумом суммарной длины путей; при равенстве выигрывает первый вариант в порядке сторон N, NE, SE, S, SW, NW по порядку
участников — результат зависит только от состояния и входа (стабилен при движении курсора). Этап k начинается с мест
этапа k−1. Клетка зелёная, только если помещается вся команда. Распределение мест (в D-033 — v0.10.0) сделано в v0.9.0,
потому что от него зависит допустимость КТД; v0.10.0 добавляет синхронность этапов, взгляды спутников и уступание прохода.
**Статус:** принято.

## D-052. Применение и жизнь командного приказа (§6.4)
`GameSimulation.ApplyGroupOrder(GroupOrder)` — транзакция: вся цепочка планируется от `CommandAnchor` участников; при любой
невозможной КТД ничего не меняется (`GroupOrderRejected`, черновик остаётся открытым). Иначе регистрируется
`GroupOrderState` (участники, капитан, КТД, места по этапам, финальные взгляды), очередь каждого участника заменяется его
местами, `OrderQueue.GroupId` указывает на приказ, ожидающие (из ростера) участники активируются. Личный приказ участнику
выводит его из командного; приказ удаляется, когда его не выполняет ни один участник (`GroupOrderFinished`). Постоянных
отрядов, смены капитана и меню строя нет. **Статус:** принято.

## D-053. Взгляд спутников в v0.9.0 (§6.3, §14.5)
Капитан — выбранный игроком сектор последней КТД; спутники в v0.9.0 смотрят так же (ТЗ §14.5 допускает «ровно
FacingCaptain»). Случайный выбор из {капитан, ±60°} один раз при подтверждении с фиксируемым seed — v0.10.0.
**Статус:** принято (временно).

## D-054. Участник ждёт участника
Если место участника занято другим участником того же командного приказа (например, капитан проходит через него), юнит
получает статус `Waiting` без события `UnitBlocked` и без красного «!»; путь пересчитывается при изменении занятости
(`TopologyVersion`). Для чужих юнитов поведение прежнее (`Blocked` с причиной). **Статус:** принято.

## D-055. Голубая графика команды (§3.1, §6)
Всё командное — голубое, в верхнем слое без теста глубины: при сборе — стрелка от корпуса каждого участника к курсору; над
допустимой клеткой — стрелки к местам (у капитана шире); подтверждённые этапы — стрелки участник → место; КТД — номерные
маркеры (в черновике с янтарной каймой), места спутников — маленькие голубые шестиугольники; взгляд капитана — белая
мини-стрелка у ребра последней КТД (у спутников — меньшие). Участники при сборе — голубые кольца, капитан — голубой ромб
над юнитом, рисуется поверх стрелок. Подтверждённые командные цепочки остаются голубыми. **Статус:** принято.

## D-056. Синхронные этапы КТД (§6.2)
Прогресс участника — число пройденных этапов (`число КТД − оставшиеся ТД приказа`, обходные шаги не считаются). Участник,
у которого прогресс больше минимального по команде, не начинает шаг к следующему месту (`Waiting`, `WaitReason.TeamStage`).
Так никто не идёт к КТД k+1, пока все не встали на места у КТД k; внутри этапа участники идут независимо. Командный приказ
завершается для всех сразу, когда закончили все (до этого закончившие остаются «своими» — их можно попросить отойти).
Участник, получивший личный приказ или обрезавший цепочку ПКМ, выходит из командного приказа и команду не задерживает.
**Статус:** принято.

## D-057. Взгляды спутников с seed (§6.3, §10, §14.5; заменяет D-053)
Смещение спутника относительно взгляда капитана ∈ {−60°, 0, +60°} = SplitMix64(seed, номер приказа, id юнита) mod 3.
`SimulationSettings.Seed` (по умолчанию 20261106). Вычисляется при подтверждении и хранится в `GroupOrderState.FinalFacings`;
`GameSimulation.PreviewCompanionFacings` даёт те же значения для предпросмотра (используется следующий номер приказа),
поэтому наведение не «перебрасывает» взгляды. Одинаковое состояние + команды + seed → одинаковые взгляды. **Статус:** принято.

## D-058. Построение без взаимной блокировки (§6.2)
Порядок прихода внутри этапа не управляется, поэтому место, на котором ждёт пришедший, не должно стоять на чужом пути.
Конфликт: место спутника на кратчайшем пути капитана; путь спутника через КТД; путь спутника через место другого спутника
(пути — по дереву кратчайших путей, участники не препятствия). Цель поиска — минимум (конфликты, суммарная длина), ничьи —
порядок сторон. Циклы «каждый ждёт клетку соседа» между спутниками невозможны (стоять на месте всегда дешевле обхода цикла);
обмен «капитан ↔ спутник на следующей КТД» исключён запретом клетки капитана для такого спутника. В узком коридоре конфликт
бывает неизбежен — тогда работает уступание прохода (D-059). **Статус:** принято.

## D-059. Ожидание и уступание прохода внутри команды (§6.2; расширяет D-054)
Если пути нет только из-за участников той же команды (путь без них есть), юнит ждёт (`WaitReason.Teammate`) без
`UnitBlocked`; путь пересчитывается при изменении занятости. Через 0,8 с ожидания первый стоящий участник на этом пути
получает обходной шаг (`Waypoint.IsDetour`) на свободную соседнюю клетку вне пути (ближе к своей цели), ждёт там, пока
попросивший не пройдёт освобождённую клетку (`WaitReason.Yielding`), и продолжает свой маршрут; закончивший участник
возвращается на своё место, и его финальный взгляд применяется снова. Обходные шаги не рисуются, не нумеруются и не
задерживаются синхронизацией. Если отойти некому/некуда 6 с — `UnitBlocked(BlockedByTeammates)`, без вечного ожидания и
без входа в занятую клетку. **Статус:** принято.

## D-060. Выбор сектора у поднятого препятствия
`PointerSample.Ground` — точка земли без учёта поднятых клеток. Если она лежит в исходной клетке черновика (юнит/последняя
ТД/КТД, клетка выбранного юнита для поворота), сектор берётся по ней, даже когда луч сначала попал в верх соседнего
препятствия, закрывающего край клетки на экране. Иначе действует прежнее правило (препятствия загораживают то, что за ними).
**Статус:** принято.

## D-061. Ромб капитана
Белый (освещённый) ромб над капитаном, рисуется без теста глубины поверх стрелок: голубой терялся на собственной голубой
стрелке капитана (уточнение D-055). **Статус:** принято.

## D-062. Версии для ТЗ части 3
ТЗ ч.3 §10 предлагает номера v0.8.0–v0.11.0, но они уже выпущены (ч.2) и неизменяемы. Строки плана ч.3 реализуются
следующими версиями: v0.11.0 — 1 гекс/с, непрерывная позиция, безопасное сглаживание; v0.12.0 — HP 100, смерть, обычная
атака 3/с, мишени, `AttackTargetOrder`; v0.13.0 — «Линейный удар»; v0.14.0 — навык в ТД (клик по ТД, иконка, красная
стрелка, шестиугольник «1»). **Статус:** принято.

## D-063. Файл актуального ТЗ
ТЗ ч.3 просит обновлять «актуальное, а не историческое ТЗ» и не трогать файлы редакций 0.1–0.2. Поэтому редакция 0.3
хранится в `docs/GAME_SPEC_PART3.md` (дословно), `GAME_SPEC.md` и `GAME_SPEC_PART2.md` не меняются; пункт §10 «обновление
`docs/GAME_SPEC.md`» трактуется как ведение актуального файла ТЗ. **Статус:** принято.

## D-064. Модель движения: шаги + кривые (§2.1–2.3)
Авторитетная модель — прежние шаги по `GraphPath`: резерв следующего гекса при начале шага, хвостовой резерв до конца
шага, одна клетка на юнита. Для каждого шага строится кривая (`StepGeometry`): первая часть внутри покидаемого гекса,
вторая — внутри входного, стык — середина общего ребра. Поворот скругляется квадратичной кривой «середина входного ребра
→ центр → середина выходного ребра» (лежит в одном гексе, касательная непрерывна); поэтому тело проходит ровно гексы пути
и в их порядке, а у заблокированного внутреннего угла остаётся ≥ 0,54 от его границы. Логический гекс переключается,
когда положение тела оказывается в следующем гексе (одно правило, нарисованное = логическое). ТД и конец маршрута —
якоря (кривая приходит в центр). Новый приказ во время шага: остаток шага перестраивается от текущей точки и касательной
(`Retarget`); шаг всегда доигрывается, `CommandAnchor` прежний (D-045). **Статус:** принято (проектное решение §2.2).

## D-065. Проверка коридора и откат (§2.2 п.4–5)
Каждая кривая проверяется выборкой через 0,03 по длине: круг тела (r 0,28) не должен задевать гекс вне {покидаемый,
входной, следующий по пути}. Не прошла — шаг идёт по прямым через центры. Для стандартных поворотов (0°, ±60°, ±120°)
проверка доказуемо проходит (тест на все 30 сочетаний); откат нужен для перестроек из нестандартного положения.
**Статус:** принято.

## D-066. Скорость и время (§2.4)
`SimulationSettings.DefaultUnitSpeed = 1,0` гекс/с. Шаг длится `1 / скорость` игрового времени независимо от длины
кривой (тело внутри шага движется равномерно по длине кривой), поэтому сглаживание не ускоряет и не замедляет маршрут:
три перехода — 3 игровые секунды при любой частоте кадров. **Статус:** принято.

## D-067. Диагностика движения (§8)
F3 (и шаг автоматизации `debug:on|off`) показывает поверх сцены: гексы `GraphPath` (жёлтые), логический гекс (белый),
кривую текущего шага (розовая) и след последних позиций (оранжевый). Только отображение; правила не меняются.
**Статус:** принято.

## D-068. Характеристики и данные баланса (§3, §8)
`UnitStats` (MaxHealth 100, MoveSpeedHexPerSecond 1,0, AttackRatePerSecond 3,0, NormalAttackDamage 10,
NormalAttackRangeHex 1) задаются в `SimulationSettings.DefaultStats`; клиент читает их из `res://data/balance.json`
(экспортируется вместе с картой). Урон 10 и дальность 1 — `PROTOTYPE_DEFAULT`, не канон (§11). **Статус:** принято.

## D-069. Смерть (§3, §7 п.5)
`GameState.ApplyDamage` уменьшает здоровье не ниже 0; при 0 юнит сразу `Dead` (не бьёт, не ходит, не получает приказов).
После всех систем тика `RemoveDead` по порядку id снимает погибших: клетка и все резервы освобождаются, очередь
сбрасывается, юнит переносится в `Fallen`, карточка ростера → `Unavailable`, событие `UnitDied`. Тело не остаётся
препятствием (допущение §3). Судьба команды при гибели капитана — открытый вопрос §11: участники просто продолжают свои
маршруты. **Статус:** принято.

## D-070. Приказ атаки (§4.1, §4.3)
`IndividualOrder.AttackTarget` — конечная стадия цепочки после ТД; `OrderQueue.AttackTarget`, `FinalFacing = null`.
Ввод: живой враг под концом стрелки (тело или его клетка) проверяется до правила «красная клетка = отмена»; клик/отпускание
→ `ApplyOrder` сразу, без выбора взгляда. Взгляд — `HexDirections.Toward(клетка юнита, клетка цели)`: ближайшее из шести
по скалярному произведению, равенство — первое в порядке N, NE, SE, S, SW, NW; ставится при подтверждении (и на паузе).
Цель — только живой юнит другой стороны (`WaypointError.InvalidTarget`). Групповая атака не вводится (§4.1 п.5).
**Статус:** принято.

## D-071. Исполнение атаки (§4.2, §7 п.4)
`AttackSystem` после `MovementSystem`, юниты по id. Пока есть ТД — идёт по ним. Цель вне радиуса — обходной шаг к
ближайшей свободной достижимой клетке в радиусе (длина пути, равенство — порядок клеток), не чаще раза в 0,5 с; клетку
цели не занимает; нет такой клетки — `TargetUnreachable` + событие, ожидание на месте. В радиусе и стоя — поворот к цели
и удар каждые 1/AttackRate игрового времени, первый — через интервал (3 с → 9 ударов). Цель ушла из радиуса — снова
подход, таймер заново. Цель погибла/исчезла — `AttackTargetLost`, приказ снят. Новой цели сам не ищет (без ИИ/агро).
**Статус:** принято (проектные предложения §4.2).

## D-072. Мишени и стенд (§9)
Враги — юниты стороны `Enemy` без приказов и без ИИ: «Мишень врага (T)» (режим выставления со стороной Enemy) и кнопка
«Стенд» (четыре мишени у стены и на открытом месте). **Статус:** принято.

## D-073. Описание навыка и область (§5.1, §8)
`SkillDefinition`: `RelativeSteps` (пути по направлениям относительно выбранного; «Линейный удар» = [вперёд], [вперёд,
вперёд]), `Damage`, `FriendlyFire = false`, `BlockedByObstacles = false`, `Cost/CooldownSeconds/CastSeconds = null`
(временные правила §5.1, расширяются данными). `Area(origin, direction, grid)` — чистая гекс-арифметика; клетки вне
поля отбрасываются. Урон «Линейного удара» (20) — в `data/balance.json`. **Статус:** принято.

## D-074. Немедленное применение (§5.2 — проектное предложение)
Вызов — кнопка «✦ Линейный удар (R)» в блоке выбранного юнита или клавиша R. Направление — ближайшее из шести к вектору
«центр клетки юнита (якорь команд) → точка курсора на земле», нейтральный центр 0,3 гекса не выбирает. Подтверждение ЛКМ
создаёт `SkillAction` (`UseSkill`), ПКМ/Esc отменяют только прицеливание. Действие срабатывает в первом тике, когда юнит
стоит в центре клетки (текущий шаг доводится до конца), — от этой клетки; юнит поворачивается в направление удара и так
остаётся до следующего шага (§6.3). Повторное прицеливание заменяет несработавшее действие (старое — `Cancelled`).
Красная стрелка прицеливания используется и здесь — тот же визуальный язык, что для ТД в v0.14.0. **Статус:** принято.

## D-075. Порядок тика (§7)
`MovementSystem` → `SkillSystem` → `AttackSystem` → снятие погибших → завершение команд. На паузе нет тиков: ни
срабатываний, ни урона, ни таймеров. Все системы обходят юнитов по возрастанию id. **Статус:** принято.

## D-076. Навык в ТД: модель (§6.1, §6.5, §8)
Навык хранится на самой ТД: `Waypoint.Skill` — `SkillAction` с `OriginWaypointId`. Подтверждённый приказ несёт
`IndividualOrder.WaypointSkills` (индекс ТД → `WaypointSkillSpec(SkillId, Direction)`), `ApplyOrder` проверяет их
(`WaypointError.InvalidSkill`: навыка нет у юнита, индекс вне цепочки) и создаёт по `SkillAction` на ТД (`SkillPlanned` с
`WaypointId`). На ТД не больше одного навыка — повторное назначение заменяет прежнее (старое `Cancelled`). Удаление ТД
(усечение, очистка, новый приказ) отменяет только её навык. Обходные ТД (подход к цели, уступание) и КТД командного
приказа навыков не несут (ТЗ ч.3 §6 описывает только собственный маршрут юнита; удержание одного участника сбивало бы
синхронные этапы).
**Статус:** принято.

## D-077. Навык в ТД: исполнение (§6.1 п.6, §6.3, §6.5, §7)
ТД с запланированным навыком — якорь: кривая приходит в её центр. `MovementSystem`, дойдя до неё, не начинает следующий
шаг в том же тике (`Waiting`, `WaitReason.Skill`); `SkillSystem` в этом тике поворачивает юнита в направление навыка,
берёт снимок врагов в двух клетках от ТД, наносит урон (`SkillActivated`) и помечает действие `Executed`; со следующего
тика маршрут продолжается сам. Итого удержание — ровно один тик (время каста 0, §7 п.6). На последней ТД после удара
юнит возвращается к финальному взгляду приказа (проектное правило §6.3). Исполнение привязано к id действия и ТД, а не к
клетке: повторный вход в клетку, пауза, перестройка кривой, частота кадров его не повторяют. Погибший юнит и
недостижимая/удалённая ТД навык не исполняют (на чужом гексе — никогда). Приказ атаки — последняя стадия после ТД и навык
не трогает. **Статус:** принято.

## D-078. Меню ТД и прицеливание от ТД (§6.1–6.2, §6.4)
- Короткий клик ЛКМ (без выхода за порог drag 8 px, D-040) по центральному маркеру ТД — круг радиуса нейтральной зоны
  (0,3 гекса) вокруг центра ТД — открывает `WaypointMenuView`: у черновика — для любой ТД, у выбранного живого своего юнита —
  для подтверждённой не обходной ТД личного (не командного) приказа. Приоритет: меню/иконка > центр маркера > сектор взгляда > гекс; центр маркера и
  сектора у рёбер не пересекаются, поэтому финальный взгляд выбирается как в ч.2.
- Меню — `WaypointMenuPanel` (UI над стрелками): «✦ Линейный удар» и «✕» (если навык назначен). Нажатия по нему в автомат
  не попадают — ТД случайно не создаётся. Клик мимо меню, ПКМ и Esc закрывают только меню; новый черновик, выбор другого
  юнита, ростер, режим «Команда» и отладочные режимы — тоже.
- Иконка → `SkillAim` с началом в ТД (`SkillAimView.FromWaypoint`): направление — ближайшее из шести к вектору «центр ТД →
  курсор», нейтральный центр не выбирает. ЛКМ: в черновике — `OrderDraft.SetSkill` и возврат в черновик (ждёт следующей ТД
  или финального взгляда, красная стрелка взгляд не подменяет); на подтверждённом маршруте — `AssignWaypointSkill`
  (одной транзакцией; отмена прицеливания ничего не меняет). ПКМ/Esc в прицеливании отменяют только его.
- Отображение: красный шестиугольник «✦1» над правым верхним краем маркера ТД (поверх стрелок, не закрывает маркер);
  серые клетки — мягкая заливка; ярко — прицеливание и ТД под курсором/с открытым меню, приглушённо — остальные
  назначенные навыки выбранного юнита; в черновике — только по наведению на ТД, чтобы не смешиваться с подсветкой
  движения. После срабатывания значок и зона исчезают (остаётся короткая вспышка удара). **Статус:** принято.

## D-079. Подсветка движения при меню ТД и прицеливании (§6.4; уточняет D-078, v0.14.1)
Пока открыто меню ТД или идёт прицеливание навыка, зелёно-красная подсветка движения черновика скрыта: клик в этих
состояниях ТД не ставит, а серая область навыка не должна смешиваться с подсветкой движения. При наведении на ТД
черновика без меню подсветка движения остаётся (её режим — приоритет), серая область этой ТД показывается поверх.
В v0.14.0 подсветка не скрывалась (тег и архив неизменяемы — исправление выпущено как v0.14.1). **Статус:** принято.

## D-081. Файл ТЗ части 4
Редакция 0.4 хранится дословно в `docs/GAME_SPEC_PART4.md`; файлы 0.1–0.3 не меняются. Правила боя и движения — по 0.3,
всё о редакторах и способе задания характеристик — по 0.4. **Статус:** принято.

## D-082. Слои Content и Editor (§10)
`HexTactics.Content` (чистый C#, ссылается на Core): определения, реестры видов/полей/эффектов, валидация, хранилище,
`RuntimeFactory`. `HexTactics.Editor` (Core + Content): Undo/Redo и модели каталога/редакторов. Simulation о Content не знает:
фабрика выдаёт типы Core (`MapDefinition`, `UnitStats`, `SkillDefinition`), поэтому «Играть» и тест из редактора используют
одну симуляцию. Клиент Godot только показывает модели (папки `MainMenu`, `GameMode`, `DeveloperMode`). Тесты — новые
проекты `Content.Tests`, `Editor.Tests`. **Статус:** принято.

## D-083. Формат определений и ID (§8.1–8.2)
Оболочка `schemaVersion, id, kind, name, description, revision, modified, tags, references, data` (`docs/CONTENT_FORMAT.md`);
`references` вычисляются из `data` при записи. ID: `[a-z0-9]+([._-][a-z0-9]+)*`, 3–64 символа; имя файла = ID;
`core.` — только встроенный контент; новые — `<kind>_<8 hex>`. JSON UTF-8 с отступами, фиксированный порядок полей,
чтение с ограничением глубины и размера (2 МБ). Схема каждого вида — версия 1. **Статус:** принято (проектное предложение §13).

## D-084. Встроенный контент — данные, один источник правды (§1, §6.6, §9.1)
Игра поставляет определения в `res://data/content` (список — `index.json`): 7 типов гексов (обычный, высокий, препятствие,
база игрока, база врага, зона выставления, край/зона появления), юнит «Оперативник», навык «Линейный удар», карта
«Прототип 12×10». «Играть» строит матч только из библиотеки: `data/balance.json` удалён (значения — в юните и навыке),
`maps/prototype.hexmap` больше не загружается игрой (оставлен эталоном для тестов: тест сравнивает карту из JSON с ним
поклеточно). Цвета типов совпадают с прежними цветами ролей. **Статус:** принято.

## D-085. Пустые места, роли и уровни гексов (§4.1–4.2)
`TileType.Void` — места рабочей области без гекса: непроходимы, не край для себя, не цель ТД, не клетка навыка, не
рисуются; гекс рядом с пустотой считается краем (для зон появления). `TileType.EnemyBase` — метка «база врага»
(проходима, без ИИ). `TileState` получил `TileId` (тип из библиотеки) и `Level` (0…3, только вид: высоты 0/0,18/0,36/0,55;
на высоком гексе юнит рисуется на его верхней грани, подсветки поднимаются, луч выбора учитывает высоту). **Статус:** принято.

## D-086. Эффекты: одна трасса данных (§6.3, §9.1–9.2)
Core: `EffectSpec` (тип + параметры-данные) и `SkillCell(смещение, эффекты)`. Content: `EffectTypeRegistry` — поля,
диапазоны, значения по умолчанию, где разрешён эффект. Simulation: `EffectResolver` — единственный исполнитель (обработчик
на тип, проверка целей `enemies/allies/self/all`); неизвестный тип не исполняется. В v0.15.0 зарегистрирован только
`damage` с фиксированной величиной — «Линейный удар» исполняется им; формулы от Attack Power, удары с интервалами, лечение,
баффы и дебаффы — v0.18.0. Смещения клеток хранятся для взгляда на север и поворачиваются `HexCoord.RotateFor` (куб
(q,r,s) → (−r,−s,−q), тест на отсутствие отражения). Порядок применения: клетка (в порядке хранения) → эффект → цель.
**Статус:** принято.

## D-087. Хранилище пользователя (§8.1)
`ContentRepository` на `user://` (или `--hx-user-root`): `content/`, `drafts/`, `backups/`, `logs/`, `packs/`.
Запись атомарна: временный файл → чтение обратно и полная проверка → переименование поверх. Удаление переносит файл в
`backups/deleted` (Undo возвращает), копии перед заменой — `backups/<время>-<причина>`, журнал — `logs/content.log`.
Файлы, которые не удалось прочитать, не меняются и показываются в сообщениях. **Статус:** принято.

## D-088. Undo/Redo (§3.3)
`CommandHistory`: команды `Do/Undo`, транзакции (одна запись, откат всех частей при ошибке), отметка сохранённого
состояния (`IsDirty`), предел 500 шагов. Команда, которую нельзя выполнить/отменить (`EditorCommandException`), историю
не меняет. В каталоге v0.15.0 через неё идут дублирование, переименование и удаление (они сразу пишутся на диск, отмена
возвращает файлы). **Статус:** принято.

## D-089. Стартовое меню и режимы (§2.1)
Корень `AppRoot` (`scenes/App.tscn`): стартовый экран «Играть» / «Разработчик» / «Выход»; одновременно живёт один режим,
симуляция в редакторе не работает. «← Главное меню» из боя — с подтверждением (бой закрывается, данные библиотеки не
меняются). `ModalDialog` перехватывает мышь и клавиатуру (Esc = отмена); в бою ввод карты под ним выключен.
**Статус:** принято.

## D-090. Каталог разработчика (§2.2, §3.1)
Категории — из реестра (видимые `Available`). Список: название, тип/описание, ID, дата, ревизия/схема, проверка; поиск по
названию/ID/описанию, сортировка по названию/дате/ID. Действия: Создать, Открыть (по реестру редакторов клиента — в
v0.15.0 пуст), Дублировать (и встроенных), Переименовать, Удалить (с проверкой ссылок), Импорт/Экспорт (v0.20.0),
«Проверить всё». Справа — свойства, ссылки, «используется в», проверка; внизу — сообщения. **Статус:** принято.

## D-091. Автоматизация режимов
Шаги приложения: `ui:<id>` (клик по зарегистрированному элементу настоящими событиями мыши), `field:<id>=<значение>`,
`key:ctrl+z`, `row:<id>|name=<название>`; проверки `expect:screen|dialog|category|rows|selected|item|undo|message`.
Аргументы `--hx-start=play|dev`, `--hx-user-root=<папка>`. `verify_release.ps1` для v0.15.0+ запускает сборку дважды с одной
временной папкой пользователя: сценарий + проверка сохранения после перезапуска. **Статус:** принято.

## D-092. Модель редактора карт (§3.3, §4)
`MapEditorModel` (Editor) редактирует рабочую копию определения; каждая правка — команда-снимок «до/после» всей карты
(карты малы, ≤ 1024 гекса), пустые правки в историю не попадают. Выбор, режим удаления и «кисть» — состояние интерфейса,
не история. Клик: пустое место в области → один гекс типа «кисти» + выбор; гекс → выбор; в режиме удаления — отметка.
Гексы хранятся по координате, двух гексов на одном месте быть не может. **Статус:** принято.

## D-093. Красная кнопка удаления (§4.3)
`PressDeleteButton`: 1-е нажатие — режим выбора (ничего не удаляется); 2-е — удаление отмеченных одной командой (если
отмеченных нет — просто выход из режима); Esc/«Отмена» — выход без удаления. Связи гекса (сейчас — тестовые точки;
размещения и цели событий появятся с их механиками) перечисляются перед подтверждением и снимаются в той же команде,
Ctrl+Z возвращает всё. Тип гекса в библиотеке при этом не трогается. **Статус:** принято.

## D-094. Тестовые точки и проверка маршрута (§4.4)
Карта может иметь тестовые точки (поле `testPoints`, необязательное — схема 1 без миграции): метки A, B, C… на реальных
гексах. Проверка ищет проходимый путь (тот же `Pathfinder`) между соседними точками по порядку; нет пути — замечание.
Без точек маршрут не проверяется: разрозненные островки — не ошибка. **Статус:** принято.

## D-095. Сохранение, черновики, выход (§2.1, §8.1)
Сохранение — через библиотеку (проверка → атомарная запись); встроенная карта сохраняется копией с новым ID. Черновик
несохранённой работы пишется в `user://drafts/maps/<id>.json` каждые 2 с при изменениях, удаляется при сохранении или
«Не сохранять»; при входе в режим разработчика найденные черновики предлагаются к восстановлению (сохранённая версия
не меняется, пока черновик не сохранят). Выход из редактора с изменениями — «Сохранить / Не сохранять / Отмена».
**Статус:** принято.

## D-096. Тест карты (§4.4, §3.2)
«Тест карты» строит матч из временной копии (`RuntimeFactory.BuildGame(library, item)`) в обычном `GameMode`: те же
жесты, симуляция, пауза, коллизии. Режим разработчика на время теста вынимается из дерева узлов (не работает и не
рисуется, но сохраняет состояние — холст, выбор, историю); «← Вернуться в редактор» возвращает его. **Статус:** принято.

## D-097. Холст редактора и выбор карты для игры
Вид — как в игре (60°) с переключателем «строго сверху»; колесо — масштаб к точке под курсором, средняя кнопка или
пробел+ЛКМ — сдвиг (`CameraRig.Zoom/Pan`). Пустые места — бледные контуры с координатами `col,row`, реальные гексы — с
цветом и высотой своего типа (`TilePalette`). Стартовый экран получил список карт для «Играть» (встроенные и свои без
ошибок). **Статус:** принято.

## D-098. Сила атаки и дробное здоровье (§5.1, §6.4)
`UnitStats.AttackPower` (дробное) — урон обычного удара и база будущих эффектов «% от Attack Power»; скорость атак —
отдельное поле. Здоровье и урон хранятся как `double` без округления (12,5 и 7,5 считаются точно); юнит мёртв при
здоровье ≤ 1e-9 (остаток плавающей точки). Отображение — до десятых (`UiText.Hp`: 77,5; 80). `GameState.Heal` не
поднимает выше максимума и не лечит мёртвых. **Статус:** принято (правило отображения — проектное, §13).

## D-099. Определение юнита в бою (§5.1, §8.4)
`UnitProfile` (Core): id определения, имя, характеристики, навыки. Ростер (`RosterEntry.Profile`) и `SpawnRequest.Profile`
создают юнита из профиля; без профиля — юнит по умолчанию (`SimulationSettings.DefaultUnitId`). У живого юнита —
`DefinitionId`, своё текущее здоровье, путь и взгляд; определение он не меняет. Вид (оттенок, размер) клиент берёт из
определения по `DefinitionId`. Кнопка навыка, R и меню ТД используют первый навык выбранного юнита. **Статус:** принято.

## D-100. Редактор юнитов (§5)
Поля — из `UnitData.Fields` (`Inspector.Field`); числа вводятся текстом, чтобы любой ввод прошёл проверку схемы
(`DefinitionEditorModel.TrySetField`): недопустимое значение не применяется, причина — в сообщениях. Навыки — ссылки по
ID (добавление только существующих из каталога с поиском; порядок важен; не больше 8). Предпросмотр «В бою» показывает
числа для этого юнита. «Тест юнита» — карта «Прототип», юнит — карточка «Альфа». На стартовом экране — выбор отряда
(5 карточек из одного определения игрока). Встроенный юнит сохраняется копией. **Статус:** принято.

## D-101. Ядро эффектов (§6.3, §9.1)
Типы v0.18.0: `damage`, `heal`, `buff`, `debuff`, `periodic` — дескрипторы `EffectTypeRegistry` (поля, диапазоны,
видимость поля от других полей) и обработчики `EffectResolver` (единственный исполнитель). Урон/лечение: `formula`
`fixed` (`amount`) или `attack`/`maxHealth` (`multiplier` × характеристика **источника** в момент попадания); 150 % —
множитель 1,5, а не доля здоровья цели. Модификатор: действующее значение = база × (1 + Σ процентов) + Σ дельт, затем
безопасный минимум (`Stats.Min*`: скорость 0,1 гекс/с, скорость атак 0,1 удар/с, сила атаки 0); бафф прибавляет,
дебафф вычитает. Контроль, отбрасывание, телепорт, щиты, вызовы не реализуются (ТЗ §6.3). **Статус:** принято.

## D-102. Статусы и повторное наложение (§6.3–6.4, §6.5)
`StatusEffect` (Core) — модификатор или периодический эффект с ключом «источник | тип | характеристика» (для навыка
источник — его ID: повтор того же навыка на ту же характеристику — «тот же эффект»), длительностью и остатком; `StatusSystem` (после атак) уменьшает остаток на тик, периодический действует
(уточнение v0.19.0: непрерывно — `perSecond` × игровое время каждого тика, а не раз в секунду), истёкший снимается с событием `StatusExpired`, характеристики пересчитываются. Политики при совпадении
ключа: `refresh` — остаток = длительность, величина не складывается (по умолчанию); `stack` — ещё один экземпляр со своим
таймером; `replace` — старый снимается, новый с полной длительностью; `ignore` — повтор не действует. На паузе тиков нет —
статусы не стареют. **Статус:** принято.

## D-103. Исполнение навыка: расписание попаданий (§6.5)
При активации строится `SkillExecution`: для каждой клетки и эффекта — попадания `k = 0…hits−1` во время `k × interval`;
порядок внутри тика — время → номер попадания → клетка (в порядке хранения) → эффект → цель (id). Попадания с временем 0
применяются на тике активации (поведение ч.3). Цели клетки берутся на тике попадания. Пока расписание не закончено,
статус действия `Executing`: юнит стоит в точке (`MovementSystem` ждёт, `AttackSystem` не бьёт), затем `SkillCompleted` и
маршрут продолжается. Удаление ТД, отмена навыка или смерть источника — `SkillInterrupted`, оставшиеся попадания не
наступают, применённое остаётся, наложенные статусы живут по своим таймерам. **Статус:** принято (ожидание в точке —
правило прототипа, §6.5).

## D-104. Клетки: наследование и переопределение (§6.2, §6.4)
Клетка без своих эффектов наследует `baseEffects` навыка; `overrides` клетки — словарь «индекс базового эффекта → поля»,
поле перекрывает только себя (приоритет у клетки). Значение, равное базовому, переопределением не хранится. «Свои эффекты»
копирует действующие эффекты клетки и дальше не зависит от базы; выключение возвращает наследование. Удаление базового
эффекта сдвигает индексы переопределений. Цвет/прозрачность клетки — только редактор: бой показывает зону стандартным
серым (§6.6). **Статус:** принято.

## D-105. Редактор навыков (§6.1, §6.4)
`SkillEditorModel` (Editor): клик по нарисованному смещению → `ToStored` (поворот на −facing), добавить/выбрать/стереть;
поле ограничено радиусом (2–6, по умолчанию 4; реальных узлов — только гексы радиуса); взгляд предпросмотра, радиус,
ластик и сила атаки предпросмотра — состояние вида, не данные (сохранение не требуется). Поля эффектов — из реестра
(`Inspector.Field`), значение проверяется схемой до применения; каждое изменение — отменяемая команда. `EffectPreview`
формулирует итог клетки числами. «Тест навыка»: `RuntimeFactory.BuildGame(…, testSkill)` — несохранённая копия навыка
первой у карточек ростера и у юнитов отладки. Переключатель «строго сверху» не добавлен (камера редактора уже сверху под
60°, допустимо по §6.1). **Статус:** принято.

## D-106. Навыки юнита в бою (§6.5, §12.2 п.18)
Меню ТД и панель показывают все навыки выбранного юнита в порядке определения (первый — R); в одной ТД — один навык.
Значок навыка на ТД и в меню — `icon` навыка. Всплывающие числа: урон — как в ч.3, лечение — зелёным «+N», статус —
подпись над юнитом; описание юнита показывает статусы с остатком и ход навыка («удары 2/3»). **Статус:** принято.

## D-107. Эффекты типов гексов: триггеры и стороны (§7.1–7.2)
Эффект типа гекса — тот же `EffectData` из реестра с отдельным набором полей для гексов (`EffectTypeDescriptor.TileFields`):
`trigger` — `stay` (пока юнит на гексе; только у `periodic`), `enter`, `exit`; `sides` — `all` / `player` / `enemy` вместо
«враги/союзники» (у гекса нет источника); урон/лечение — фиксированные (`amount`), без формул от силы атаки, попаданий и
интервалов. Периодический `stay` — непрерывно `perSecond` × время тика (`EffectInvocation.Slice`), без статуса; `enter`/`exit`
периодического — статус на `duration` с политикой повтора. Ключ статуса — `ID типа | тип | характеристика`. Других
триггеров нет (нет обработчика — нет поля). Радиус действия не вводится. **Статус:** принято.

## D-108. Логический гекс и порядок (§7.2, ч.3 §2)
`TileEffectSystem` («Tiles», после атак, до статусов) запоминает гекс каждого живого юнита. Смена `UnitState.Cell` (при
пересечении ребра) — `exit` прежнего типа, затем `enter` нового; первое появление на гексе — вход; гибель — без выхода.
`stay` — каждый тик для текущего гекса: тик принадлежит ровно одному гексу, поэтому сглаженная траектория и интерполяция
не дают двойного начисления. На паузе тиков нет. Здоровье дробное (D-098), округляется только на экране. **Статус:** принято.

## D-109. «Можно ставить ТД/КТД» (§7.1)
Поле типа `waypoints` (по умолчанию да) → `TileState.AllowsWaypoints`. `WaypointRules.ValidateTarget` и проверка КТД
отклоняют такой гекс (`WaypointError/GroupPlanError.WaypointsForbidden`), подсветка — красная; путь через гекс и стоянка на
нём по другим причинам (появление, места спутников команды) не запрещены — сложную систему разрешений не выдумываем.
**Статус:** принято.

## D-110. Экземпляр гекса и тип (§7.1, §7.2)
Гекс карты хранит только ссылку на тип и свои допустимые переопределения v0.16.0 (высота, зона, тестовая точка,
комментарий). Эффекты, проходимость и «ТД» берутся из типа; поштучного переопределения эффектов нет — изменить правила
можно только у типа, и после сохранения они действуют на всех картах (матч строится заново из библиотеки).
**Статус:** принято (поштучные эффекты — при отдельном решении).

## D-111. Редактор типов гексов и тест (§7)
`TileEditorModel` (Editor): поля `TileData.Fields`, эффекты — `AddEffect/RemoveEffect/SetEffectField` по полям для гексов,
проверка до применения, отмена; `TilePreview` — правила словами (общая с редактором карт). Клиент `TileEditor`: предпросмотр —
тип на центре и кольце среди обычных гексов. «Тест гекса» — `RuntimeFactory.BuildGame(…, testTile)`: гексы
`RuntimeFactory.TileTestCells` (col 2–3, row 4–6 «Прототипа») становятся несохранённой копией типа. Значок типа рисуется
`BoardView` на каждом его гексе. Числа непрерывных эффектов суммируются клиентом раз в игровую секунду. **Статус:** принято.

## D-112. Чистый выход (v0.19.1)
Все пути выхода идут через `AppExit.Quit`: `GC.Collect` → `GC.WaitForPendingFinalizers` → `GC.Collect` → `SceneTree.Quit`;
закрытие окна перехвачено (`AutoAcceptQuit = false`, `NotificationWMCloseRequest`). Причина: финализатор обёртки ресурса
Godot, сработавший во время остановки движка, обращался к освобождённой памяти (v0.19.0 под Wine после длинной сессии,
воспроизводилось 3 из 3; с исправлением — 0 из 3). **Статус:** принято.

## D-113. Формат экспорта (§8.3)
Один объект — тот же JSON, что и в библиотеке (`ContentSerializer`), поэтому сохраняются все поля. Пакет `.hxp` — ZIP:
`manifest.json` (`format = hextactics-package`, `formatVersion = 1`, имя, описание, версия игры, время, объекты с `kind`,
`id`, `name`, `revision`, `schemaVersion`, `path`, `sha256`, `bytes`, список нужных встроенных объектов) и
`content/<папка вида>/<id>.json`. В пакет попадают отмеченные пользовательские объекты и все их зависимости (замыкание по
`references`, зависимости раньше), встроенные — не копируются (есть в каждой установке). Других файлов в пакете нет:
пользовательские визуальные ресурсы пока не поддерживаются (их нет в данных). **Статус:** принято.

## D-114. Проверка импорта (§8.3)
До установки: размер (объект ≤ `MaxFileBytes`, пакет ≤ `MaxPackageBytes`), число файлов, суммарная распаковка, чтение
каждого файла не дальше предела, коэффициент сжатия > 200 у файлов от 64 КБ — отказ; путь — относительный, без `..`, `\`,
`:`, только `[A-Za-z0-9._/-]`; только `.json`; каждый файл указан в manifest, путь = `content/<папка>/<id>.json`, SHA-256
совпадает, объект внутри тот, что заявлен, без повторов. Ошибка уровня файла отклоняет весь файл. Затем каждый объект
проверяется как при сохранении, со ссылками на объекты файла и библиотеки; объект с ошибкой (и зависящий от него, если
библиотека его не заменит) не устанавливается. **Статус:** принято.

## D-115. Конфликты и установка (§8.3)
Статусы: новый (по умолчанию «установить»), без изменений (данные, название и описание совпадают; «пропустить» или
«копией»), конфликт (по умолчанию «пропустить»; «заменить с резервной копией» — только для своих объектов; «копией с новым
ID»), ошибки («пропустить»). Копия получает новый ID и название «… (импорт)»; ссылки выбранных объектов на скопированные
перепривязываются (`IContentData.RemapReferences`). Установка: проверка всего набора поверх библиотеки (`Overlay`) → запись
по одному (замена — после `Backup`) → при исключении удаление созданных и восстановление заменённых. После установки
библиотека перечитывается, история Undo каталога очищается (её команды относились к прежнему состоянию). **Статус:** принято.

## D-116. Миграция при загрузке (§8.4, §12.3 п.29)
Файл со `schemaVersion` меньше текущей версии вида проходит `ContentKind.Migrate` по шагам; если получилось, оригинал
копируется в `backups/<время>-migration-schemaN/`, затем файл переписывается атомарно с проверкой. Нет шага миграции или
версия новее — объект не загружается, файл не трогается (сообщение в каталоге). Сейчас все виды — схема 1; механизм
проверен тестом с видом схемы 2. **Статус:** принято.

## D-117. Пределы (§8.3)
`ContentLimits`: размеры, клетки, радиус, эффекты, навыки юнита, текст, `MaxSkillHitEvents = 1024` (стоимость одного
применения навыка), `MaxPackageBytes = 32 МБ`, `MaxPackageEntries = 512`, `MaxUnpackedBytes = 64 МБ`. `user://limits.json`
может задать целые от 1 до жёстких пределов (`HardCaps`); остальное — предупреждение, стандартное значение. **Статус:** принято.

## D-118. Окна импорта и экспорта
Экспорт и импорт — окна каталога на основе `ModalDialog` (прокручиваемое содержимое). Файл импорта — путь или имя файла
из папки `exports` этой установки; «Обзор…» — `FileDialog` Godot (не системный, чтобы работать одинаково). Логика — модели
`ExportPlan` и `ImportSession` (Editor), исполнение — `ContentExporter`/`ContentImporter` (Content). **Статус:** принято.

## D-119. Версии для ТЗ части 5
ТЗ ч.5 §12 предлагает v0.18.0–v0.22.0, но эти номера уже выпущены (ч.4) и неизменяемы. Строки плана реализуются
следующими версиями: v0.21.0 — `DamageEvent`/`DamageResolver`, каталог типов (физический: колющий/режущий/дробящий,
магический, чистый), одиночные/площадные компоненты, формула R −500…+500, детерминизм и совместимость; v0.22.0 —
`DefenseRule` и цепочка иммунитет/конверсия/отражение/щит/плоское снижение, пределы рекурсии, сценарий «огонь 300%»;
v0.23.0 — «Механики»: создание типов урона, шаблоны правил, профили сопротивлений, предпросмотр расчёта; v0.24.0 —
«Сопротивления» в редакторе юнита (простой UI, сложные реакции, фильтры, поиск), отладка тестового запуска; v0.25.0 —
сквозная проверка сохранения/импорта/экспорта/миграций, UX-испытания, регрессия. По постоянному правилу ч.4 §9.3 каждая
новая редактируемая механика получает поля в редакторе в той же версии, где появляется: сопротивления юнита и типы урона в
навыках/гексах/обычной атаке — уже в v0.21.0 простыми полями; v0.24.0 строит на них полный UX. **Статус:** принято.

## D-120. Единый расчёт урона (ч.5 §5)
`DamageResolver` (Simulation, `GameSimulation.Damage`) — единственное место, где урон снимает HP. Событие `DamageEvent`
(Core) создаёт источник: обычная атака (`AttackSystem`), эффект `damage` (навык/гекс), срез поверхности, периодический
статус. Стадии v0.21.0: допуск (цель жива на момент удара) → D0 = max(0, сила), NaN → 0 → R (только сопротивляемые типы) →
HP (`GameState.ApplyDamage`, смерть — в конце тика). Остальные стадии §5.1 (иммунитет, конверсии, плоское снижение, предел,
щиты, реакции, очередь) добавляются в этот же порядок с v0.22.0. Значения — `double`, порядок вычислений фиксирован на
фиксированном тике, внутренние значения не округляются (только отображение); 5 HP/с × 2 с = 10 с точностью 1e-9, три
удара по 7,5 = 22,5. Это проверенная детерминированная альтернатива фиксированной точке 1/1000 (§5.6). **Статус:** принято.

## D-121. Типы урона (ч.5 §2)
Вид `damage_type`: `family` (пусто — тип сам семейство), `strategy` (`resistance_affected` | `true_like`), `tags`, цвет,
значок, `legacy`. Подтип наследует стратегию семейства (другая — ошибка), семейство подтипа должно быть семейством. Встроенные
ID неизменяемы: `core.damage.physical/piercing/slashing/blunt/magical/true`, служебные `core.damage.untyped` (физическое
семейство) и `core.damage.direct` (как чистый). Стихии не вводятся. Тип — природа удара; форма (одна цель / область) —
отдельно. В v0.21.0 категория скрыта из каталога (встроенные типы используются в списках редакторов), создание своих — в
«Механиках» v0.23.0. **Статус:** принято.

## D-122. Формула сопротивления (ч.5 §3)
`R_до = clamp(R_global + R_семейство + R_подтип + R_временное, −500, +500)`; `R = R_до > 0 ? max(0, R_до − пробитие) : R_до`;
`урон = D × max(0, 1 − R/100)`. Для типа-семейства слой подтипа не берётся. Ключи сопротивлений юнита — `global` или ID
типа. `R_временное` — статусы `stat = resistance` (`resistanceOf` = `global` или тип, `delta` в п.п.; бафф +, дебафф −).
Чистый (и любой `true_like`) R не использует. Значения в определении — −500…+500, конечные, шаг 0,01; сумма слоёв за пределом
— предупреждение. **Статус:** принято.

## D-123. Область урона (ч.5 §2.1, §2.3)
Обычная атака: `attackAreaRadius` 0–3 — цели — враги атакующего в радиусе от гекса цели на момент удара (по возрастанию ID),
`attackAreaSplit` — делить силу поровну. Навык: область — клетки навыка; поле эффекта урона `area` = `full` | `split`:
при `split` сила эффекта в одном ударе делится между целями, которых задел этот эффект (базовый эффект i во всех
наследующих клетках или свой эффект клетки — «группа»). Цель одной клетки — один юнит, поэтому двойного попадания от
пересечения нет. **Статус:** принято.

## D-124. Миграция контента частей 3–4 (ч.5 §9.5)
Схемы `skill`, `tile`, `unit` → 2. Урон навыков и периодические статусы без типа → `core.damage.untyped`; урон гексов →
`core.damage.direct` (прежние HP/с для любой цели, в том числе с новыми сопротивлениями); обычная атака юнита →
`core.damage.untyped`; сопротивлений, щитов, правил нет. Новые эффекты и юниты получают `core.damage.physical`. Файл
обновляется при загрузке с копией оригинала (D-116). **Статус:** принято.

## D-125. Сокрытие защиты в игре (ч.5 §7.4)
Карточка юнита, статусы, всплывающие числа в «Играть» не показывают R, иммунитеты и правила: статус сопротивления —
«↑/↓ защита» без чисел, числа урона — следствие боя. Значения видны в редакторе юнита; явная отладка тестового запуска —
v0.24.0. **Статус:** принято.

## D-126. Правила защиты как данные (ч.5 §4, §6.3, §9.1)
Вид `defense_rule` (схема 1, папка `defense_rules`): `trigger` (`on_hit_contact` | `on_health_loss` | `on_damage_dealt` |
`on_status_applied`), `damageTypeId` (ID типа/семейства или `any`), `damageTag`, `minimumEffectiveResistancePercent` и
`healthBelowPercent` (null — условия нет), `triggerOnImmuneContact`, `priority` 0–1000, `cooldownSeconds` 0–600,
`maxTriggers` 0–10000, `actions` (1–8) — `{ "effect": "<id>", …поля }` из `DefenseActionRegistry` (Content). Каждая
реакция принадлежит одному «когда»; условия — только AND (ИЛИ — несколько правил, §6.3). Юнит хранит ссылки
`defenseRules` (без копий) и свои `shields`. Ответ на ответ (`allowReactiveChain: true`) в этой редакции — ошибка проверки
(§5.5: цепочки только с будущими отдельными ограничителями); поле `false` принимается, чтобы контракт §9.3 читался
дословно. **Статус:** принято.

## D-127. Порядок и бюджет (ч.5 §4.3, §5.1–5.2)
Правила «получен удар» отбираются по типу/семейству/тегу, условиям и готовности, сортируются `priority`, затем ID.
Иммунитет: HP-урона нет; конверсии и прочее при иммунитете — только у правил с `triggerOnImmuneContact`. Конверсии берут
`min(доля × D0, остаток)`; перерасход — событие `CombatLimitReached` (журнал), не отрицательный остаток. Лечение конверсией —
через общий путь лечения сразу (до урона остатка), неиспользованное не возвращается. Без целей доля отражения исчезает.
Дальше: R → плоское снижение (только `resistance_affected`) → предел → щиты (порядок, затем название; фильтр типа/семейства;
чистый урон щит принимает) → HP. Ответный удар — после фактической потери HP/щита живого защитника, не от реактивного
события; вампиризм — у атакующего от снятого HP (не при иммунитете и не при уроне только по щиту). «Здоровье ниже» у
вампиризма — здоровье владельца правила. Одно правило срабатывает за удар не более одного раза (перезарядка и лимит
считаются по срабатываниям). **Статус:** принято.

## D-128. Пределы реакций (ч.5 §5.5)
`CombatLimits`: `MaxProcDepth` = 1 (реактивный пакет не порождает реакций), `MaxGeneratedEventsPerRoot` = 64,
`MaxEventsPerTick` = 4096, `MaxReactionTargets` = 32 (цели по возрастанию ID). Реакции ставятся в очередь и
исполняются итеративно после текущего удара (не рекурсией) в порядке создания. Ответ на непрерывный урон (поверхность,
периодический статус) суммируется по (защитник, правило, реакция, источник) и отправляется раз в игровую секунду —
иначе 30 мелких пакетов в секунду. Превышение предела — `CombatLimitReached`, событие отбрасывается. Технические
значения, не баланс. **Статус:** принято.

## D-129. Щиты (ч.5 §4.5)
Щит юнита: `name` (уникально, до 40 символов), `capacity` (0 < … ≤ 100 000), `damageTypeId` (`any`, тип или семейство),
`order` 0–100. В бою щит начинается полным; «поглотить в щит» пополняет названный щит не выше прочности. Длительность и
износ щита (§4.5 «необязательно») не вводятся до отдельного решения. **Статус:** принято.

## D-130. Иммунитет к статусам и запрет лечения (ч.5 §4.1, §4.6)
Иммунитет к статусам — правило «накладывается статус» с категорией `debuff`/`buff`/`periodic`/`all` (тип эффекта);
заблокированный статус — событие `StatusBlocked`, в игре слово «невосприимчив». Запрет лечения — не отдельная механика, а
характеристика `healingReceived` (множитель входящего лечения, ≥ 0), которую меняют бафф/дебафф; единый путь лечения
(`DamageResolver.Heal`) умножает на неё любое лечение (навык, гекс, статус, конверсия, вампиризм). **Статус:** принято.

## D-131. Пример «огонь» (ч.5 §5.3, §9.3, §13.4)
Встроенный тип `core.damage.fire_example` («Огонь (пример)», подтип магического, тег `fire`) и правило
`core.rule.fire_convert_25_reflect_75` — только демонстрация и тестовые данные; элементальная система и её матрица не
вводятся. Встроенные объекты только читаются; изменения сохраняются копией с новым ID. **Статус:** принято.

## D-132. «Механики» в каталоге (ч.5 §6.1)
Виды `damage_type`, `defense_rule`, `resistance_profile` — категории реестра с `Group = mechanics`. Каталог показывает
«Механики» одной позицией: её первый экран строится из категорий группы (три крупные кнопки с описанием и числом
объектов), разделы доступны и ссылками под ней (их ID для автоматизации прежние: `dev.cat.<вид>`). Отдельного моря вкладок
нет; список, инспектор и редакторы — те же, что у остальных категорий. **Статус:** принято.

## D-133. Наборы сопротивлений и слои (ч.5 §6.4)
`resistance_profile`: `parent` (набор-основа или пусто) и `values` (ключи как у юнита). Значения набора = значения основы,
перекрытые своими по ключу (цепочка до 8, цикл — ошибка проверки и остановка разрешения). Юнит: `resistanceProfiles` по
порядку — более поздний набор перекрывает ранний по ключу; `resistances` — свои значения юнита поверх всех наборов (явный 0
допустим). Итог — базовые значения формулы D-122 (слои «все типы + семейство + подтип» складываются как раньше). Набор —
данные, а не боевой механизм; изменение набора действует на всех юнитов после сохранения. **Статус:** принято.

## D-134. Конструктор типа урона (ч.5 §6.2)
Новый тип создаётся только от явной основы: подтип физического/магического (стратегия — семейства), подтип чистого
(`true_like`) или самостоятельное семейство (стратегия выбирается явно). ID — из пространства пользователя
(`damage_type_<hex>`), встроенные `core.*` не меняются. Подтип не может стать семейством подтипа; семейство с подтипами
не меняет стратегию (иначе их расчёт поменялся бы молча) — нужен новый тип; смена стратегии у семейства с пользователями
показывает предупреждение и число затронутых объектов. **Статус:** принято.

## D-135. Песочница «Проверить на ударе» (ч.5 §6.5)
`HitSandbox` (Editor) строит одноразовую `GameSimulation` на пустом поле 7 × 7: цель в центре, атакующий рядом (или в трёх
гексах), враги и союзники цели на соседних гексах; здоровье цели выставляется прямым уроном до удара. Удар — тот же
`DamageResolver`, с трассировкой (`DamageResolver.Trace`, `RuleCheck`: применено / другой тип / тег / нет R / R ниже порога
/ здоровье не ниже / перезарядка / иммунитет / нечего делать). Для правила — второй прогон без него. Черновики редакторов
передаются как есть; библиотека, файлы и матч не затрагиваются (проверено тестом по `ContentLibrary.Version`). **Статус:**
принято.

## D-136. Инспектор юнита секциями (ч.5 §7.1)
Секции «Основное», «Атака и навыки», «Сопротивления», «Дополнительно»; открыта одна (по умолчанию «Основное»), заголовки
закрытых — одна строка резюме. Название и описание — в общей шапке редактора. Сценарии автоматизации, обращающиеся к
элементу закрытой секции, сначала раскрывают её через `IContentEditor.Reveal` (не более нескольких кадров ожидания; если
элемента нет — проверка проваливается), поэтому старые сценарии v0.17–v0.23 идут без изменений шагов. **Статус:** принято.

## D-137. Короткая таблица и поиск (ч.5 §7.2, §7.5)
Без поиска видны: «все типы», встроенные семейства (`core.*`), любые строки с значением (своим или из набора), подтипы
раскрытого семейства. Свои типы и нулевые подтипы скрыты и посчитаны. Поиск (название, ID, тег, название семейства)
показывает только совпадения и семейства вокруг совпавших подтипов; «Показать все» — всё, кроме служебных типов без
значения. Чистый (и любой `true_like`) — строка без числа со ссылкой на правила. **Статус:** принято.

## D-138. Правило поверх юнита (ч.5 §7.3)
«Добавить правило» → шаблон: новое правило (ID пользователя, имя «<юнит>: <шаблон>») открывается во вложенном редакторе;
сохранено — юнит ссылается на него; не сохранено — юнит не меняется. «Изменить копию»: копия с новым ID, юнит заменяет
ссылку на том же месте одним шагом отмены; общее правило не меняется. Несохранённые правки юнита на время вложенного
редактора сохраняются в его модели (узел откладывается, не уничтожается). **Статус:** принято.

## D-139. Отладка защиты тестового запуска (ч.5 §7.4)
Только в `GameMode` с `isTest` (запуск «▶ Тест» из редактора): кнопка «Отладка защиты (тест)», по умолчанию выключена; при
включении карточка юнита дополняется блоком «⚙ ОТЛАДКА ЗАЩИТЫ (только тест из редактора)» — R по ключам, правила с
приоритетом, щиты (текущая/полная), множитель лечения. В обычной игре кнопки и блока нет (проверка `expect:control`).
Это разделение режимов интерфейса, а не защита файлов. **Статус:** принято.

## D-140. Длинный текст не расширяет панели (v0.24.1)
Подписи переменной длины в верхних панелях (заголовок объекта, строка состояния каталога и редактора) обрезаются
многоточием с подсказкой, описание категории над списком переносится. Ширина панелей задаётся окном, а не текстом, поэтому
кнопки справа доступны при любом размере окна от 1280 px. Регрессия проверяет это шагом `expect:on-screen`. **Статус:** принято.

## D-141. Этапы до D0 — точка для стихий (ч.5 §13.4)
`IDamageStage` (Simulation): `Name`, `Apply(DamageEvent, GameState) → DamageEvent`; список `SimulationSettings.PreDamageStages`
исполняется в `DamageResolver` для каждого события (и реактивного) до заморозки D0 — до иммунитета, конверсий и R. По
умолчанию список пуст: в этой редакции этапов нет, поэтому поведение и числа не меняются, и в интерфейсе ничего не
появляется. Будущая часть о стихиях регистрирует здесь взаимодействия элементов, «Механики» получают раздел через реестр
категорий (группа `mechanics`), сопротивления — группу через семейства и теги. **Статус:** принято.

## D-142. Завершение плана части 5 (v0.25.0)
План ТЗ ч.5 §12 выполнен версиями v0.21.0–v0.25.0 (и исправлением v0.24.1). Каждый пункт приёмки §11 привязан к тесту или
шагу сценария (`docs/ACCEPTANCE_PART5.md`); UX-испытание пяти юнитов — `docs/UX_TRIALS.md`. Неопределённое ТЗ (§13.3:
стихии, криты, уклонение, позиционные бонусы…) не вводилось. **Статус:** принято.

## D-143. Версии для ТЗ части 6
ТЗ ч.6 §13 предлагает v0.23.0–v0.28.0, но эти номера уже выпущены (ч.5) и неизменяемы. Строки плана реализуются следующими
версиями: v0.26.0 — единый реестр определений, реактивная доставка новых определений во все совместимые редакторы,
типизированные фильтры селекторов, анализ зависимостей при удалении (отмена / замена ссылок / архивация), создание типа
прямо из селектора без перезапуска; v0.27.0 — защита A по всем/семействам/типам, пробитие A, формула K/(K+A) в общем
`DamageResolver` после R и до плоского снижения, миграция A = 0, тестовый стенд; v0.28.0 — единый движок модификаторов и
индивидуальные пассивы (характеристики, исходящий/входящий урон, R/A, ограничители, «откуда взялось»); v0.29.0 — дерево
видов, общие теги, наследование/конфликты/группы, подсчёт стаи по `packId`; v0.30.0 — `combat_ruleset`, шесть секторов
внезапности, детерминированные броски, крит и сверхкрит, AoE/серии; v0.31.0 — полный редактор с шаблонами, предпросмотром,
импортом/экспортом зависимостей, миграции и сквозная регрессия UX. По постоянному правилу (ТЗ ч.4 §9.3, ч.6 §2.5) каждая
механика появляется сразу с исполнением, редактором, схемой, импортом/экспортом и тестами. **Статус:** принято.

## D-144. Единый реестр определений (ч.6 §2.1–2.3)
Отдельного второго реестра не создаётся: `ContentTypeRegistry` (виды, схемы, миграции, реестры эффектов и действий) и
`ContentLibrary` (объекты встроенного и пользовательского источников по `kind + id`) уже образуют единый реестр с устойчивыми
ID. Добавлено событие `ContentLibrary.Changed`: его вызывает каждое изменение библиотеки (тот же счётчик `Version`, что
раньше), открытые редакторы подписаны и перестраивают свои списки, не трогая черновик. Подписка снимается при удалении
редактора. **Статус:** принято.

## D-145. Каталог ссылок и типизированные фильтры (ч.6 §2.2)
`ReferenceCatalog.Options(library, kind, filter, current, allowCreate)` — единственный источник вариантов для полей-ссылок
(инспектор, конструкторы, таблица R, песочница). Фильтр задаётся в схеме поля (`FieldSchema.RefFilter`): `Any`, `Family`
(только семейства), `Subtype` (только подтипы), `ResistanceAffected` (только учитывающие R — например «сопротивление к» у
баффа/дебаффа). Служебные (`legacy`) и архивные объекты не предлагаются, но остаются в списке, если уже выбраны, — значение
поля никогда не теряется из-за фильтра. Группы — по семействам; свой тип подписан «(свой)», элемент — «· элемент».
**Статус:** принято.

## D-146. Создание из селектора (ч.6 §2.4)
Пункт «＋ Новый тип урона…» есть только там, где новый объект можно сразу настроить без потери контекста (поля типа урона в

ссылок пункта пока нет (`ReferenceCatalog.CanCreate`). **Статус:** принято.

## D-147. Классификация типа урона (ч.6 §10.2)
`damage_type.classification` — список меток (до 8, 1–32 символа); первая и единственная предопределённая метка — `element`
(«элемент»). Она влияет только на подпись и группировку в списках; формулы, R и правила защиты её не читают. Стихийной

## D-148. Удаление используемого объекта: замена или архив (ч.6 §2.5)
Удаление объекта с пользователями по-прежнему запрещено библиотекой; редактор предлагает два безопасных пути.
**Замена ссылок** (`ContentLibrary.ReplaceReferences`): во всех пользователях ссылка переписывается на выбранный объект того
же вида (у типов урона — той же стратегии: замена не меняет смысл расчёта на «чистый» или обратно), сохранение всех
пользователей транзакционно — при ошибке любого все возвращаются; затем объект удаляется; одна отмена возвращает объект и
прежние версии пользователей. **Архив** (`archived: true` в оболочке): объект остаётся рабочим для существующих ссылок,
скрыт в новых выборах и помечен «🗄» в каталоге; проверка пользователей даёт замечание (не ошибку). **Статус:** принято.

## D-149. Неизвестные поля (ч.6 §2.3, §10.4)
Поля оболочки и `data`, которых эта версия не знает, при чтении сохраняются как есть (`ContentItem.ExtraEnvelope/ExtraData`)
с замечанием и записываются обратно при сохранении, не перекрывая известные поля. Они ничего не исполняют: обработчик
выбирается только по известным полям. Это защищает данные, созданные более новой версией игры, от молчаливой потери.
**Статус:** принято.

## D-151. Защита A — одна стадия расчёта (ч.6 §3, §8)
`ArmorSet` (Core) хранит A по ключам `global` / семейство / тип, как `ResistanceSet`; `ArmorMath.Raw` складывает слои
типа (у семейства — без слоя подтипа, один профиль не применяется дважды) и временные статусы `Stats.Armor` с ключом слоя;
`Effective = max(0, max(0, raw) − flat) × (1 − clamp(%, 0, 100)/100)`; `Multiplier = K / (K + A_eff)`, при A_eff = 0 — ровно
1. В `DamageResolver` стадия стоит сразу после R и до плоского снижения/предела (§8, стадия 7): конверсии по-прежнему берут
долю D0 до R и A, щиты — остаток после. Чистые типы (`true_like`) обходят A и её пробитие, как R. `DamageResult` хранит
`ArmorRaw`, `Armor`, `DefenseK`, `AfterArmor` — песочница показывает стадию отдельно от R. Нет промежуточного округления.
Значения A — очки 0…1 000 000; ввод «25 %» отклоняется (проценты — сопротивление). **Статус:** принято.

## D-152. Правила боя и K (ч.6 §3.2, §9.5, §10.3)
Новый вид `combat_ruleset` (группа «Механики»): `defenseK` (PROTOTYPE_DEFAULT 100, 0,01…1 000 000) и `defenseKByFamily`
(только семейства, учитывающие R). Встроенные `core.ruleset.standard` и `core.ruleset.legacy` (`legacy_combat_ruleset` ТЗ):
сейчас у обоих K = 100; в v0.30.0 у совместимых останутся выключены внезапность и крит. Карта ссылается на правила полем
`combatRuleset`; пустое — совместимые (так играют все карты до v0.27.0), новая карта из редактора получает стандартные.
`RuntimeFactory.BuildGame` передаёт правила в `SimulationSettings.CombatRules`; отсутствующие правила — предупреждение и
значения по умолчанию. Со сценариями части 7 (v0.34.0) главнее станет ссылка сценария (D-150). **Статус:** принято.

## D-153. A в профилях и интерфейсе (ч.6 §3.2, §9.1, §9.4)
A не получила отдельного вида профилей: `resistance_profile` хранит обе таблицы (`values` — R, `armor` — A) с одной основой
и одним порядком наслоения, категория называется «Профили защиты и сопротивлений» (ID вида не меняется). В редакторах одна
строка таблицы — пара полей «R, % | A» (`Inspector.PairText`), подсказка показывает источник и итог обоих. «Сохранить как
набор» и «Копировать защиту» переносят R и A вместе. A на чистом типе — предупреждение «значение не действует», свой K для
подтипа или обходящего семейства — ошибка. **Статус:** принято.

## D-154. Пассивы — данные юнита, исполняет один движок (ч.6 §4.1–4.2)
Пассив — `PassiveData` в `UnitData.Passives` (до 16): операция из реестра `PassiveOperations` (ID операции, поля,
диапазон, шаблон и подсказка), параметры и необязательное условие «пока здоровье ниже N %» (только у модификаторов урона —
их проверяют в момент удара). Неизвестная операция — ошибка проверки, пассив не действует (P6-08). Переиспользуемые общие
наборы появятся тегами и видами (v0.29.0) с теми же операциями. Исполняет `Content/Runtime/PassiveEffects` — единственное
место: `RuntimeFactory.BuildUnit` получает из него характеристики, R, A, правила и модификаторы урона, редактор — те же
значения и «откуда взялось». Характеристики: `база × (1 + Σ%/100) + Σчисло` (сначала проценты от базы, потом числа),
затем безопасные пределы (здоровье ≥ 1, скорости ≥ 0,1, сила ≥ 0); A слоя — так же и не ниже 0; R слоя — `+ Σ п.п.`.
Повтор одного ID пассива не удваивает эффект. В бою пассивы не меняют определения (P6-31). **Статус:** принято.

## D-155. Модификаторы урона и группы (ч.6 §4.2–4.3, §8)
`DamageModifier` (Core) — постоянный процентный модификатор: `Outgoing` действует при формировании D0 (§8, стадия 2, до
этапов `IDamageStage` и конверсий) только у первичной обычной атаки или навыка живого источника; `Incoming` — после R, A и
плоского снижения, до предела урона и щитов (стадия 8). Фильтр: тип или семейство (с подтипами); пусто — все типы для
исходящих и все сопротивляемые для входящих (чистый урон снижается только явным фильтром, как он обходит R и A).
`ModifierMath.DamageMultiplier`: проценты одной группы складываются, группы перемножаются, каждая группа не ниже ×0.
Стандартные группы — `outgoing` и `incoming` (пример ТЗ «−50 % −25 % = −75 %»); своя группа задаётся полем пассива.
`DamageResult` хранит `BaseAmount`, `OutgoingMultiplier`, `AfterFlat`, `IncomingMultiplier` и источники — песочница
показывает их отдельными стадиями. **Статус:** принято.

## D-156. «Особенности» в редакторе юнита (ч.6 §4.1, §9.2)
Пятая секция редактора юнита «Особенности» (по ТЗ — область «Особенности: теги + пассивы»; теги добавятся в v0.29.0):
карточки, шаблон + «＋ Добавить пассив», поля только своей операции. «Откуда взялось» — раздел предпросмотра (база, итог,
каждый источник; группы урона с итоговым множителем). Песочница получила выбор атакующего; в редакторе юнита — «этот юнит
бьёт пустую цель» для проверки его исходящих пассивов без сохранения. **Статус:** принято.

## D-157. Происхождение: виды и теги (ч.6 §5.1–5.3, §5.6, §9.1)
Вид (`species`) — узел дерева: один `parent`, эффекты списком `PassiveData` (тех же операций, что пассивы). `PassiveEffects`
собирает эффекты от корня к виду юнита по ключу эффекта (`id`): одноимённый эффект потомка заменяет эффект предка
(`replace`), отключает его (`disable`) или действует вместе (`stack`); поэтому предок никогда не применяется дважды.
Тег (`trait`) — общая особенность: категория, эффекты, `allowedSpecies` (с потомками), `requiredTraits`, `excludedTraits`,
`exclusiveGroup` + `conflictPolicy` (`error` — ошибка проверки юнита; `replace` — действует последний; `highest_priority` —
старший), `stackPolicy` (`unique` — один раз; `stack` — до `maxStacks`). Порядок источников: вид → теги → личные пассивы.
Проверки: цикл и глубина дерева, теги юнита (допустимый вид, обязательные/несовместимые, конфликт группы). Группа
каталога `origin` («Происхождение и теги») показывается как «Механики» — общий код групп. **Статус:** принято.

## D-158. Реестр характеристик (ч.6 §5.7)
Исполняемые характеристики (сила атаки, здоровье, скорость, темп атак) остаются полями юнита; новые числа — вид `unit_stat`
(единица, база, диапазон, знаки). Встроенная «Ловкость» — база 100 (PROTOTYPE_DEFAULT). Юнит может иметь свою базу
(`stats`). Пассивы и теги меняют любую характеристику реестра (база × (1 + %) + число, затем диапазон и округление).
Ни одна механика этой редакции не читает характеристики реестра, поэтому они не меняют бой (P6-32): влияние появится только
вместе с правилом, которое явно его задаёт. **Статус:** принято.

## D-159. Стая и «за каждого союзника» (ч.6 §5.5)
Операция `count_matching_units`: характеристика (только сила атаки, скорость движения, темп атак — их читает бой; здоровье
не меняется динамически), процент за юнита, вид (с потомками, через линию вида юнита `UnitStats.Species`), та же стая
(`packId` из определения юнита), себя, радиус, предел. `PackSystem` — первая система тика: пересчёт только при изменении
`GameState.RosterVersion` (появление, гибель) или, если есть радиус, занятости клеток; также сразу при появлении юнита (и на
паузе). Бонус хранится в `UnitState.PackPercent` и входит в `StatModifiers.Effective` вместе с процентами статусов —
определение юнита не меняется. **Статус:** принято.

## D-160. Внезапный удар по стороне цели (ч.6 §6)
Сторона считается в Core (`SurpriseMath.Sector`) по геометрии гексов: направление от **логической** клетки цели к логической
клетке атакующего на тике попадания — ближайшее из шести (`HexDirections.Toward`, скалярное произведение на плоскости;
ничья — первое направление в порядке N, NE, SE, S, SW, NW), затем смещение относительно **логического** взгляда цели
`UnitState.Facing` (не анимации): 0 — спереди, 1 — передний правый фланг, 2 — задний правый, 3 — сзади, 4 — задний левый,
5 — передний левый (по часовой). Шанс берётся из правил боя (`SurpriseChance[6]`, ограничен 0…100 %), успех даёт
`SurpriseMultiplier`. Внезапность возможна только у первичного удара обычной атаки или навыка с живым источником, отличным от
цели; отражение (`Reactive`), поверхность, периодический урон и удар без источника/направления — никогда (§6.2). Защитник не
поворачивается к атакующему перед проверкой. «Сзади 100 %» — явное предположение ТЗ ч.6 §6.1 (противоречие «0 % сзади» в §1.2).
Пресет симметричен: в редакторе правка флангового значения зеркалит его на другую сторону, пока не включено «Разные
левый/правый». Исключение «неуязвим к внезапному удару» — операция эффекта `surprise_immunity` (пассив, вид, тег);
«разрешённые типы атак» — флажок `canSurprise` эффекта урона навыка. Остальные исключения §6.4 («игнорирует направление»,
«бонус только для ближнего боя», порядок модификаторов, дополнительный эффект) в v0.30.0 не реализованы — их место в полном
редакторе v0.31.0. **Статус:** принято.

## D-161. Крит и сверхкрит (ч.6 §7)
Итоговый шанс C = max(0, `BaseCritChance` правил + `critChance` юнита + Σ `crit_chance_delta_pp` его вида, тегов и пассивов)
в процентных пунктах. Ступени (`CritMath`): P(сверхкрит) = clamp((C − 100) / 100, 0, 1), P(только крит) = clamp(C / 100,
0, 1) − P(сверхкрит); один бросок r ∈ [0, 1): r < P(сверхкрит) → сверхкрит, иначе r < P(сверхкрит) + P(крит) → крит. Две
ступени, третьей нет; избыток сверх 200 хранится и показывается («лишние 50 п.п. пока не дают эффекта: максимум —
сверхкрит»). Обычная атака критует всегда (при включённых правилах); навык — только с `canCrit` у эффекта урона (серия:
`critRoll` `per_hit` / `per_series`; область: `critTargets` `per_target` / `shared`); поверхность, периодический урон,
отражение, лечение и щиты не критуют. `crit_immunity` цели отключает крит. Стадия 1b `DamageResolver` — после исходящих
пассивов (1a), до зарегистрированных стадий (1c) и D0: D0 = база × пассивы × внезапность × крит (20 × 1,5 × 2,25 = 67,5,
P6-42), затем конверсии, R, A, плоское снижение, входящие пассивы. Компоненты смешанного удара — отдельные события с одним
ключом броска: один исход на удар, множитель применяется к каждому компоненту ровно один раз. **Статус:** принято.

## D-162. Детерминированные броски (ч.6 §6.3, §7.2, P6-44)
Генератора с состоянием нет: `DeterministicRoll.Of(seed, key, purpose)` — FNV-1a 64 по строке «seed|purpose|key» с
перемешиванием, верхние 53 бита → [0, 1). `seed` — `SimulationSettings.Seed`; `purpose` — `surprise` или `crit` (броски
независимы); `key` — ключ попадания: обычная атака `atk:{атакующий}:{номер удара}:{цель}`, навык
`skill:{действие}:{попадание | s}:{цель | all}`. Поэтому пауза, наведение стрелки, камера, FPS, перерисовка и предпросмотр не
тратят и не меняют бросков: бросок существует только у фактического события попадания, и тот же бой даёт те же числа.
Песочница разработчика может **задать** исход (`ForcedSurprise`, `ForcedCrit`) для доказуемой проверки — в матче этого
пути нет. **Статус:** принято.

## D-163. Совместимость правил боя v0.30.0 (ч.6 §10.3, P6-46)
Новый набор `combat_ruleset` создаётся с выключенными внезапностью и критами — автор включает их явно. Встроенный
`core.ruleset.standard` (новые карты) включает их с пресетом 0/25/75/100/75/25, ×1,5, крит ×1,5, сверхкрит ×2,25;
`core.ruleset.legacy` — выключены. Миграции: правила схемы 1 → 2 — выключены (прежние числа); карта схемы 1, выбравшая
`core.ruleset.standard` в v0.27–v0.29, → `core.ruleset.legacy` (иначе её бой молча получил бы броски). Юниты 7 → 8 —
`critChance: 0`. Шансы, стороны и броски видны только в режиме разработчика (правила боя, «В бою», песочница); карточка
юнита в режиме «Играть» их не показывает. Редактор v0.30.0 задаёт шесть шансов полями (пары флангов или все шесть) и
показывает формульную таблицу; визуальный шестиугольник секторов и наглядный тест на 1000 бросков (§9.5) входят в полный
редактор v0.31.0. **Статус:** принято.

## D-164. Длинный регрессионный сценарий и командная строка Windows
Сценарий v0.30.0 (33 854 символа) длиннее предела командной строки Windows (32 767 символов на всю строку), поэтому первая

## D-166. Исключения внезапности (ч.6 §6.3 п.2, §6.4)

## D-168. Завершение части 6: юнит, теги, игра, пакеты (ч.6 §9.2, §10.3, P6-47…P6-55)

Версии определений в пакете (§10.3): при импорте объект с тем же ID и другим содержимым — конфликт с выбором «пропустить»
(оставить текущую версию), «заменить» (взять версию пакета, с резервной копией) или «копией» (зафиксировать версию пакета

число) или считают юнитов, ни одна не читает итог той же характеристики. Часть 6 закрыта; следующая — часть 7 с v0.32.0
(D-150). **Статус:** принято.

## D-169. Строка каталога ниже края окна в автоматизации

щёлкает сам. Сборку и тег v0.31.0 не меняем: в `$PersistenceScenarioV31` перед выбором «Убийцы» список сужается поиском

зрения, щелчок выполняется в следующем кадре по уже прокрученной позиции. **Статус:** принято.

## D-170. Автоатака включается картой (ч.7 §8, §10, M7-55, M7-56)
Юнит получил `basicAttack` (ссылка на `basic_attack`, по умолчанию встроенная `core.basic_attack.front` — один передний гекс)
и `autoAttackEnabled` (по умолчанию — да, «стандартный боевой юнит», ч.7 §8.2); миграция юнитов 8 → 9 ставит ровно это и не
трогает уже заданные значения (идемпотентно). Но включить автоатаку на всех старых картах значило бы молча поменять каждый
прежний бой: юниты рядом с врагами начали бы бить сами, и все сценарии частей 1–6 разошлись бы с проверенными числами. Поэтому,
как с совместимыми правилами боя части 6, действие разрешает **карта**: необязательное поле `autoAttacks` (пишется только
когда включено; нет поля — выключено) и флажок «Автоатака юнитов» в редакторе карт. Старые и встроенные карты (прототип)

## D-171. Исполнение базовой атаки (ч.7 §8.2–8.4)
`BasicAttackDefinition` (Core): клетки — осевые смещения для взгляда на север (как у навыков), поворот `RotateFor(facing)`;
приоритет `nearest` (расстояние, затем порядок клеток, затем id) / `lowest_hp` / `pattern_order`; 1…6 целей за удар, каждая
со своим ключом броска `auto:{юнит}:{удар}:{цель}`; сила — % силы атаки юнита; тип — свой или тип обычной атаки; флажки крита,
внезапности и «в движении». `AttackSystem`: без явного `AttackTargetOrder` юнит бьёт только врагов в своей повёрнутой области,
сам не поворачивается и не идёт к ним; таймер `AutoTimer` копит игровое время, пока в области есть враг (первый удар — через
полный интервал `1 / AttackRate`), без врага обнуляется — удар не тратится впустую; на паузе системы не тикают — нет
«догоняющих» ударов. При явном приказе темп ведёт приказ, `AutoTimer` обнуляется — без бесплатного лишнего удара (M7-47).
Пока идёт навык, обычных атак нет (как в части 3). Не больше `MaxHitsPerTick` = 4 ударов за тик, остаток не копится сверх
интервала. Цель, умершая на этом тике, повторно не выбирается. Не сделано в v0.32.0: приоритет `first_along_route` (нужны
маршруты, v0.35.0) и линия видимости (в игре нет преград для атак) — эти настройки не показываются, пока нет исполнения.
Редактор: «Механики» → «Базовые атаки» (гекс-поле радиуса 4 с юнитом и указателем взгляда, щелчок — гекс в область или из
неё, поворот поля Q/E), у юнита в «Атака и навыки» — «Автоатака включена», «Базовая атака» и строка «В бою» «Базовая
атака: 3 удар/с · передний гекс · 1 враг · 10 урона до защиты». Шаг автоматизации `row:` теперь прокручивает список и
щёлкает в следующем кадре (D-169). **Статус:** принято.

## D-172. Блок — характеристика реестра (ч.7 §7.1, §7.4, §10)
`BlockCapacity` — встроенная характеристика `core.stat.block` («Блок», база 0, 0…1000, целые) общего реестра `unit_stat`
(ч.6 §5.7): своё значение юнита хранится в `stats` (как «Ловкость»), пассивы и теги меняют её тем же движком модификаторов,
бафф/дебафф «блок» — целыми слотами на время. Отдельного поля `blockCapacity` и второй системы нет; схема юнита не меняется:
нет значения — 0 (у старых юнитов — 0, M7-55). В редакторе юнита — одно поле «Блок» в «Атака и навыки» (из «Особенностей»
убрано, чтобы не было двух мест для одного числа); строка «В бою»: «Блок: 2 — пока стоит, удерживает до 2 двигающихся врагов
на их гексах». Блок не защита A, не урон, не влияет на атаку. **Статус:** принято.

## D-173. Связи блока (ч.7 §7.2–7.3, §11.2, M7-36…M7-42, M7-57)
`BlockSystem` (вторая система тика, после стаи и до движения): в начале тика снимает недействительные связи — блокер или враг
погиб/убран, блокер получил приказ движения или идёт (блокирует только стоя), не соседи, стороны совпали, враг больше не идёт
(нет приказа); при ёмкости меньше числа связей отпускаются самые новые (затем больший id). Контакт решается в момент, когда
идущий юнит хотел бы начать следующий шаг (`MovementSystem.TryStartStep` → `HoldsBack`): соседний стоящий юнит другой стороны
со свободным слотом создаёт `BlockLink` — при нескольких выбирается меньший id (одно и то же решение при каждом запуске); враг
остаётся на своём гексе (состояние ожидания `Blocked`), два юнита в одном гексе невозможны. У врага не больше одного блокера;
принадлежность к линии маршрута отдельных слотов не даёт. Блок 0 — никаких связей, атаки не затронуты (лучник стреляет).
Действует во всех режимах для идущих юнитов противника обеих сторон; так как у всех юнитов, сделанных раньше, блок 0, прежние
бои не меняются. Отключение блока в правилах сценария — с `ScenarioDefinition` (v0.34.0). Настройки «Механики → Контакт и
блок» (дистанция, правило выбора) в этой версии не открываются: действуют значения выше (дистанция 1, меньший id, новые
отпускаются первыми) — без «мёртвых» полей. В игре над удержанным врагом — слово «блок»; числа ёмкости игроку не
показываются. **Статус:** принято.

## D-174. Сценарий — один вид контента `scenario` (ч.7 §2.1, §2.2, §9.1, §10)
`ScenarioDefinition` — вид `scenario` (папка `scenarios`, схема 1, категория каталога «Сценарии» сразу после «Карт»): режим
(`mode`), карта (`map`), правила боя (`ruleset`, пусто — правила карты), отряд игрока (`squad`, 1…5 юнитов библиотеки — карточки
нижней панели по порядку), враги на карте (`enemies`: юнит, гекс, взгляд), переключатели `autoAttacks`, `blocking`,
`startPaused` и ограничение времени `timeLimit` (0 — нет). Режимы — реестр `ScenarioData.Modes` с четырьмя карточками ч.7 §9.1;
выбрать можно только режим с исполнителем: в v0.34.0 — «Обычный бой» (`battle`), остальные показаны серыми с версией появления
(Tower Defense — v0.36.0, «Оборона» — v0.37.0, «Исследование» — v0.38.0), а данные с таким режимом получают ошибку проверки.
Ссылки сценария (карта, правила, все юниты отряда и врагов) — обычные `References()`: экспорт пакета берёт их зависимостями,
импорт копией переназначает (M7-54). Проверка в два уровня: данные (`Validate`: режим, отряд 1…5, хотя бы один враг в бою, два
врага на одном гексе, время 0…36000) и `RuntimeFactory.CheckScenario` с картой и юнитами (карта есть и без ошибок, у карты есть
гексы выставления, каждый враг — юнит библиотеки на существующем проходимом гексе, правила боя существуют). Сохранять можно
черновик с ошибками второго уровня (сценарий станет неисправным после правки карты), запустить — нельзя (M7-59). Маршруты,
источники, волны, объекты и ИИ добавятся полями схемы в своих версиях. Встроенный пример — «Учебный бой» (`core.scenario.training`,
три оперативника противника на прототипной карте; демонстрация, не баланс). **Статус:** принято.

## D-175. Цели обычного боя и состояния сценария (ч.7 §2.3, §3.2, §11.1 п.9, M7-02…M7-04)
`ObjectiveSystem` — последняя система тика; без правил сценария (свободная игра, тесты объектов) ничего не делает. Состояния
`Preparing → Running → Victory | Defeat`: первый идущий тик переводит подготовку в бой, часы сценария считают только время боя
(не паузу). Победа — живых врагов 0; поражение — нет живых юнитов игрока на карте и ни одной карточки, которую ещё можно
выставить (`AvailableInRoster`/`PlacementPreview`; выставленный без взгляда — уже юнит); дополнительное поражение — вышло время.
Проверка — один раз по подтверждённому состоянию тика, победа раньше поражения (последний враг и последний юнит игрока в одном
тике — победа). Итог логический: событие `ScenarioEnded`, симуляция сразу встаёт на паузу и снять её нельзя
(`GameSimulation.IsScenarioOver`), эффекты гибели итог не задерживают. «Подготовка» — пауза старта (`startPaused`, по умолчанию
включена): игрок выставляет отряд и задаёт маршруты, ничего не идёт до «Начать бой» (пробел); снятый флажок запускает бой сразу.
Пустая нижняя панель при ещё доступных карточках — не поражение (M7-03). **Статус:** принято.

## D-176. Запуск сценария (ч.7 §2.2, §3.1)
В стартовом меню — выбор «Сценарий» (по умолчанию «свободная игра на карте» — прежние карта и отряд, все старые сценарии
автоматизации `ui:menu.play` не меняются); в списке только сценарии без ошибок. `RuntimeFactory.BuildScenario` строит матч:
карта сценария, нижняя панель — ровно отряд сценария (три юнита — три карточки), враги стоят на своих гексах до начала, правила
боя сценария поверх правил карты, автоатака и блок — как в сценарии. Автоатака в сценарии по умолчанию включена (сценарий —
новый контент ч.7; переключатель карты из D-170 по-прежнему решает для свободной игры и тестов). Матч создаёт общий
`MatchFactory.Start(GameContent)` — им пользуются игра, «▶ Тест сценария» и автотесты, поэтому сценарий играется так, как
проверен. Над полем во время подготовки — «ПОДГОТОВКА · пробел — начать бой», в итоге — «ПОБЕДА» / «ПОРАЖЕНИЕ»; в панели слева —
цели простыми словами и число оставшихся врагов. Числа сопротивлений и защиты по-прежнему не показываются. **Статус:** принято.

## D-177. Редактор сценария (ч.7 §3.4, §9.2, §9.3)
Один экран общей оболочки редактора, разделы в порядке пути мастера ч.7 §9.3: «Тип сценария» (четыре карточки) → «Карта» →
«Враги на карте» → «Отряд игрока» → «Правила боя» → справа «Сценарий словами» и «Проверка»; «Проверить», «Сохранить», «▶ Тест
сценария» — в верхней строке. Посередине — сама карта сценария: ЛКМ по свободному проходимому гексу ставит врага выбранного
юнита (и выбирает его), ЛКМ по врагу выбирает, ПКМ убирает, Q / E поворачивают выбранного (без выбора — взгляд новых врагов),
Delete убирает, Esc снимает выбор; препятствие и пустота отказываются с причиной. Недопустимые после смены карты враги видны
серыми на красном и убираются одной отменяемой кнопкой. «✎ Открыть карту в редакторе» открывает общую карту поверх сценария
(встроенная сохраняется копией, и сценарий переходит на копию). Юниты выбираются из библиотеки, а не копией редактора юнита;
новый пользовательский юнит сразу есть в списках (реактивное обновление ч.6). Пошаговый мастер с автоскрытием шагов —
в v0.39.0 (план ч.7 §13), когда режимов с исполнителем станет больше одного. **Статус:** принято.

## D-178. Маршруты врагов и базы — данные карты (ч.7 §4.1, §4.3, §9.2, §10)
Геометрия маршрутов хранится в карте (`routes`), а привязки волн и жизни баз — в сценарии (v0.36.0): один маршрут карты
используют разные сценарии. Маршрут — устойчивый `id` (`route1`, `route2`…; не меняется при переименовании и перерисовке),
название, номер базы врага, номер базы игрока, упорядоченный список посещений `[col,row]` (повторы и пересечения — норма, не
множество координат) и `enabled`. Базы: гексы категорий «база врага» / «база игрока» получают номер `base` 1…9 (нет поля —
база 1), гексы одной стороны с одним номером образуют одну базу (`MapBase`), названия — `bases`; роль берётся из данных
типа гекса, не из цвета. Проверка `RouteCheck` использует ту же модель проходимости, что и движение (`TileState.IsWalkable`):
начало на своей базе врага, конец на своей базе игрока, каждая пара — один шаг на соседний гекс, каждый гекс существует и
проходим. Ограничений по высоте в модели движения нет (уровень — только вид гекса, ч.4), поэтому высота маршрут не
ограничивает. Типов передвижения («летает»/«ходит») в данных нет и выдумывать их нельзя (ч.7 §4.3 п.3), поэтому проверка
пока одна для всех юнитов; проверка каждого назначенного на линию типа врага (M7-14) появится с волнами (v0.36.0) тем же
`RouteCheck`. Уровни ошибок: структурные (повторный ID, несоседние посещения, номер базы вне 1…9) — ошибка данных; зависящие
от гексов (гекс под маршрутом удалён или закрыт, база исчезла) — предупреждение «маршрут … требует проверки» с номером шага и
гексом: карта остаётся пригодной для свободной игры, а сценарий с таким маршрутом не запустится (v0.36.0). **Статус:** принято.

## D-179. Прохождение маршрута (ч.7 §4.4, §11.2, M7-09, M7-10, M7-16)
Источник истины — `RouteProgress` юнита (маршрут и индекс достигнутого посещения). `MovementSystem` ведёт идущего по
маршруту строго к следующему посещению: без A*, без обхода и без перехода на пересекающуюся линию. Следующий гекс занят,
зарезервирован или закрыт — юнит ждёт на своём гексе (`WaitReason.RouteAhead`) и потом идёт с того же индекса, без пропусков
и повторов; блок (D-173) удерживает идущего по маршруту так же, как идущего по ТД (`UnitState.WantsToMove`). Плавная
траектория строится тем же `StepGeometry` с просмотром на одно посещение вперёд и не выходит за гексы маршрута. Последнее
посещение — событие `RouteFinished`; утечка в базу и жизни — с волнами (v0.36.0). Явный приказ (ТД) главнее маршрута; если
он увёл юнита с линии, маршрут снимается — возврата прыжком нет. `GameSimulation.SpawnOnRoute` ставит юнита на первое
посещение лицом ко второму; занятое начало — отказ (очереди спавна — v0.36.0). **Статус:** принято.

## D-180. Инструмент «Маршруты» редактора карт (ч.7 §4.2, M7-06…M7-13)
Один переключатель «〰 Маршруты» в верхней строке редактора карт; слева — список линий, карточка выбранной и одна кнопка
«Проверить маршруты»; инструмент удаления гексов на это время скрыт. ЛКМ по гексу базы врага начинает черновик (база игрока,
обычный гекс — отказ с подсказкой); дальше автор только ведёт курсор: клиент проходит по экранному отрезку между двумя
событиями мыши с шагом 4 пикселя и предлагает черновику каждый пересечённый гекс по порядку, модель принимает только соседа
(неоднозначный пропуск заполняется прямой линией гексов `HexCoord.LineTo`, без прыжков). Гекс вне области, пустое место или
непроходимый гекс останавливает черновик: последний верный участок остаётся, место подсвечивается красным, причина — в
панели. Вход на гекс базы игрока завершает маршрут одним отменяемым шагом («Новый маршрут «Маршрут 2»»). Backspace /
«⌫ Последний сегмент» снимает одно посещение, Esc / ПКМ отменяют только черновик. ЛКМ по линии выбирает маршрут (повторно —
следующий на этом гексе). Карточка: ID, название, откуда → куда, число посещений и повторов, «Включён», проблемы с гексами,
«Перерисовать» (новая линия заменяет посещения, ID и название остаются), «Копия», «Удалить» с подтверждением. Удаление
гексов называет маршруты, которые через них идут, но маршрут не удаляет. Отдельной кнопки «тест маршрута» нет: проверка
ходьбой — «▶ Тест карты» → «▶ Враг: …» (без дублирования игрового режима). Линии рисует `RouteLayer`: полоса с шевронами
направления и номером маршрута у начала, без теста глубины (поверх моделей), ниже стрелок приказов; разные линии чуть
разведены в стороны, черновик — оранжевый. В редакторе линии видны всегда. **Статус:** принято.

## D-181. Маршруты в игре (ч.7 §4.2 п.10, M7-15)
В бою линии маршрутов скрыты; в панели отладки — раздел «Маршруты врагов» (только у карт с маршрутами): «Показать линии
маршрутов» и «▶ Враг: «название»» — враг отладки встаёт в начало линии и проходит её. Маршрут с проблемами не запускается
(сообщение с первой проблемой). В карточке юнита — «идёт по маршруту «…»: гекс 3 из 12» / «пройден», ожидание — «следующий
гекс маршрута занят». В автоматизации шаг `routedraw` ведёт курсор по одному движению за кадр (Godot объединяет движения
мыши одного кадра), как рука. **Статус:** принято.

## D-182. Волны и расписание (ч.7 §4.5, §11.1 п.2–3, M7-17…M7-19, M7-25)
Волны и их группы хранятся в сценарии (`waves`), геометрия — в карте (D-178); группа ссылается на маршрут карты по его
устойчивому ID и на юнит библиотеки. Группа: число врагов (0…500, 0 — предупреждение), задержка первого, интервал (0 — «все
сразу», вход пропускает по одному), сдвиг группы, «включена». Волна: название, одно правило старта — «после окончания
предыдущей» (по умолчанию; для первой — от начала боя) + задержка, «в секунду боя», «через N с после начала предыдущей» —
поэтому расписание никогда не запускает волну дважды. Число врагов волны, маршрута и сценария только вычисляется. Время —
игровые секунды идущей симуляции: на паузе таймеры и очереди стоят, результат не зависит от частоты кадров (шаг 1/30 с).
`WaveSystem` — первая система тика (`Waves, Packs, Blocks, Movement, Skills, Attack, Tiles, Statuses, Objectives`): стартует
волны, ставит наступивших врагов в очередь входа их маршрута в фиксированном порядке (волна, группа, номер) и впускает из
каждой очереди не больше одного врага за тик, когда первый гекс маршрута свободен и не зарезервирован; ожидание не даёт
продвижения. Волна разрешена, когда все её враги впущены и ни одного из них нет на карте. Выключенная волна или группа
остаётся в данных, но не идёт и не считается; копия волны сохраняет маршруты и юнитов. **Статус:** принято.

## D-183. Жизни баз, утечки, победа и поражение (ч.7 §4.6, §11.2, M7-20…M7-24)
У каждой базы игрока — жизни (по умолчанию 20, PROTOTYPE_DEFAULT) и флаг «критическая». Утечка: враг, чей маршрут кончается
на его базе игрока, дошёл до последнего посещения — или стоит перед ним, когда гекс базы занят юнитом (достаточно последней
границы, входить в занятый гекс не нужно); середина маршрута через гекс базы утечку не даёт. Враг снимается с карты без гибели
(`GameState.RemoveFromMap`, событие `EnemyLeaked`), жизни теряет только его база — ровно 1 за врага (свойство «урон утечки» у
типа врага пока не вводится). Политика поражения выбирается явно: любая критическая база без жизней (по умолчанию), все базы
без жизней, общий запас жизней исчерпан. Поражение по жизням проверяется раньше победы; победа — все волны разрешены и на поле
нет врагов (в том числе стоявших с начала). Сценарий не запускается, если группа ссылается на отсутствующий, выключенный или
требующий проверки маршрут (ошибка с волной и группой, M7-24), если у карты нет базы игрока или нет волны с врагами.
Проверка «для каждого типа врага линии» (M7-14) выполняется той же моделью проходимости: типов передвижения в данных нет,
поэтому для всех типов результат одинаков (D-178). **Статус:** принято.

## D-184. Редактор Tower Defense и экран боя (ч.7 §4.5, §4.7, §9.3)
Режим «Tower Defense» в карточках сценария стал доступен. В редакторе сценария для него — разделы «Базы игрока» (жизни и
«критическая» для каждой базы карты), «Волны — врагов всего N» (список волн с суммами, «＋ Волна»), карточка выбранной волны
(название, старт, задержка/секунда, «Включена», «Копия», ↑, ↓, «Удалить») с группами (маршрут карты, юнит, число, первый через,
интервал, сдвиг, «включена», «Убрать группу», «＋ Группа») и «Поражение, когда» в «Правилах боя»; на поле — красные линии
маршрутов карты. «Сценарий словами» — сумма по маршрутам, расписание волн словами и базы. Отдельной категории «Волны» в
каталоге нет: волны живут внутри сценария. В бою — «Волна 2 из 3 · впереди врагов · на поле», жизни каждой базы (или общий
запас), сообщения о начале волны и прорыве к базе, баннеры «ПОБЕДА · все волны пройдены» / «ПОРАЖЕНИЕ · база потеряла все
жизни». Числа сопротивлений и приоритеты ИИ игроку не показываются. **Статус:** принято.
