# Формат игрового контента HexTactics

Документ описывает объекты библиотеки контента (ТЗ ч.4 §8): как они хранятся, какие поля имеют и как проверяются.
Актуален для **v0.17.0** (схема данных `schemaVersion = 1` у всех видов). История схем — `docs/MIGRATIONS.md`.

## 1. Где лежит контент

| Источник | Путь | Изменяемость |
|---|---|---|
| Встроенный | `src/GodotClient/data/content/<папка>/<id>.json` (в сборке — `res://data/content`), список — `index.json` | только чтение; можно дублировать |
| Пользовательский | `user://content/<папка>/<id>.json` | создаётся и меняется в режиме «Разработчик» |

`user://` — папка данных пользователя Godot (Windows: `%APPDATA%\Godot\app_userdata\HexTactics`). Новые сборки игры её
не перезаписывают. Структура:

```text
user://content/maps|units|skills|tiles/<id>.json   сохранённые объекты
user://drafts/<папка>/<id>.json                    восстанавливаемые черновики редакторов
user://backups/<время>-<причина>/…                 копии перед заменой/миграцией
user://backups/deleted/<папка>/<id>.<время>.json   удалённые объекты (Ctrl+Z возвращает)
user://logs/content.log                            журнал удалений, восстановлений, копий, миграций
user://packs/                                      установленные пакеты (v0.20.0)
```

Для тестов и проверки сборки корень можно заменить аргументом `--hx-user-root=<папка>`.

## 2. Общая оболочка объекта

```json
{
  "schemaVersion": 1,
  "id": "skill_5f2c9a1b",
  "kind": "skill",
  "name": "Тройной рубящий удар",
  "description": "…",
  "revision": 3,
  "modified": "2026-11-07T12:00:00Z",
  "tags": [],
  "references": [ { "kind": "skill", "id": "core.skill.linear_strike" } ],
  "data": { … }
}
```

| Поле | Правило |
|---|---|
| `schemaVersion` | версия схемы `data` для этого вида; новее поддерживаемой — объект не загружается и **не меняется** на диске |
| `id` | устойчивый идентификатор: `a–z`, `0–9`, разделители `.` `_` `-`, 3–64 символа; не меняется при переименовании; имя файла = `id.json` |
| `kind` | `map` · `unit` · `skill` · `tile` (реестр `ContentTypeRegistry`) |
| `name`, `description` | название (1–100 символов) и описание (до 2000) |
| `revision` | номер сохранения, +1 при каждом сохранении |
| `modified` | время последнего сохранения (UTC) |
| `references` | ссылки на другие объекты по `kind + id`; при записи вычисляются из `data` (никогда не устаревают) |
| `data` | содержимое вида (ниже) |

Префикс `core.` зарезервирован за встроенным контентом; новые объекты получают ID вида `<kind>_<8 hex>`. JSON — UTF-8,
отступ 2 пробела, кириллица без экранирования, фиксированный порядок полей.

## 3. Виды объектов (`data`)

### 3.1. Тип гекса — `tile` (`tiles/`)

```json
{ "category": "ground", "passable": true, "level": 0, "color": "#CCCCCF", "effects": [] }
```

| Поле | Значения | По умолчанию |
|---|---|---|
| `category` | `ground` обычный · `obstacle` препятствие · `playerBase` база игрока · `enemyBase` база врага (метка) · `deploy` зона выставления · `spawn` край/зона появления | `ground` |
| `passable` | проходимость; препятствие — всегда `false`, базы и зоны — всегда `true` | `true` |
| `level` | уровень рельефа 0…3 — только вид (высота 0 / 0,18 / 0,36 / 0,55) | 0 |
| `color` | `#RRGGBB` | `#CCCCCF` |
| `effects` | эффекты типа гекса (периодические — с v0.19.0) | `[]` |

Роль в правилах: непроходимый → препятствие; иначе категория → база/зона/спавн/обычный (`RuntimeFactory.TypeOf`).

### 3.2. Карта — `map` (`maps/`)

```json
{
  "layout": "flat-top odd-q", "columns": 12, "rows": 10, "baseName": "База игрока",
  "zones": [ { "id": 1, "name": "Северный край" } ],
  "tiles": [ { "col": 0, "row": 0, "tile": "core.tile.ground" },
             { "col": 6, "row": 0, "tile": "core.tile.spawn", "zone": 1, "level": 1, "note": "…" } ]
}
```

- `columns × rows` — рабочая область (по умолчанию 12 × 10, до 32 по стороне). **Реально существуют только гексы из
  `tiles`**; остальные места пусты: непроходимы, не зона спавна, не цель ТД и не клетка эффекта.
- Гекс задаётся геометрической координатой odd-q `col,row` (не номером в списке); две записи на одной координате — ошибка.
- `tile` — ссылка на тип гекса; `level` — локальная высота (иначе — уровень типа); `zone` — номер зоны появления 1…9
  для гексов категории `spawn`; `note` — комментарий разработчика.
- `testPoints` (необязательно, с v0.16.0): `[{ "col": 3, "row": 4, "label": "A" }, …]` — тестовые точки на реальных гексах;
  проверка ищет проходимый маршрут A → B → … и предупреждает, если его нет.

### 3.3. Юнит — `unit` (`units/`)

```json
{ "maxHealth": 100, "moveSpeed": 1.0, "attackRate": 3.0, "attackPower": 10, "attackRange": 1,
  "skills": ["core.skill.linear_strike"], "side": "player", "color": "#4D80CC", "scale": 1.0 }
```

| Поле | Смысл | Диапазон | По умолчанию |
|---|---|---|---|
| `maxHealth` | максимум здоровья (текущее здоровье в бою хранится отдельно, дробное) | 1…100 000, целое | 100 |
| `moveSpeed` | скорость движения, гекс/с | 0,1…10 | 1,0 |
| `attackRate` | скорость обычной атаки, удар/с (не сила удара) | 0,1…20 | 3,0 |
| `attackPower` | сила атаки (Attack Power) — урон обычного удара и база навыков «% от атаки»; `PROTOTYPE_DEFAULT` | 0…10 000 | 10 |
| `attackRange` | дальность обычной атаки, гекс | 1…6 | 1 |
| `skills` | ссылки на навыки (до 8) | — | `[]` |
| `side` | `player` · `enemy` | — | `player` |
| `color`, `scale` | оттенок, размер модели (0,6…1,4) — только вид | — | `#4D80CC`, 1,0 |

### 3.4. Навык — `skill` (`skills/`)

```json
{ "icon": "✦", "anchor": "caster", "rotationMode": "facing", "baseEffects": [],
  "cells": [ { "q": 0, "r": -1, "color": "#2A2B36", "alpha": 0.28,
               "effects": [ { "type": "damage", "amount": 20, "targets": "enemies" } ] } ] }
```

- Клетки — смещения axial `q, r` от юнита **для взгляда на север** (`N` = `(0, −1)`); для остальных пяти направлений
  смещение поворачивается одной функцией `HexCoord.RotateFor` (поворот куба на k × 60° по часовой, без отражения).
  Клетка `(0, 0)` — сам юнит.
- `effects` клетки пусты → клетка наследует `baseEffects` навыка.
- `color`/`alpha` — пометка автора в редакторе; правила от цвета не зависят.
- Ограничения: до 64 клеток, до 6 гексов от юнита, до 8 эффектов на клетку, без повторов клеток.

### 3.5. Эффект

`{ "type": "<тип>", …параметры }` — тип из реестра `EffectTypeRegistry`, параметры — по схеме полей типа; не заданный
параметр берёт значение по умолчанию. Неизвестный тип — ошибка (объект не сохраняется и не исполняется).

| Тип | Где | Параметры (v0.15.0) |
|---|---|---|
| `damage` — урон | навык | `amount` HP за попадание (0…10 000, по умолчанию 10); `targets`: `enemies` · `allies` (свои, включая себя) · `self` · `all` |

Строки параметров никогда не исполняются как код: тип выбирает заранее реализованный обработчик `EffectResolver`.

## 4. Проверка

Объект с ошибками **не сохраняется**; файл с ошибками при загрузке остаётся на диске нетронутым и попадает в сообщения.

- Оболочка: повреждённый JSON, неизвестный вид, нет/новее версии схемы, неверный ID, файл больше 2 МБ.
- Значения: тип, диапазон, `NaN`/бесконечность, целые там, где нужны целые, цвет `#RRGGBB`, варианты выбора.
- Ссылки: каждая `kind + id` существует в библиотеке; циклы запрещены; удаление объекта, на который ссылаются, запрещено.
- Карта: дубли координат, гексы вне области, отсутствующие типы; замечания — спавн не на краю, нет мест выставления,
  область больше 16 × 12 (может не поместиться на экран).
- Конфликт ID (два файла с одним `id`), `core.`-ID в пользовательской папке — файл не загружается.

## 5. Как контент попадает в игру

`RuntimeFactory` превращает определения в модель Core: карта → `MapDefinition` (пустые места — `TileType.Void`, у гекса —
`TileId` и уровень), юнит → `UnitStats` и список навыков, навык → `SkillDefinition` (клетки с `EffectSpec`), тип гекса →
вид (`TileVisual`). «Играть» и тестовые запуски редакторов используют одну и ту же фабрику и одну симуляцию.

## 6. Постоянное правило расширения (ТЗ ч.4 §9.3)

> При создании **любой новой редактируемой механики** одновременно: (1) опиши её правила в актуальном ТЗ; (2) создай/расширь
> версионированную схему определения; (3) добавь проверку значений и миграцию старых данных; (4) подключи единый обработчик
> в симуляции; (5) зарегистрируй поля и предпросмотр в режиме разработчика; (6) обеспечь сохранение, импорт и экспорт;
> (7) добавь тест игрового действия, UI-редактирования, загрузки, совместимости и отката. Не добавляй новый игровой
> параметр, не дав создателю контента средства управлять им, кроме прямо обозначенных базовых алгоритмов. Новые категории
> добавляй через реестр, сохраняя уже существующие объекты и их стабильные ID.

Новый вид объектов — `ContentTypeRegistry.Register(new ContentKind { … })`; новый тип эффекта — дескриптор в
`EffectTypeRegistry` (поля, контексты) + `IEffectHandler` в `EffectResolver`. Тест `RegistryTests` требует, чтобы у каждого
зарегистрированного типа эффекта был обработчик в симуляции.
