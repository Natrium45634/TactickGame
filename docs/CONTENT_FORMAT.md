# Формат игрового контента HexTactics

Документ описывает объекты библиотеки контента (ТЗ ч.4 §8): как они хранятся, какие поля имеют и как проверяются.
Актуален для **v0.27.0** (схемы: `map` 1, `unit` 5, `skill` 2, `tile` 2, `damage_type` 1, `defense_rule` 1,
`resistance_profile` 2, `combat_ruleset` 1). История схем —
`docs/MIGRATIONS.md`.

## 1. Где лежит контент

| Источник | Путь | Изменяемость |
|---|---|---|
| Встроенный | `src/GodotClient/data/content/<папка>/<id>.json` (в сборке — `res://data/content`), список — `index.json` | только чтение; можно дублировать |
| Пользовательский | `user://content/<папка>/<id>.json` | создаётся и меняется в режиме «Разработчик» |

`user://` — папка данных пользователя Godot (Windows: `%APPDATA%\Godot\app_userdata\HexTactics`). Новые сборки игры её
не перезаписывают. Структура:

```text
user://content/maps|units|skills|tiles/<id>.json   сохранённые объекты
user://drafts/<папка>/<id>.json                    восстанавливаемые черновики редакторов
user://backups/<время>-<причина>/…                 копии перед заменой/миграцией
user://backups/deleted/<папка>/<id>.<время>.json   удалённые объекты (Ctrl+Z возвращает)
user://logs/content.log                            журнал удалений, восстановлений, копий, миграций
user://packs/                                      установленные пакеты (v0.20.0)
```

Для тестов и проверки сборки корень можно заменить аргументом `--hx-user-root=<папка>`.

## 2. Общая оболочка объекта

```json
{
  "schemaVersion": 1,
  "id": "skill_5f2c9a1b",
  "kind": "skill",
  "name": "Тройной рубящий удар",
  "description": "…",
  "revision": 3,
  "modified": "2026-11-07T12:00:00Z",
  "tags": [],
  "references": [ { "kind": "skill", "id": "core.skill.linear_strike" } ],
  "data": { … }
}
```

| Поле | Правило |
|---|---|
| `schemaVersion` | версия схемы `data` для этого вида; новее поддерживаемой — объект не загружается и **не меняется** на диске |
| `id` | устойчивый идентификатор: `a–z`, `0–9`, разделители `.` `_` `-`, 3–64 символа; не меняется при переименовании; имя файла = `id.json` |
| `kind` | `map` · `unit` · `skill` · `tile` (реестр `ContentTypeRegistry`) |
| `name`, `description` | название (1–100 символов) и описание (до 2000) |
| `revision` | номер сохранения, +1 при каждом сохранении |
| `modified` | время последнего сохранения (UTC) |
| `references` | ссылки на другие объекты по `kind + id`; при записи вычисляются из `data` (никогда не устаревают) |
| `archived` | необязательно (с v0.26.0): `true` — объект в архиве: существующие ссылки работают, в новых выборах он не предлагается (D-148) |
| `data` | содержимое вида (ниже) |

Поля оболочки и `data`, неизвестные этой версии (например, из файла более новой версии игры), загружаются с замечанием,
не действуют и при сохранении записываются обратно без изменений (с v0.26.0, D-149).

Префикс `core.` зарезервирован за встроенным контентом; новые объекты получают ID вида `<kind>_<8 hex>`. JSON — UTF-8,
отступ 2 пробела, кириллица без экранирования, фиксированный порядок полей.

## 3. Виды объектов (`data`)

### 3.1. Тип гекса — `tile` (`tiles/`)

```json
{ "category": "special", "passable": true, "waypoints": true, "level": 0, "color": "#E0805A", "icon": "♨",
  "effects": [ { "type": "periodic", "trigger": "stay", "kind": "damage", "perSecond": 5, "sides": "all" } ] }
```

| Поле | Значения | По умолчанию |
|---|---|---|
| `category` | `ground` обычный · `obstacle` препятствие · `playerBase` база игрока · `enemyBase` база врага (метка) · `deploy` зона выставления · `spawn` край/зона появления · `special` особый/поверхность (с v0.19.0) | `ground` |
| `passable` | проходимость; препятствие — всегда `false`, базы и зоны — всегда `true` | `true` |
| `waypoints` | можно ли ставить ТД/КТД на гексы типа (с v0.19.0); проходить можно всегда, если `passable` | `true` |
| `level` | уровень рельефа 0…3 — только вид (высота 0 / 0,18 / 0,36 / 0,55) | 0 |
| `color` | `#RRGGBB` | `#CCCCCF` |
| `icon` | значок на каждом гексе типа, до 4 символов (с v0.19.0) | `""` |
| `effects` | эффекты типа гекса с триггерами (с v0.19.0; см. §3.5), до 8 | `[]` |

Роль в правилах: непроходимый → препятствие; иначе категория → база/зона/спавн/обычный (`RuntimeFactory.TypeOf`).

### 3.2. Карта — `map` (`maps/`)

```json
{
  "layout": "flat-top odd-q", "columns": 12, "rows": 10, "baseName": "База игрока",
  "zones": [ { "id": 1, "name": "Северный край" } ],
  "tiles": [ { "col": 0, "row": 0, "tile": "core.tile.ground" },
             { "col": 6, "row": 0, "tile": "core.tile.spawn", "zone": 1, "level": 1, "note": "…" } ]
}
```

- `columns × rows` — рабочая область (по умолчанию 12 × 10, до 32 по стороне). **Реально существуют только гексы из
  `tiles`**; остальные места пусты: непроходимы, не зона спавна, не цель ТД и не клетка эффекта.
- Гекс задаётся геометрической координатой odd-q `col,row` (не номером в списке); две записи на одной координате — ошибка.
- `tile` — ссылка на тип гекса; `level` — локальная высота (иначе — уровень типа); `zone` — номер зоны появления 1…9
  для гексов категории `spawn`; `note` — комментарий разработчика.
- `testPoints` (необязательно, с v0.16.0): `[{ "col": 3, "row": 4, "label": "A" }, …]` — тестовые точки на реальных гексах;
  проверка ищет проходимый маршрут A → B → … и предупреждает, если его нет.
- `combatRuleset` (необязательно, с v0.27.0): ссылка на правила боя `combat_ruleset`. Нет поля — совместимые правила
  `core.ruleset.legacy` (так играют все карты, созданные раньше); новая карта из редактора получает `core.ruleset.standard`.

### 3.3. Юнит — `unit` (`units/`)

```json
{ "maxHealth": 100, "moveSpeed": 1.0, "attackRate": 3.0, "attackPower": 10, "attackRange": 1,
  "skills": ["core.skill.linear_strike"], "side": "player", "color": "#4D80CC", "scale": 1.0 }
```

| Поле | Смысл | Диапазон | По умолчанию |
|---|---|---|---|
| `maxHealth` | максимум здоровья (текущее здоровье в бою хранится отдельно, дробное) | 1…100 000, целое | 100 |
| `moveSpeed` | скорость движения, гекс/с | 0,1…10 | 1,0 |
| `attackRate` | скорость обычной атаки, удар/с (не сила удара) | 0,1…20 | 3,0 |
| `attackPower` | сила атаки (Attack Power) — урон обычного удара и база навыков «% от атаки»; `PROTOTYPE_DEFAULT` | 0…10 000 | 10 |
| `attackRange` | дальность обычной атаки, гекс | 1…6 | 1 |
| `skills` | ссылки на навыки (до 8) | — | `[]` |
| `side` | `player` · `enemy` | — | `player` |
| `color`, `scale` | оттенок, размер модели (0,6…1,4) — только вид | — | `#4D80CC`, 1,0 |

- С v0.21.0 (схема 2): `attackDamageType` — тип урона обычной атаки (по умолчанию `core.damage.physical`);
  `attackAreaRadius` 0…3 — область обычной атаки вокруг гекса цели (враги атакующего); `attackAreaSplit` — делить силу
  между целями области; `resistances` — объект «`global` или ID типа урона → сопротивление в %», −500…+500, шаг 0,01,
  отсутствующие = 0, например `{ "core.damage.physical": 50, "core.damage.piercing": -100 }` (итог колющего −50 %).
- С v0.22.0 (схема 3): `defenseRules` — ссылки на правила защиты (до 16, без повторов; порядок применения задаёт приоритет
  правила); `shields` — до 4 щитов `{ "name": "Барьер", "capacity": 30, "damageTypeId": "any", "order": 0 }`: название
  (уникальное, до 40 символов), прочность 0 < … ≤ 100 000 HP, принимаемый урон (`any`, тип или семейство — с подтипами),
  порядок 0–100 (меньше — тратится раньше). В бою щит начинается полным.
- С v0.23.0 (схема 4): `resistanceProfiles` — ссылки на наборы сопротивлений (до 8); значения наборов — основа (более поздний
  набор перекрывает ранний по ключу), `resistances` — свои значения юнита поверх них (явный 0 допустим).
- С v0.27.0 (схема 5): `armor` — защита A, «`global` или ID типа урона → очки», 0…1 000 000, шаг 0,01, отсутствующие = 0;
  наслаивается на A профилей так же, как `resistances`. В бою после сопротивления урон × K / (K + A), где
  A = все типы + семейство + подтип + временные изменения (итог ниже 0 — 0), K — из правил боя карты. Чистые типы A не
  учитывают (значение для них — предупреждение). `attackArmorPenetration` (очки, 0…1 000 000) и
  `attackArmorPenetrationPercent` (0…100 %) — пробитие A обычной атакой: сначала очки, затем доля оставшейся A; на R не
  влияют. Миграция 4 → 5: `armor: {}`, пробитие 0 — прежние числа урона.

### 3.4. Навык — `skill` (`skills/`)

```json
{ "icon": "✦", "anchor": "caster", "rotationMode": "facing",
  "baseEffects": [ { "type": "damage", "formula": "attack", "multiplier": 1.5, "hits": 3, "interval": 0.5, "targets": "enemies" } ],
  "cells": [ { "q": 0, "r": -1 },
             { "q": 0, "r": -2, "overrides": { "0": { "multiplier": 0.75 } } },
             { "q": -1, "r": 0, "color": "#D04040", "alpha": 0.55,
               "effects": [ { "type": "damage", "formula": "fixed", "amount": 7, "hits": 1, "interval": 0, "targets": "enemies" } ] } ] }
```

- Клетки — смещения axial `q, r` от юнита **для взгляда на север** (`N` = `(0, −1)`); для остальных пяти направлений
  смещение поворачивается одной функцией `HexCoord.RotateFor` (поворот куба на k × 60° по часовой, без отражения).
  Клетка `(0, 0)` — сам юнит.
- `effects` клетки пусты → клетка наследует `baseEffects` навыка; `overrides` (с v0.18.0, необязательно) — поля,
  которые клетка задаёт сама: ключ — индекс базового эффекта (строкой), значение — объект «поле → значение». Остальные
  поля берутся из базового эффекта. У клетки со своими `effects` переопределений нет.
- Пример выше — «Тройной удар»: при силе атаки 10 клетка `(0,−1)` — 3 попадания по 15 (45), `(0,−2)` — 3 по 7,5 (22,5),
  `(−1,0)` — 7.
- `color`/`alpha` — пометка автора в редакторе; правила от цвета не зависят.
- Ограничения: до 64 клеток, до 6 гексов от юнита, до 8 эффектов на клетку, без повторов клеток.

### 3.5. Эффект

`{ "type": "<тип>", …параметры }` — тип из реестра `EffectTypeRegistry`, параметры — по схеме полей типа; не заданный
параметр берёт значение по умолчанию. Неизвестный тип — ошибка (объект не сохраняется и не исполняется).

| Тип | Где | Параметры (v0.18.0) |
|---|---|---|
| `damage` — урон | навык | `formula`: `fixed` (`amount` HP за попадание, 0…10 000, по умолчанию 10) · `attack` (`multiplier` × сила атаки источника, 0…50, по умолчанию 1 = 100 %); `hits` 1…20 (1), `interval` 0…10 с (0); `targets` (`enemies`) |
| `heal` — лечение | навык | `formula`: `fixed` (`amount`) · `attack` · `maxHealth` (`multiplier` × сила атаки / максимум здоровья источника, 0,5); не выше максимума цели; `hits`, `interval`; `targets` (`allies`) |
| `buff` — бафф, `debuff` — дебафф | навык | `stat`: `moveSpeed` · `attackPower` · `attackRate`; `mode`: `percent` (`percent`, 0…10 = 0…1000 %, 0,3) · `fixed` (`delta` в единицах характеристики, 1); `duration` 0,1…600 с (5); `stacking`: `refresh` · `stack` · `replace` · `ignore` (`refresh`); `hits`, `interval`; `targets` (бафф — `allies`, дебафф — `enemies`) |
| `periodic` — периодический | навык | `kind`: `damage` · `heal`; `perSecond` HP/с (0…10 000, 5); `duration` (3); `stacking`; `targets` (`enemies`) |

`targets`: `enemies` — только враги источника · `allies` — союзники, включая самого источника · `self` — только источник ·
`all` — все. Числа дробные, без незаметного округления; на экране здоровье — до десятых.

Правила исполнения (D-101–D-103): попадания одного эффекта — моменты `0, interval, 2 × interval…`; цели клетки — на момент
каждого попадания; порядок в тике — время → попадание → клетка → эффект → цель. Бафф/дебафф меняет действующую
характеристику: база × (1 + Σ %) ± Σ фикс., не ниже безопасного минимума (скорость 0,1 гекс/с, скорость атак 0,1 удар/с,
сила атаки 0); по истечении значение возвращается. Повторное наложение того же эффекта того же источника: `refresh` —
обновить длительность, `stack` — ещё один экземпляр, `replace` — заменить, `ignore` — не накладывать. Периодический
действует непрерывно: `perSecond` × игровое время каждого тика (5 HP/с за 2 с — ровно 10). На паузе таймеры стоят.

**На типе гекса** (с v0.19.0) у эффектов свой набор полей (D-107): `trigger` — `stay` (пока юнит на гексе; только
`periodic`, без `duration`), `enter` (при входе, также при появлении на гексе), `exit` (при выходе); `sides` — `all` · `player` ·
`enemy`; урон и лечение — только `amount`; бафф/дебафф — `stat`, `mode`, `percent`/`delta`, `duration`, `stacking`;
периодический при `enter`/`exit` — статус на `duration`. Считается **логический** гекс юнита (D-108).

```json
"effects": [
  { "type": "periodic", "trigger": "stay", "kind": "damage", "perSecond": 5, "sides": "all" },
  { "type": "debuff", "trigger": "enter", "stat": "moveSpeed", "mode": "percent", "percent": 0.5, "duration": 3,
    "stacking": "refresh", "sides": "enemy" }
]
```

С v0.27.0 (без смены схемы навыка, поля необязательные): у `damage` — `armorPenetration` (очки, 0…1 000 000) и
`armorPenetrationPercent` (0…100) — пробитие защиты A, отдельно от `penetration` (пробитие R); у `buff`/`debuff` —
`stat: "armor"` (защита A) с `armorOf` (`global`, семейство или тип, учитывающий R) и `delta` в очках. Итог A с дебаффом
может быть отрицательным — в расчёте он 0.

Строки параметров никогда не исполняются как код: тип выбирает заранее реализованный обработчик `EffectResolver`.

### 3.7. Тип урона — `damage_type` (`damage_types/`, с v0.21.0)

```json
{ "family": "core.damage.magical", "strategy": "resistance_affected", "tags": ["fire"], "color": "#E8743B", "icon": "",
  "classification": ["element"] }
```

`family` — ID семейства (пусто — тип сам семейство); `strategy` — `resistance_affected` (учитывает R) или `true_like`
(обходит численные R и плоское снижение; иммунитет и щиты действуют); у подтипа стратегия семейства. `legacy: true` — тип
старого контента, в новых списках не предлагается. Встроенные: `core.damage.physical` (`piercing`, `slashing`, `blunt`),
`core.damage.magical` (пример подтипа — `core.damage.fire_example`, только демонстрация), `core.damage.true`; служебные
`core.damage.untyped`, `core.damage.direct`.

`classification` (с v0.26.0, необязательно) — до 8 меток по 1–32 символа; `element` — пользовательский элемент: подпись
«· элемент» и группировка в списках. На расчёт метки не влияют, отношений элементов нет (D-147). В списках выбора типы
сгруппированы по семействам; поля со ссылкой на тип несут фильтр (`Family`, `Subtype`, `ResistanceAffected`), служебные и
архивные типы не предлагаются, пока не выбраны (D-145).

### 3.8. Правило защиты — `defense_rule` (`defense_rules/`, с v0.22.0)

```json
{ "trigger": "on_hit_contact", "damageTypeId": "core.damage.fire_example", "damageTag": "",
  "minimumEffectiveResistancePercent": 300, "healthBelowPercent": null, "triggerOnImmuneContact": false,
  "priority": 100, "cooldownSeconds": 0, "maxTriggers": 0,
  "actions": [
    { "effect": "convert_to_healing", "fraction": 0.25, "recipient": "self" },
    { "effect": "redirect_as_damage", "fraction": 0.75, "targeting": "adjacent_hex_ring", "radiusHexes": 1,
      "includeCenter": false, "targetFilter": "enemies_of_defender", "targetDamageMode": "full_per_target",
      "responseDamageType": "same_as_incoming" } ] }
```

| Поле | Смысл |
|---|---|
| `trigger` | `on_hit_contact` — получен удар; `on_health_loss` — потеряно HP или прочность щита; `on_damage_dealt` — свой удар снял HP; `on_status_applied` — накладывается статус |
| `damageTypeId` | ID типа или семейства (семейство — со всеми подтипами) или `any` (любой, и чистый) |
| `damageTag` | дополнительно: у типа есть этот тег (пусто — не проверять) |
| `minimumEffectiveResistancePercent` | условие: R после пробития против удара ≥ порога (−500…500); `null` — нет; у чистого урона R нет — не выполняется; не для `on_damage_dealt` |
| `healthBelowPercent` | условие: здоровье владельца до удара < порога (1…100 %); `null` — нет |
| `triggerOnImmuneContact` | действовать и при иммунитете к удару (по умолчанию нет) |
| `priority`, `cooldownSeconds`, `maxTriggers` | меньше — раньше (0…1000, 100); игровые секунды между срабатываниями (0…600); срабатываний за бой (0 — без предела) |
| `actions` | 1…8 реакций `{ "effect": …, поля }` |

| `effect` | Когда | Поля |
|---|---|---|
| `immunity` — иммунитет к урону | удар | — |
| `negate` — поглотить долю | удар | `fraction` 0…1 (доля D0) |
| `convert_to_healing` — поглотить и лечиться | удар | `fraction`, `recipient`: `self` |
| `convert_to_shield` — поглотить в щит | удар | `fraction`, `shield` (название щита юнита) |
| `redirect_as_damage` — отразить часть урона | удар | `fraction`; `targeting`: `attacker` · `adjacent_hex_ring` (`radiusHexes` 1…3, `includeCenter`, `targetDamageMode`: `full_per_target` · `split_between_targets`); `targetFilter`: `enemies_of_defender` · `allies_of_defender` · `all_units`; `responseDamageType`: `same_as_incoming` или ID типа |
| `flat_reduction` — плоское снижение | удар | `amount` HP (после R, не для чистого) |
| `damage_cap` — предел урона за удар | удар | `amount` HP |
| `retaliate` — ответный удар | потеря HP | `fraction` 0…5 (доля потери), `base`: `health_loss` · `shield_loss`; поля целей как у отражения |
| `vampirism` — вампиризм | свой удар | `fraction` (доля снятого HP) |
| `status_immunity` — иммунитет к статусам | статус | `statusCategory`: `debuff` · `buff` · `periodic` · `all` |

- Сумма `fraction` поглощений и отражений одного правила ≤ 1 (100 % силы удара); реакция не к своему `trigger` — ошибка;
  `allowReactiveChain: true` — ошибка (ответ на ответ запрещён, ТЗ ч.5 §5.5). Иммунитет вместе с поглощением без
  `triggerOnImmuneContact` — предупреждение.
- Порядок в бою (D-127): иммунитет → поглощения/лечение/отражение из D0 по приоритету → R → плоское снижение → предел → щиты
  → HP → ответный удар, вампиризм. Ответные пакеты сами реакций не вызывают.
- Запрет лечения — дебафф характеристики `healingReceived` («получаемое лечение»): 100 % — лечение 0.

### 3.9. Набор сопротивлений — `resistance_profile` (`resistance_profiles/`, с v0.23.0)

```json
{ "parent": "core.profile.armored", "values": { "core.damage.magical": 60, "core.damage.blunt": -25 } }
```

`parent` — набор-основа (пусто — нет); `values` — «`global` или ID типа → R», −500…+500, шаг 0,01. Значения набора = основа,
перекрытая своими по ключу; цикл основ — ошибка. Встроенные примеры: `core.profile.armored` («Бронированный»),
`core.profile.weak_piercing` («Слаб к колющему»).

С v0.27.0 (схема 2) вид называется «Профили защиты и сопротивлений» и хранит ещё `armor` — «`global` или ID типа → A» в
очках 0…1 000 000 с той же основой и тем же наслоением, например `"armor": { "core.damage.physical": 100 }`. Миграция 1 → 2:
`armor: {}`.

### 3.10. Правила боя — `combat_ruleset` (`combat_rulesets/`, с v0.27.0)

```json
{ "defenseK": 100, "defenseKByFamily": { "core.damage.magical": 200 } }
```

`defenseK` — K формулы защиты `K / (K + A)` (больше 0, не больше 1 000 000; PROTOTYPE_DEFAULT 100: A = 100 — урон вдвое
меньше); `defenseKByFamily` — свой K для семейства (ключ — семейство, учитывающее R; подтип или чистое семейство — ошибка),
действует на его подтипы. Встроенные: `core.ruleset.standard` («Стандартные правила боя», новые карты) и
`core.ruleset.legacy` («Совместимые правила (старые карты)», карты без поля `combatRuleset`). Направление и криты добавятся
в этот же вид (v0.30.0).

## 3.6. Экспорт и импорт (с v0.20.0)

- **Один объект** — тот же JSON, что в библиотеке (оболочка §2 + `data`), UTF-8. Если объект ссылается на другие ваши объекты,
  файл **не самодостаточен**: при импорте в установку без них объект не установится (окно экспорта предупреждает).
- **Пакет `.hxp`** — ZIP:

```text
manifest.json
content/tiles/tile_7ea7ab67.json
content/maps/map_b321571d.json
content/skills/skill_88be7634.json
content/units/unit_49816844.json
```

```json
{ "format": "hextactics-package", "formatVersion": 1, "name": "Поверхности", "description": "…",
  "gameVersion": "0.20.0", "created": "2026-11-07T12:00:00Z",
  "objects": [ { "kind": "tile", "id": "tile_7ea7ab67", "name": "Жгучая поверхность", "revision": 1, "schemaVersion": 1,
                 "path": "content/tiles/tile_7ea7ab67.json", "sha256": "…", "bytes": 612 } ],
  "builtInDependencies": [ { "kind": "tile", "id": "core.tile.player_base" } ] }
```

- В пакете допускаются **только** `manifest.json` и JSON-объекты по путям `content/<папка вида>/<id>.json`, перечисленные в
  manifest с верной SHA-256. Пути — относительные, без `..`, `\`, `:`. Исполняемые файлы, библиотеки, скрипты не
  принимаются никогда.
- Пределы (D-117): пакет ≤ 32 МБ, ≤ 512 файлов, распаковка ≤ 64 МБ, объект ≤ 2 МБ; навык — не больше 1024 применений
  эффектов за использование. Файл `user://limits.json` может понизить пределы (целые от 1 до жёстких пределов), например
  `{ "maxPackageBytes": 4194304, "maxSkillHitEvents": 256 }`.
- Конфликт `kind + id` при импорте: пропустить (по умолчанию) / заменить с резервной копией / копией с новым ID (ссылки
  внутри пакета перепривязываются). Установка транзакционная.

## 4. Проверка

Объект с ошибками **не сохраняется**; файл с ошибками при загрузке остаётся на диске нетронутым и попадает в сообщения.

- Оболочка: повреждённый JSON, неизвестный вид, нет/новее версии схемы, неверный ID, файл больше 2 МБ.
- Значения: тип, диапазон, `NaN`/бесконечность, целые там, где нужны целые, цвет `#RRGGBB`, варианты выбора.
- Ссылки: каждая `kind + id` существует в библиотеке; циклы запрещены; удаление объекта, на который ссылаются, запрещено.
- Карта: дубли координат, гексы вне области, отсутствующие типы; замечания — спавн не на краю, нет мест выставления,
  область больше 16 × 12 (может не поместиться на экран).
- Конфликт ID (два файла с одним `id`), `core.`-ID в пользовательской папке — файл не загружается.

## 5. Как контент попадает в игру

`RuntimeFactory` превращает определения в модель Core: карта → `MapDefinition` (пустые места — `TileType.Void`, у гекса —
`TileId` и уровень), юнит → `UnitStats` и список навыков, навык → `SkillDefinition` (клетки с `EffectSpec`), тип гекса →
вид (`TileVisual`). «Играть» и тестовые запуски редакторов используют одну и ту же фабрику и одну симуляцию.

## 6. Постоянное правило расширения (ТЗ ч.4 §9.3)

> При создании **любой новой редактируемой механики** одновременно: (1) опиши её правила в актуальном ТЗ; (2) создай/расширь
> версионированную схему определения; (3) добавь проверку значений и миграцию старых данных; (4) подключи единый обработчик
> в симуляции; (5) зарегистрируй поля и предпросмотр в режиме разработчика; (6) обеспечь сохранение, импорт и экспорт;
> (7) добавь тест игрового действия, UI-редактирования, загрузки, совместимости и отката. Не добавляй новый игровой
> параметр, не дав создателю контента средства управлять им, кроме прямо обозначенных базовых алгоритмов. Новые категории
> добавляй через реестр, сохраняя уже существующие объекты и их стабильные ID.

Новый вид объектов — `ContentTypeRegistry.Register(new ContentKind { … })`; новый тип эффекта — дескриптор в
`EffectTypeRegistry` (поля, контексты) + `IEffectHandler` в `EffectResolver`. Тест `RegistryTests` требует, чтобы у каждого
зарегистрированного типа эффекта был обработчик в симуляции.
