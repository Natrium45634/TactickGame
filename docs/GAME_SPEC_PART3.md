# ТЗ гексагональной тактической игры — часть 3

**Редакция документа:** 0.3  
**Темы:** плавное перемещение поверх дискретного гекс-маршрута; базовые характеристики; приказ атаки по врагу; базовый направленный навык; планирование применения навыка в ТД.  
**Статус:** авторские требования обязательны; недоопределённые параметры и варианты UX явно отмечены как **проектные допущения**.  
**Приоритет:** часть 3 уточняет и переопределяет противоречащие положения редакций 0.1–0.2. Исторические файлы редакций 0.1 и 0.2 остаются нетронутыми.  
**Важное различие:** редакция *ТЗ* 0.3 не равна релизу *игры* v0.3.0; функциональность добавляется в план реализации последовательно.

## 1. Цель и принцип реализации

Добавить боевую и визуальную глубину, **не увеличивая количество обязательных жестов игрока**. У юнита сохраняется строго управляемый путь по гексам; видимое перемещение сглаживается. Игрок по-прежнему управляет белой стрелкой движения, ТД, непрерывной цепочкой и обязательным направлением взгляда; теперь враг может стать целью атаки, а ТД — носителем запланированного навыка.

Ключевые независимые понятия:

1. `GraphPath` — **технический путь**, список допустимых смежных гексов, полученный A*. Не заменяется кривой.
2. `VisualMotionCurve` — **плавная пространственная траектория**, построенная по `GraphPath`. Не является самостоятельным разрешением на проход сквозь препятствие.
3. `Waypoint` / `ТД` — обязательная точка маршрута; при наличии навыка юнит действительно достигает этой клетки и выполняет действие.
4. `MoveOrder` — приказ на перемещение через ТД с финальным направлением взгляда.
5. `AttackTargetOrder` — приказ атаковать конкретного вражеского юнита; при выборе врага направление взгляда определяется автоматически.
6. `WaypointSkillAction` — одно запланированное применение навыка в заданной ТД с сохранённым направлением; не уничтожает последующие ТД.

## 2. Передвижение: техническая сетка и плавная траектория

### 2.1. Обязательная логика

- В основе передвижения — **те же 120 flat-top гексов**, соседство шести направлений, алгоритм A* и проверка проходимости/занятости из частей 1–2.
- Маршрут юнита хранится как **упорядоченный список гексов**; обычные «технические» шаги нужны симуляции, поиску пути, занятости, боевой геометрии и определению достижения ТД.
- **Реальный видимый путь не должен быть ломаной из прямых «центр–центр» на каждом повороте.** Юнит плавно проходит изгибы, срезает безопасные углы, идёт по дугам там, где это допустимо, без резких разворотов на границах соседних гексов.
- Графический юнит должен оставаться в пределах **разрешённого коридора движения**, построенного из гексов его `GraphPath` и согласованных безопасных переходов. Сглаживание не даёт права проходить через стену, непроходимый гекс, занятый чужим юнитом гекс либо за край поля.
- **ТД нельзя «срезать»:** каждая ТД маршрута должна быть реально достигнута как соответствующий логический гекс; если в ТД назначен навык, выполнение привязывается к достижению её опорной точки и остановке/фазе действия, а не к приблизительному прохождению рядом.
- Видимая линия приказа **остаётся прямой белой стрелкой** (голубой для команд), поверх всех объектов карты. Плавная траектория — отдельная внутренняя визуализация/анимация; она не должна подменять UI-стрелку приказа. Существующая **ненавязчивая подсветка технического маршрута по гексам сохраняется**: при планировании игрок по-прежнему видит выбранные алгоритмом клетки, независимо от плавной траектории модели. Отображение технического маршрута должно быть отдельным слоем от основной прямой стрелки приказа; для диагностики допускается усиленный debug-режим.
- Ориентация по шести направлениям — **игровое значение `Facing`**. Визуальная модель может плавно поворачиваться между направлениями, но её положение не изменяет правила шести направлений и расчёт области навыка.

### 2.2. Рекомендуемый алгоритм сглаживания (проектное техническое решение)

1. A* формирует путь `H0 → H1 → … → Hn` с препятствиями и резервированием.
2. Разбить путь на отрезки, **разделённые обязательными ТД**: каждая ТД — жёсткий якорь, а навык в ТД — якорь действия.
3. Внутри каждого отрезка получить плавную траекторию (например, локальные квадратичные/кубические кривые Безье или Catmull–Rom с контролем выхода за коридор). Выбор кривой — деталь реализации, а не новая игровая механика.
4. Перед принятием кривой проверить её **всю протяжённость**, а не только контрольные точки: дискретной выборкой с достаточной плотностью плюс точной проверкой пересечений границ/препятствий. Учитывать радиус коллизии юнита, а не только центральную точку.
5. При слишком узком проходе, препятствии у внутреннего угла, неопределённости коллизии или невозможности безопасно сгладить угол **локально вернуться к движению через центры**. Важнее правильность, чем эффектная дуга.
6. Плавно параметризовать кривую по длине, чтобы повороты не создавали заметных скачков скорости. Перестройка пути начинается с **текущего реального положения**, не со скачка к центру ближайшего гекса.
7. Для команды применять те же ограничения индивидуально ко всем участникам; сглаживание не может обойти правило «один логический гекс — один юнит» и резервацию безопасных переходов.

### 2.3. Симуляция и занятость

- Авторитетны **состояние симуляции**, `GraphPath`, опорные ТД и данные коллизий. Самостоятельное движение Godot-ноды вне разрешённой траектории запрещено.
- Положение юнита непрерывно в пространстве карты; **текущий логический гекс** вычисляется/обновляется по одному детерминированному правилу пересечения границы смежных гексов. В момент перехода сохраняется корректное резервирование целевого гекса.
- Не допускать расхождения между отрисованной позицией, доступностью для выбора на текущем гексе, проверкой направления атаки и логикой занятости. Во время движения юнит выбирается согласно правилам части 2 и может перепланироваться на паузе.
- Сглаживание не может «перескочить» промежуточный гекс, если это ломает последовательность занятости или разрешённых переходов. Если геометрически допустимый срез пропускает логический гекс, траекторию/коридор следует ограничить.
- При столкновении с новым препятствием или резервом другого юнита безопасно затормозить и перестроить оставшуюся геометрию; **не проходить сквозь объект**, не возвращаться рывком назад, не телепортироваться.
- В тактической паузе симуляция, движение и анимация изменения положения остановлены; **планирование и предпросмотр кривой** доступны. После замены приказа траектория подхватывается без скачка от позиции юнита в момент паузы.

### 2.4. Скорость движения

**Авторское требование:** базовая скорость каждого юнита — **1 гекс в секунду** (`MoveSpeedHexPerSecond = 1.0`). Это заменяет тестовый ориентир **2 гекса/с** из части 1.

**Проектная трактовка для реализации:** время прохождения технического маршрута между двумя опорными точками измерять по числу гекс-переходов: `время_сегмента = число_переходов / MoveSpeedHexPerSecond`; плавная траектория распределяется по этому времени с учётом её длины. Это сохраняет баланс в единицах гекс/с и не ускоряет юнита только потому, что его путь сгладили. При необходимости будущие ускорения/замедления рассчитывать через симуляционное время. Для ТД с навыком время применения навыка учитывается отдельно.

## 3. Характеристики юнита: минимальная модель

| Характеристика | Поле модели | Базовое значение | Правило |
|---|---|---:|---|
| Максимальное здоровье | `MaxHealth` | **100 HP** | Верхняя граница здоровья |
| Текущее здоровье | `CurrentHealth` | **100 HP** при появлении | Урон уменьшает значение; не ниже 0 |
| Скорость перемещения | `MoveSpeedHexPerSecond` | **1.0 гекс/с** | Время следования по техническому маршруту |
| Скорость обычной атаки | `AttackRatePerSecond` | **3 удара/с** | Интервал между ударами `1 / 3 с ≈ 0,3333 с` |

- У каждого юнита — союзного и вражеского — есть идентификатор, команда/фракция, обязательное направление взгляда, активность, здоровье, параметры движения и атаки, набор навыков.
- Юнит считается **мёртвым при `CurrentHealth == 0`**; одновременно запрещаются дальнейшие удары, навыки, изменение маршрута и получение новых приказов. Остановить его текущие действия; освободить занятый/зарезервированный маршрутом ресурс согласно единому порядку симуляции.
- Визуальное исчезновение тела/анимация смерти не должны определять момент смерти в логике. Если труп когда-нибудь станет физическим препятствием, это потребуется определить отдельным требованием; в текущем прототипе погибший перестаёт занимать клетку (**проектное допущение**).
- Урон и гибель обрабатываются **на фиксированном игровом тике**, а не прямо в кадре UI. Несколько эффектов одного тика исполняются в заранее заданном, тестируемом порядке.
- **Обычный урон одной атаки, дальность обычной атаки, броня, сопротивления и лечение автором ещё не заданы.** Не выдавать временные значения за окончательный баланс. Для работающего тестового прототипа разрешено параметризованное значение обычного урона **10 HP за удар** и дальность **1 соседний гекс**, явно помеченные `PROTOTYPE_DEFAULT` в конфигурации и документации, без жёсткого встраивания в обработчик ввода.
- **Проектное правило частоты:** удары при активной атаке происходят не чаще одного раза за `1 / AttackRatePerSecond` игрового времени. Первый удар — после первого интервала (для стабильного тестирования); будущие бонусы скорости и анимации не меняют этого лимита без отдельного решения.

## 4. Атака по вражеской цели из стрелки движения

### 4.1. Переход в атаку

1. Игрок ведёт **обычную белую стрелку движения** от юнита или от очередной ТД.
2. Если конечный гекс содержит **живого вражеского юнита**, наведение показывает режим **«Атака»**, а подтверждение ЛКМ создаёт **`AttackTargetOrder(enemyUnitId)` вместо новой ТД**. На занятом врагом гексе нельзя создавать фиктивную ТД и пытаться встать туда одновременно. **Приоритет ввода:** проверка живого врага производится *до* общего правила «красный/занятый гекс = недопустимая ТД = отмена черновика»; в режиме прицеливания по врагу клетка показывается особым маркером цели, а не как обычная запрещённая ТД.
3. **Не запрашивать отдельную точку зрения** для этого приказа. В момент подтверждения цель сама задаёт направление: юнит **немедленно поворачивает игровое `Facing` к врагу**; белый указатель на его текущем гексе обновляется. На паузе приказ и взгляд меняются сразу, хотя время атаки не течёт.
4. Если в цепочке уже есть ТД, они сохраняются как предшествующие этапы. Атака становится **конечной стадией данной цепочки**, а не произвольной невидимой дополнительной ТД. После неё не появляется обязательное меню выбора взгляда. Позднее можно разрешить дополнительные действия после цели отдельным расширением.
5. При групповой КТД автоматическую групповую атаку **пока не добавлять**, чтобы не выдумывать поведение капитана и спутников. Режим групповых стрелок/команд из части 2 сохраняется; применение атаки к группе требует будущей спецификации.

### 4.2. Геометрия цели, дальность и слежение

- При выборе врага юнит **не занимает его клетку**. Если цель вне досягаемости обычной атаки, игра может автоматически построить кратчайший путь к **достижимой свободной клетке**, из которой цель находится в радиусе атаки. Это **проектное предложение** для прототипа; ближайшая по длине допустимая позиция выбирается детерминированно.
- Пока атака выполняется, юнит удерживает или обновляет направление взгляда на живую цель. Для цели на линии между двумя из шести направлений применять детерминированное правило выбора ближайшего направления с устойчивым разрешением равенства.
- Если враг перемещается, маршрут преследования допускает перерасчёт с ограничением частоты (не каждый кадр). При невозможности достичь дистанции атаки юнит останавливается и получает понятное состояние `TargetUnreachable`; при гибели/удалении цели приказ корректно завершается.
- Атака наносит обычный настраиваемый урон по таймеру `AttackRatePerSecond`, **только когда живая цель в допустимой дальности**. Коллизии/препятствия и линия видимости для обычного удара в будущем могут усложняться, но в прототипе должны быть описаны явно.
- **Не включать автопоиск новой цели, агро, ответный огонь ИИ и систему обычных атак по площади:** пользователь пока их не описал.

### 4.3. Уточнение прежнего правила об обязательном взгляде

Часть 2 требовала, чтобы **каждый подтверждённый приказ имел валидное конечное направление взгляда**. Для `AttackTargetOrder` оно **не исчезает**, а **вычисляется автоматически из вражеской цели**, поэтому игрок не выбирает его вручную. Для обычного `MoveOrder` по-прежнему необходимо выбрать сторону гекса в конце цепочки.

## 5. Первый навык: направленный удар по двум гексам

### 5.1. Функциональные требования

**Временное игровое название:** `Линейный удар` (только для прототипа; название и иконка могут поменяться).

- Навык использует **одно из шести направлений `Facing`** юнита.
- Область действия: **ровно два последовательных гекса перед юнитом**, на расстоянии 1 и 2 гекс-перехода по выбранному направлению. Это **не** круг, не два соседних боковых сектора и не радиус 2 вокруг юнита.
- До активации область **подсвечивается серым, полупрозрачно**, чтобы игрок понимал, какие два гекса будут поражены. Для задания с ТД предпросмотр рассчитывается **от координаты ТД**, а не от текущего местоположения идущего к ней юнита.
- При активации навык **однократно наносит 20 HP урона каждому живому врагу**, который **в этот конкретный момент** находится в одной из двух целевых клеток. Проверять актуальное расположение врагов в симуляции на тике применения; не «запоминать» тех, кто стоял в подсветке при планировании.
- Если в зоне два врага — каждый получает 20 HP. Если в зоне нет врагов — попаданий нет, навык всё равно считается применённым. Если часть области выходит за границы карты, отображаются и проверяются только существующие гексы; отсутствующие клетки не порождают ошибку.
- **Проектные временные настройки:** союзники не получают урон от этого навыка (friendly fire отключён); препятствия пока не перекрывают его воздействие; стоимость ресурса, перезарядка и анимационное время каста отсутствуют **до отдельного согласования**. Код заранее позволяет добавить всё перечисленное конфигурацией/новыми правилами.
- Навык исполняется **один раз за одно запланированное действие**, а не на протяжении пребывания в ТД и не три раза в секунду. `AttackRatePerSecond` относится к **обычной атаке**, не к разовому навыку.

### 5.2. Предпросмотр при обычном использовании

- В UI юнита отображается иконка навыка. При выборе навыка показывается **серая область двух поражаемых клеток** в направлении предполагаемого удара.
- Для обычного немедленного применения (вне ТД) разрешить выбор одного из шести направлений; после подтверждения навык применяется с текущей клетки юнита (при тактической паузе — только после её снятия). **Способ вызова иконки вне ТД — проектное предложение**, поскольку пользователь явно описал интерфейс назначения из ТД.
- Серую подсветку не путать с красно-зелёным режимом доступности движения: разные типы наложений и разная смысловая нагрузка.

## 6. Назначение навыка непосредственно на ТД

### 6.1. Один понятный жест, без изменения цепочки

1. Игрок прокладывает обычную цепочку `Юнит → ТД1 → ТД2 → …` без дополнительных меню.
2. Игрок **коротко нажимает ЛКМ по существующей ТД** (не тянет её). **Рядом с ТД** появляется компактный интуитивный контекстный интерфейс с **иконкой доступного навыка**.
3. При ЛКМ по этой иконке интерфейс входит в режим `SkillAimFromWaypoint`: от ТД за курсором тянется **красная стрелка направления применения навыка**, отображаемая поверх всех объектов игрового поля.
4. Игрок указывает одно из **шести направлений**. Гексы на расстояниях 1 и 2 **от данной ТД** мгновенно подсвечиваются серым. ЛКМ подтверждает направление и сохраняет `WaypointSkillAction` вместе с ТД.
5. У ТД появляется **красная шестигранная иконка с символом навыка и числом `1`**, показывающая **одно назначенное применение**. Два серых гекса остаются подсвеченными, пока это действие находится в очереди/режиме планирования (с правилами видимости ниже).
6. Имеющиеся **следующие ТД не удаляются**. Во время исполнения юнит достигает выбранной ТД, выполняет навык, а затем **автоматически продолжает маршрут к следующей ТД**. Повторного приказа игрока не требуется.
7. После подтверждения направления навыка управление возвращается в прежний режим: редактирование цепочки/ожидание выбора обязательного конечного взгляда либо обычное состояние HUD, если приказ уже подтверждён.

### 6.2. Клик и перетаскивание на одной ТД

- **Короткий клик ЛКМ по центральному маркеру ТД** → открыть интерфейс её действия/навыка.
- **ЛКМ с перетаскиванием от маркера ТД** (движение курсора за порог распознавания) → продолжить или изменить маршрут **как ранее**, без открытия панели навыка.
- **Клик по одному из шести секторов возле стороны последней ТД** в активном черновике → выбрать обязательное **конечное направление взгляда** (как в части 2), а не открыть навык. Для надёжности центральная кликабельная зона маркера ТД и сектора направления у её граней не пересекаются: `контекстный интерфейс/иконка > центр маркера ТД > сектор взгляда > гекс`. Наведение без нажатия показывает соответствующий предпросмотр.
- **Автоматическое продолжение цепочки** после постановки ТД из части 2 **сохраняется**: чтобы создать следующую точку, вообще не надо снова трогать ТД. Жест перетаскивания существующей ТД нужен только для явного редактирования ранее созданной ветки.
- **Проектная величина порога** — ~6–10 экранных пикселей с поправкой на масштабирование интерфейса; не требовать длинного удержания для различения клика/drag.
- В открытом контекстном интерфейсе приоритет обработки кликов имеет иконка навыка; попадание по ней не должно создавать ТД. ПКМ отменяет **текущий предпросмотр навыка/меню**, затем по следующей ПКМ — более общий черновик маршрута, не стирая подтверждённые чужие команды.
- Если игрок назначает навык в ТД **пока весь маршрут ещё черновой**, действие остаётся в том же `DraftOrder` и подтверждается атомарно с финальным взглядом. Если ТД уже принадлежит утверждённому, но не исполненному маршруту, редактирование навыка должно быть транзакционным: отмена правки не удаляет исходный маршрут.

### 6.3. Направление навыка и направление взгляда юнита

- Существующее `Facing` юнита **всегда определено**; направление самого навыка задаётся красной стрелкой.
- В момент применения из ТД юнит **ориентируется в выбранное для навыка направление** — таким образом, удар действительно происходит в сторону его взгляда.
- **Проектное правило совместимости с частью 2:** если у ТД есть явное закреплённое направление взгляда, которое должно сохраняться после действия (например, финальная ТД), то **после удара** юнит возвращается в это направление. Иначе направление после удара соответствует направлению навыка, до следующего шага маршрута.
- Если на конечной ТД навык назначен, но игрок ещё не выбрал **обязательное финальное направление**, `MoveOrder` остаётся незавершённым черновиком; красная стрелка навыка **не подменяет** автоматически выбор финального взгляда.
- Нормальная атака по врагу, выбранная стрелкой, — другой тип приказа. Она **не подменяет и не удаляет** ранее назначенный навык на предшествующей ТД.

### 6.4. Область, иконки, визуальные приоритеты

- Два серых гекса отражают **планируемую область удара**, а не обещание попадания по врагу. Враг может уйти с них до момента активации.
- Предпросмотр серой области и постоянная отметка ТД не перекрывают гекс, персонажей, их HP и границы непрозрачной сплошной заливкой. Рекомендуется мягкая заливка α около 0,18–0,28 и тонкая нейтральная обводка только при наведении.
- Красная стрелка выбора навыка — **выше всей игровой сцены**, как белые и голубые стрелки; HUD/контекстное меню могут находиться выше стрелок. Красная **шестигранная иконка** должна читаться поверх базового маркера ТД, но не закрывать саму ТД и соседние кликабельные элементы.
- Если на маршруте назначено несколько навыков в разных ТД, каждая ТД несёт **свою отдельную** иконку и свои две клетки. Для читаемости активное/выделенное действие подсвечивается ярче, а остальные — более приглушённо. Нельзя смешивать серую зону навыка с текущей зелёно-красной подсветкой доступности маршрута (при одновременном отображении подсветка движения имеет приоритет в своём режиме, но области запланированного удара доступны по наведению/выбору ТД).
- После выполнения навыка его **красная иконка и предиктивная серая зона исчезают** из очереди активных приказов. В отладочном режиме разрешено показывать факт исполнения/лог; никаких «призрачных зон поражения», вводящих игрока в заблуждение.

### 6.5. Ограничения и ошибки

- В текущем этапе — **не больше одного навыка в одной ТД** (красная иконка `1`); между разными ТД можно запланировать несколько применений, если иное не ограничено в будущем перезарядкой или ресурсом.
- Нельзя назначить навык на недостижимую/отменённую ТД, мёртвому юниту или при активном конфликтующем режиме редактирования. Если редактирование маршрута удаляет конкретную ТД, **связанный с ней навык удаляется вместе с ней**, а навыки на сохранившихся ТД остаются.
- Если юнит погиб до прибытия в ТД, навык не исполняется. Если ТД стала недостижима, навык **не срабатывает на чужом гексе**; юнит останавливается/перестраивает путь по правилам части 2.
- Нельзя активировать навык повторно из-за повторного входа в ту же клетку, пересчёта кривой, изменения FPS или перехода пауза/игра. У каждого действия есть устойчивый идентификатор и флаг исполнения.

## 7. Последовательность событий симуляции и пауза

Для повторяемости результата **проектное правило** фиксированного тика:

1. Принять уже **подтверждённые** приказы; неопределённые черновики и наведение курсора симуляцию не меняют.
2. С учётом резервов передвинуть юнитов по логическим маршрутам и сглаженным безопасным траекториям; определить достигнутые ТД.
3. На достигнутой ТД **до перехода к следующей** выполнить назначенное действие: установить направление навыка, взять снимок текущего расположения целей, применить однократный урон 20 HP.
4. Применить обычные атаки, которым пришло время согласно `AttackRatePerSecond`; проверить живость и дальность целей.
5. Обработать смерть/освобождение клеток, снять выполненные действия, сформировать события для визуализации.
6. Разрешить продолжение движения на следующем игровом тике. При нулевом времени каста нет необходимости удерживать юнита в ТД дольше одного тика; будущие длительности вводить отдельными параметрами.

При **тактической паузе** таймеры атак и навыков не продвигаются, урон не наносится. Игрок может планировать цель, навык в ТД и менять путь; показ серых гексов и красной стрелки работает. Утверждённые на паузе изменения начинают исполняться только после её снятия.

Важно: `AttackTargetOrder` может **автоматически менять игровой взгляд прямо при подтверждении на паузе**, но не причиняет урон до возобновления симуляции. Это не нарушение паузы, а изменение запланированной ориентации игроком.

## 8. Архитектура и модель данных

Разделение `Core` / `Simulation` / `Input` / `Presentation` / `UI` из редакции 0.2 **сохраняется**. Дополнить его следующими моделями и сервисами (точные имена можно адаптировать к реальной структуре Godot/.NET, сохранив смысл):

```text
UnitStats {
    maxHealth: 100,
    moveSpeedHexPerSecond: 1.0,
    attackRatePerSecond: 3.0,
    normalAttackDamage: configurable_prototype_value,
    normalAttackRangeHex: configurable_prototype_value
}
UnitState { id, team, currentHealth, logicalHex, worldPosition, facing,
            movementState, attackState, skillSet, lifeState }
GraphPath { orderedHexes, waypointAnchors, reservations }
MotionPlan { graphPathRef, safeCurves, arcLengthData, progress }
OrderStep = MoveToWaypoint | ExecuteWaypointSkill | AttackTarget
Waypoint { id, hex, index, optionalSkillActionId, optionalFinalFacing }
WaypointSkillAction { id, skillId, direction6, originWaypointId,
                      executionStatus: Planned|Executed|Cancelled }
AttackTargetOrder { attackerId, enemyUnitId, state }
SkillDefinition { id, relativeHexOffsetsPerDirection, damage, hitRules,
                  cost?, cooldown?, castDuration? }
AttackService / DamageService / DeathService
MotionSmoothingService / MotionCorridorValidator
SkillAreaPreviewService / WaypointSkillScheduler
CommandInputStateMachine: SkillMenuAtWaypoint | SkillAimFromWaypoint
VisualOrderOverlay: whiteMoveArrow | cyanGroupArrow | redSkillAimArrow
```

Структура должна обеспечить:

- **Чистую проверяемую арифметику на гексах** для направлений и двух клеток поражения. Не рассчитывать игровой урон по экранным пикселям, наклону камеры или повороту меша.
- **Неизменяемый идентификатор ТД**, чтобы её навык не переназначился случайно при перестроении пути/сглаживании и чтобы можно было корректно отменить её с последующими точками.
- **События симуляции** `WaypointReached`, `SkillActivated`, `DamageApplied`, `UnitDied`, `AttackTargetLost` с идентификаторами и игровым временем.
- **Детерминированный порядок** событий при одновременных смертях, пересечениях ТД и попаданиях, без зависимости от FPS.
- **Конфигурируемый баланс** через ресурсы/данные, а не константы в коде мыши.
- Разделение трёх временных масштабов: **реальное время UI**, **симуляционное игровое время** (останавливается на паузе) и **интерполяция кадра** для плавности.
- Дополнительный режим диагностики: показать `GraphPath`, безопасный коридор, фактическую кривую, логический гекс, ID навыка, ожидаемую область удара, счётчики ударов/HP и версии правил.

## 9. Приёмочные тесты для части 3

Минимальные сценарии, которые должны пройти **в дополнение** к тестам частей 1–2:

1. **Сглаживание:** юнит на маршруте с несколькими поворотами не ломает траекторию в точных центрах каждого транзитного гекса; визуально заметен плавный дугообразный проход.
2. **Безопасность угла:** если внутренний угол граничит с препятствием, кривая не заходит в него; при необходимости применяется локальное движение без сглаживания.
3. **Сохранение пути:** фактически пройденные логические гексы в правильном порядке соответствуют разрешённому `GraphPath`; нельзя перейти через непроходимую клетку, «срезав» её по диагонали.
4. **ТД как якорь:** сглаженная траектория действительно достигает ТД1 и ТД2 в заданном порядке; на ТД с навыком не происходит пролёта мимо точки активации.
5. **Изменение маршрута на паузе:** после изменения приказа в середине движения юнит продолжает из фактического положения, без скачка и без пересечения чужой клетки.
6. **Скорость:** чистый путь из трёх гекс-переходов при 1 гекс/с занимает 3 игровых секунды (без навыков, блокировок и иных модификаторов), независимо от кадровой частоты.
7. **Характеристики:** новые союзный и вражеский юниты получают 100/100 HP, скорость движения 1 гекс/с, скорость обычной атаки 3/с.
8. **Смерть:** получение 100 суммарного урона приводит к 0 HP и состоянию смерти; мёртвый юнит не выполняет новые команды и не наносит ударов.
9. **Частота обычной атаки:** на неподвижной доступной цели в течение трёх игровых секунд производится ровно девять ударов по принятому правилу первого удара; пауза не добавляет ударов.
10. **Клик по врагу:** белая стрелка на живого врага создаёт `AttackTargetOrder` вместо ТД, отдельного выбора направления не требует, `Facing` устанавливается в сторону врага.
11. **Цель вне дальности:** при разрешённом тестовом автоподходе юнит занимает свободную допустимую атакующую клетку, но никогда клетку врага; недостижимая цель вызывает явный отказ/ожидание без телепортации.
12. **Геометрия навыка:** по всем шести направлениям подсвечиваются ровно два следующих гекса; на краю карты корректно остаются только существующие клетки.
13. **Урон навыка:** два врага на двух поражаемых клетках получают по 20 HP; союзник в зоне не получает урон по принятому временному правилу friendly fire.
14. **Уход из зоны:** враг, бывший на сером гексе при планировании, но ушедший к активации, не получает урон. Враг, вошедший позже к моменту каста, получает 20 HP.
15. **Планирование из ТД:** короткий ЛКМ по **центральному маркеру** ТД открывает меню, ЛКМ по иконке навыка — красную стрелку, выбор направления — серую область; подтверждение добавляет красный шестиугольник с цифрой `1`. Клик у грани последней ТД по-прежнему выбирает конечный взгляд.
16. **Различение жестов:** короткий клик на ТД не создаёт новую точку, а перетаскивание из ТД не раскрывает меню; непрерывная прокладка ТД2 после создания ТД1 работает без нового захвата.
17. **Навык между ТД:** маршрут `ТД1 → ТД2(навык) → ТД3` полностью исполняется в таком порядке: дойти до ТД2, однократно нанести урон в двух гексах, продолжить к ТД3.
18. **Многократные ТД:** навыки, назначенные на разные ТД, имеют разные идентификаторы; каждое запланированное действие выполняется ровно один раз.
19. **Отмена:** ПКМ из режима красной стрелки отменяет предпросмотр навыка, но не стирает весь маршрут и не затрагивает приказы других юнитов; отмена самой ТД удаляет только связанный с ней навык.
20. **Визуальные приоритеты:** белые/голубые/красные стрелки не скрываются зданиями/юнитами; серый предпросмотр не закрывает карту полностью и не мешает выбрать ТД.
21. **Пауза:** назначение навыка или атаки на паузе само по себе не наносит урон и не запускает таймер атаки.
22. **Сохранение совместимости:** 20 сценариев второй части ТЗ и начальные тесты первой части продолжают проходить.

Для ручной проверки создать **отладочную сцену** из нескольких союзных юнитов, неподвижных вражеских мишеней, препятствия с углом, серии ТД, команды из пяти участников и возможности быстро включать паузу. Это тестовый стенд, **не полноценный вражеский ИИ**.

## 11. Явно открытые вопросы — НЕ вводить незаметно как канон

- Обычный урон и дальность удара, ближняя/дальняя атака, автоматическое нападение при появлении врага, блокирование линии удара препятствиями.

- Приказ на групповую атаку, скилл на КТД для капитана/каждого члена команды и взаимодействие с автоматическими взглядами спутников.
- Что делать с командой, когда капитан или часть участников погибают, и какие группы могут выполнять сложные способности совместно.
- Приоритет нескольких одновременных навыков в один тик в окончательной боевой модели, агро/ИИ, удерживание цели, укрытия, дальности обзора и обнаружение врагов.

**Технические допущения для рабочего прототипа** (не авторские решения): обычный урон 10 HP/удар, дальность 1 гекс, первый обычный удар через интервал, автоматический подход к цели, отсутствие задержки/ресурса/перезарядки навыка, отсутствие friendly fire, навык без блокировки препятствиями, одно применение на ТД, локальное сглаживание с безопасным откатом на прямые, время по числу переходов и порядок событий симуляции.

## 12. Инструкция Claude Code для внедрения этой части

> Обнови **актуальное**, а не историческое ТЗ. Сохрани все существующие механики карты, белых/голубых стрелок, непрерывных ТД, обязательной ориентации, команды, КТД и паузы. Внедряй требования части 3 по одной версии игры, **не пытайся реализовать все v0.8.0–v0.11.0 в одной сборке**. Раздели логический путь и сглаженную траекторию, проверяй безопасность каждого поворота и не используй анимацию как источник истины о занятости. Скорость юнита — 1 гекс/с, HP 100, атака 3/с. При клике стрелкой на живого врага формируй `AttackTargetOrder` и автоматически устанавливай взгляд; на обычном маршруте финальный взгляд остаётся обязательным. Добавь направленный навык на два гекса с уроном 20 и отложенное применение в ТД через короткий ЛКМ, контекстную иконку и красную стрелку. Навык не прерывает последующую цепочку. Подтверждай события только на фиксированных тиках, тестируй паузу, смерть и однократность навыка. Проверь регрессию всех старых функций, создавай новые архивы сборок, не переписывая старые.
