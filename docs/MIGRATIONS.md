# История схем пользовательских данных

ТЗ ч.4 §8.4, §12.3 п.29: изменение формата не должно молча портить объекты пользователя. Перед несовместимой миграцией
объект копируется в `user://backups/`, неподдерживаемая (более новая) версия схемы не загружается и файл не трогается.
Миграция данных вида — функция `ContentKind.Migrate(from, data, issues)`, шаг за шагом `from → from + 1`.

Сквозная проверка v0.25.0: юнит схемы 1 (v0.15–v0.20) проходит шаги 1 → 2 → 3 → 4 при одной загрузке с одной копией оригинала;
пакеты v0.20.0 импортируются на установку v0.25.0 (чистая установка в регрессии).

Новые **необязательные** поля с значением по умолчанию добавляются без смены версии схемы: старые файлы остаются
корректными. Удаление или переименование поля, изменение смысла значения — новая версия схемы и миграция.

## Как выполняется миграция (с v0.20.0)

При загрузке пользовательского файла старой схемы (D-116): `ContentKind.Migrate` шаг за шагом → оригинал копируется в
`user://backups/<время>-migration-schemaN/<папка>/<id>.json` → файл переписывается атомарно (временный файл → проверка →
замена) → запись в `logs/content.log`. Нет шага миграции или версия новее поддерживаемой — объект не загружается, файл не
меняется. Импорт (`.json`/`.hxp`) мигрирует объекты старой схемы так же — в предпросмотре видно «схема N → M».

| Формат | Версия | С версии игры | Изменения |
|---|---|---|---|
| пакет `.hxp` (`manifest.json`, `formatVersion`) | 1 | v0.20.0 | первая версия: объекты, SHA-256, нужные встроенные объекты |
