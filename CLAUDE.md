# CLAUDE.md — правила работы с проектом HexTactics

Этот файл читается Claude Code перед любыми изменениями. ТЗ: `docs/GAME_SPEC.md` (редакция 0.1, историческая,
**не изменять**), `docs/GAME_SPEC_PART2.md` (редакция 0.2, историческая, **не изменять**; переопределяет 0.1),
`docs/GAME_SPEC_PART3.md` (редакция 0.3, **не изменять**; правила боя и движения), `docs/GAME_SPEC_PART4.md`
(редакция 0.4, **не изменять**: режим «Разработчик», редакторы, пользовательский контент), `docs/GAME_SPEC_PART5.md`
(редакция 0.5, **не изменять**: единая система урона и защиты, типы урона, сопротивления, «Механики») и
`docs/GAME_SPEC_PART6.md` (редакция 0.6, **не изменять**: игра как визуальный конструктор боевой системы — единый реестр
пользовательских определений, защита A, пассивы, теги и дерево видов, внезапность по направлению, крит и сверхкрит;
дополняет 0.1–0.5 в названных местах, ТЗ ч.6 §14.1; её план версий ещё выполняется) и `docs/GAME_SPEC_PART7.md`
(редакция 0.7, **актуальная**: четыре типа сценариев — обычный бой, Tower Defense, оборона, исследование — через общий
`ScenarioDefinition`, маршруты и волны врагов, простой ИИ, характеристика «Блок», автоматическая базовая атака; при прямом
пересечении определяет правила сценариев, блока и автоатаки, остальное из 0.1–0.6 действует).

## Порядок работы

1. Прочитать `CLAUDE.md`, `docs/GAME_SPEC.md`, `docs/GAME_SPEC_PART2.md`, `docs/GAME_SPEC_PART3.md`, `docs/GAME_SPEC_PART4.md`, `docs/GAME_SPEC_PART5.md`, `docs/GAME_SPEC_PART6.md`,
   `docs/GAME_SPEC_PART7.md`, `docs/ARCHITECTURE.md`, `docs/CONTENT_FORMAT.md`, `docs/DECISIONS.md`, `CHANGELOG.md`, историю Git (`git log --oneline`, `git tag`).
2. Реализовывать **только очередную версию** из плана версий, сохраняя все работающие функции. Выпущенные v0.1.0–v0.5.0
   неизменяемы; план ТЗ ч.2 §13 реализован версиями v0.6.0–v0.10.0 (D-033), план ТЗ ч.3 §10 — v0.11.0–v0.14.1 (D-062),
   план ТЗ ч.4 §11 — v0.15.0–v0.20.0 (D-080), план ТЗ ч.5 §12 реализован версиями v0.21.0–v0.25.0 (с исправлением v0.24.1; соответствие —
   DECISIONS D-119, приёмка — docs/ACCEPTANCE_PART5.md), план ТЗ ч.6 §13 реализуется версиями v0.26.0–v0.31.0 (соответствие —
   DECISIONS D-143, приёмка — docs/ACCEPTANCE_PART6.md), план ТЗ ч.7 §13 — версиями v0.32.0–v0.39.0 **после** завершения
   части 6 (соответствие — DECISIONS D-150).
3. Перед кодом — короткий план и список файлов. Не переписывать фундамент без необходимости; несовместимые изменения сначала описать в `docs/DECISIONS.md` (раздел «Миграции»).
4. После изменений: сборка, тесты, сценарии мыши (автоматизация `--hx-script`), экспорт Windows.
5. Версия считается готовой только после проверки запуска.

## Слои и правила кода

| Слой | Где | Правило |
|---|---|---|
| Core (домен) | `src/Core` → `HexTactics.Core` | Чистый C#, **без Godot**. Правда о состоянии игры. |
| Simulation | `src/Simulation` → `HexTactics.Simulation` | Фиксированный тик 1/30 с, приказы, движение, пауза, события; новые правила — через `ISimulationSystem`. Без Godot. |
| Interaction | `src/Interaction` → `HexTactics.Interaction` | Конечный автомат ввода в координатах карты. Без Godot. |
| Content | `src/Content` → `HexTactics.Content` | Определения контента (карты, юниты, навыки, типы гексов), реестры видов/полей/эффектов, валидация, хранилище `user://`, `RuntimeFactory` (определение → модель Core). Без Godot. |
| Editor | `src/Editor` → `HexTactics.Editor` | Логика режима «Разработчик»: Undo/Redo, модели каталога и редакторов. Без Godot. |
| Presentation / Input glue / UI | `src/GodotClient` (Godot-проект, сборка `HexTactics`) | Стартовое меню, режимы «Играть»/«Разработчик», отображение, перевод экран → карта, HUD, формы редакторов. **Никаких игровых правил.** |

- Шестисоседняя гекс-система **flat-top, odd-q offset**, вычисления в axial/cube; направления — по рёбрам
  (N, NE, SE, S, SW, NW). Pointy-top/odd-r запрещены (ТЗ ч.2 §2.5). Не использовать TileMap/прямоугольный pathfinding.
- Стрелки и маркеры приказов — в верхнем слое без теста глубины (поверх всех объектов сцены). Личные — белые, командные — голубые.
- Проходимость — только из данных (`TileState`), не из цвета/материала.
- Маршрут хранится в модели, а не в визуальных линиях. Правила не зависят от FPS.
- Боевые механики — только заданные ТЗ ч.3–7 (HP, смерть, обычная атака выбранной цели, навыки из клеток с эффектами
  урон/лечение/бафф/дебафф/периодический, эффекты типов гексов; с ч.5 — типы урона, сопротивления, иммунитеты, конверсии,
  отражения, щиты; с ч.6 — защита A, пассивы, теги, дерево видов, подсчёт стаи, внезапность по шести сторонам, крит и
  сверхкрит с детерминированными бросками; с ч.7 — автоматическая базовая атака в собственной повёрнутой области без
  самовольного поворота и погони, блок `BlockCapacity` (связь с соседним врагом, без двух юнитов в одном гексе), сценарии,
  маршруты и волны врагов, жизни баз, цели миссий и **только** простые пресеты ИИ `AttackUnits`, `AttackObjective`,
  `UnitsThenObjective`, `ObjectiveThenUnits`, `Guard`); деревья поведения, оценку угроз карты, экономику и стоимость
  выставления, контроль, телепорт, стихийную матрицу, уклонение/промахи, третью ступень крита, скрытность, сложные
  триггеры, бесконечные волны и т. п. **не добавлять** без нового этапа ТЗ. Элементы — только пользовательские
  определения (ТЗ ч.6 §2). Временные значения помечать `PROTOTYPE_DEFAULT`.
- Инвариант «один активный юнит — один логический гекс» не нарушается ни в одном режиме (ТЗ ч.7 §7.2, M7-57).
- Любой урон — только типизированное событие `DamageEvent` через единый `DamageResolver` (обычная атака, навык, поверхность,
  периодический статус, отражение); лечение — через единый путь лечения. Численные сопротивления и правила защиты
  **не показывать в режиме «Играть»** (только в «Разработчике» и в явно включённой отладке тестового запуска).
- Игровой контент — **данные** библиотеки (`src/GodotClient/data/content` — встроенный, `user://content` — свой), а не код:
  один источник правды, без особого кода для отдельных навыков/гексов. Эффекты исполняет только `EffectResolver`;
  произвольный код пользователя не исполняется никогда.
- Видимое положение юнита — из симуляции (сглаженная траектория по `GraphPath`), а не из движения Godot-ноды.
- Комментарии в коде — на английском, документация — на русском.

## Постоянное правило расширения механик (ТЗ ч.4 §9.3)

> При создании **любой новой редактируемой механики** одновременно: (1) опиши её правила в актуальном ТЗ; (2) создай/расширь
> версионированную схему определения; (3) добавь проверку значений и миграцию старых данных; (4) подключи единый обработчик
> в симуляции; (5) зарегистрируй поля и предпросмотр в режиме разработчика; (6) обеспечь сохранение, импорт и экспорт;
> (7) добавь тест игрового действия, UI-редактирования, загрузки, совместимости и отката. Не добавляй новый игровой
> параметр, не дав создателю контента средства управлять им, кроме прямо обозначенных базовых алгоритмов. Новые категории
> добавляй через реестр, сохраняя уже существующие объекты и их стабильные ID.

Базовые системные механики (гекс-координаты, поиск пути и занятость, смысл ТД/КТД, автомат ввода, фиксированный тик)
остаются программными и пользователю не открываются; их **данные** (проходимость, скорость и т. п.) — открываются.

## Команда ТЗ ч.5 §14 (дословно)

> Реализуй часть 5 текущего ТЗ как **продолжение** частей 1–4, не изменяя существующие правила ТД, КТД, камеры, плавного движения, боевой паузы и редакторов без явной необходимости. Построй один **типизированный `DamageResolver`**, пригодный для обычных ударов, навыков, эффектов местности, DoT и ответных эффектов; раздели **семейство/подтип урона** и **форму атаки (одиночная/AoE)**. Предусмотри физический (колющий/режущий/дробящий), магический (реестр будущих элементов), чистый, пользовательские типы и смешанные компоненты; **не определяй пока финальные стихии**. У юнитов введи значения сопротивлений −500…+500% и вычисляй их по одной документированной формуле. Явные иммунитеты, конверсии входящего урона в лечение/обнуление/перенаправление, зеркальное отражение, щиты, плоское снижение, предел урона и эффекты фактической потери HP должны иметь строгий порядок, общий бюджет и защиту от циклов. Обязательно реализуй и проверь случай **огненный D0=40, R=300%, 25%=10 лечения, 75%=30 отражённого урона по каждому допустимому соседнему врагу, потери HP нет**. Значение R=300% само по себе не создаёт лечение. В режиме разработчика добавь пункт **«Механики»** с конструкторами новых типов, правил и профилей; в редакторе юнита — компактный подпункт «Сопротивления» с наследованием, поиском, шаблонами и предпросмотром, **без лишних вкладок/кнопок**. Параметры и точные проценты не показывай игроку в обычном режиме. Интегрируй новые типы во все существующие редакторы, библиотеку, импорт/экспорт и миграции с общими ID и схемами. Отдельно тестируй порядок реакций, чистый урон, AoE, тактическую паузу, отсутствие бесконечного отражения, и сохранение старого контента. Любая новая редактируемая механика одновременно получает поддержку в симуляции, редакторе, схемах, импорте/экспорте и тестах. Работай по версиям, сохраняя все старые теги, отдельные ZIP-сборки, контрольные суммы и документацию. Не добавляй неопределённую пока элементальную матрицу и не выполняй пользовательский код.

## Команда ТЗ ч.6 §15 (дословно)

> Продолжай единый проект по актуальному ТЗ 0.6, сохраняя части 1–5, старые версии игры, Git-теги, ZIP-релизы и документацию. Считай игру **визуальным конструктором тактических игр**, а не игрой с зашитым набором стихий/существ. Реализуй общий реестр типизированного контента с устойчивыми ID и реактивным обновлением всех релевантных редакторов: созданный пользователем тип «Огонь» сразу доступен в навыках, обычных атаках, R, A, пассивах, тегах, гексах, реакциях и тестах. Не кодируй заранее стихийную матрицу и не требуй от пользователя программирования. Добавь **защиту A**, отдельно от R, с наследованием по всем/семейству/типу, пробитием, формулой A/(A+K) и единой точкой в `DamageResolver` после R и до FlatReduction. Добавь индивидуальные постоянные пассивы, общие переиспользуемые теги, дерево видов с наследованием, конфликты и условия без двойного применения. Поддержи боевые множители по типам, подсчёт живых союзников своего `packId`, эффекты характеристик и прозрачный предпросмотр итогов. Реализуй шесть секторов внезапного удара относительно логического направления защищающегося: 0/25/75/100% в симметричном пресете (сзади 100% — явное предположение из-за противоречия исходной формулировки). Добавь крит и сверхкрит: 100%=крит гарантирован, 125%=25% сверхкрита, 200%=сверхкрит гарантирован; все проценты и множители редактируемы. Весь бой — через существующий единый конвейер и воспроизводимые события, без новой параллельной логики. Обнови компактный режим разработчика с редакторами видов/тегов, шаблонами условий/пассивов, A/R и настройками направления/критов, без множества постоянных вкладок. Каждый новый редактируемый элемент немедленно доступен везде, где совместим, с реальным исполнением, сохранением, импортом/экспортом, миграциями и автоматическими тестами. Старые проекты сохраняют результаты через нулевую A и совместимый `legacy_combat_ruleset`; примеры с Волками и Слизями — демонстрационные, не базовый игровой контент. Все изменения должны быть проверены в Windows-сборке и подробно задокументированы.

Контракт ТЗ ч.6 §2.5: любой новый редактируемый тип, характеристика, фильтр, эффект, статус или механика проходит
`Runtime → Registry → Schema → Editor → Preview → Save/Load → Import/Export → Migrations → Automated Tests`; пункт без
реального исполнения не считается сделанным, «мёртвых» настроек в UI нет.

## Команда ТЗ ч.7 §15 (дословно)

> Продолжай проект по актуальному полному ТЗ 0.7, сохраняя все прежние правила частей 1–6. Реализуй четыре типа сценариев через общий `ScenarioDefinition`, общие системы движения, спавна, волн, целей, блока, автоатаки и одного боевого конвейера; не создавай четыре отдельные игры. Сохрани старые ТД/КТД, направление взгляда, технические пути и плавную визуальную траекторию, тактическую паузу, редактор пользовательского контента и импорт/экспорт. Для Tower Defense поддержи несколько баз и маршрутов, их редактирование ведением красной линии через смежные гексы, повторные посещения/пересечения и строгую проверку проходимости для фактических типов врагов. Волны и их тайминги настраиваются визуально, с очередью занятых спавнов и точными ссылками на линии. Оборона должна запускаться БЕЗ базы игрока, иметь простой выбираемый ИИ и отдельные защищаемые объекты; исследование — исходную точку, выход и гибкие условия победы. Добавь юниту `BlockCapacity >= 0` и самостоятельную базовую атаку с собственной областью и частотой из `AttackSpeed`, отличную от активных навыков и явного приказа атаки. Не допускай двух юнитов в одном гексе. Все новые параметры немедленно поддерживай в режиме разработчика, с компактным UI и автоматическим обновлением пользовательских списков; не требуй программирования от автора. Перед релизом проверяй тесты M7-01…M7-60, сохраняй версии Windows-сборок, миграции и документацию, не переписывай предыдущие релизы.

## Команды

```bash
dotnet build HexTactics.sln                 # сборка всех проектов
dotnet test HexTactics.sln                  # автотесты
godot --headless --path src/GodotClient --import
godot --path src/GodotClient                # запуск из исходников
# скриншот / сценарий (аргументы после --); с v0.15.0 запуск начинается со стартового меню:
godot --path src/GodotClient --windowed --resolution 1920x1080 -- --hx-start=play --hx-script="hover:5,5" --hx-screenshot=shot.png
# сценарий с проверками (код выхода 1 при провале), шаги — docs/ARCHITECTURE.md «Автоматизация»;
# --hx-user-root=<папка> — отдельная папка пользовательского контента (не трогать настоящий user://):
godot --path src/GodotClient -- --hx-user-root=/tmp/hx --hx-script="ui:menu.play;spawn:base;drag:0,4>3,2;key:Space;expect:paused:true" --hx-quit
```

Godot: **4.7.2 stable .NET** (не переходить на beta/dev). .NET SDK 8, `TargetFramework net8.0`.
Рендерер — Compatibility (OpenGL 3.3); он затеняет в sRGB-пространстве (см. `VisualConfig.ToRenderColor`).

## Версии и релизы

- Версия задаётся в двух местах и должна совпадать: `Directory.Build.props` (`HexTacticsVersion`) и `src/GodotClient/project.godot` (`config/version`).
- Процедура релиза vX.Y.Z:
  1. Обновить версию, `CHANGELOG.md`, `README.md`, `docs/ARCHITECTURE.md`, `docs/CONTENT_FORMAT.md` (и `docs/MIGRATIONS.md`,
     если менялась схема данных), создать `docs/releases/vX.Y.Z/README.md`. Чек-лист — `docs/RELEASE_CHECKLIST.md`.
  2. Коммит, затем аннотированный тег: `git tag -a vX.Y.Z -m "HexTactics vX.Y.Z"`. Теги неизменяемы — не удалять и не переносить.
  3. `pwsh tools/build_release.ps1` (тесты + экспорт + ZIP + SHA-256 + BUILD_INFO) → `release_archives/vX.Y.Z/`.
  4. `pwsh tools/verify_release.ps1 -Version X.Y.Z -Run` (на Linux: `-Launcher wine64` под `xvfb-run`,
     `WINEDLLOVERRIDES="dinput8=d"`) — сквозной регрессионный сценарий в самой сборке.
  5. Отдельным коммитом добавить архив (`release_archives/**`, обычные файлы Git, без LFS — см. D-010), скриншот
     `docs/releases/vX.Y.Z/screenshot.png`; push ветки и тега. Если push тега запрещён средой (облачная сессия),
     тег восстанавливается позже `tools/create_release_tags.ps1` по `BUILD_INFO.txt` (D-012).
- Никогда не перезаписывать существующие архивы и не переписывать опубликованную историю.
- В Git не коммитить `.godot/`, `bin/`, `obj/`, `build/`, `staging/`.

## Отчёт после версии

Кратко: что сделано, что проверено (тесты, сценарии, экспорт), какие файлы затронуты, где архив, как откатиться.
